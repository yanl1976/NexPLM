# 核心域复刻分析与执行顺序（编码 · 物料/零部件 · BOM）

> 定位：用户要求「先做最基础的四域，结合蓝本与 `TCPLM` 分析后复刻」。
> 本文是**分析结论 + 执行顺序**，不是进度台账（台账仍在 `docs/03`）；蓝本结构见 `docs/13`，分类数据见 `docs/14`。
> 所有蓝本数据均为**只读**取证（`SELECT` / `sys.*`），未对 `TCPLM` 做任何写入。

## 一、结论摘要（先看这五条）

1. **蓝本编码 = 「对象所属分类的编码」+「该分类内独立递增的流水」**（`EXP-20261108-43` 取证修正）。
   `CODERES` 里 `OBJECTTYPE='零组件'` 的记录形如 `CODES=10010100001`、`ORDINAL=00001`、`PROPERTY=ECODE`、
   `GENERATORPATH=种类ID;分类链路…`；16,343 条零件-分类关系中 **15,476 条（94.7%）零件编码以分类码开头**，
   每个分类组都从 `xxxxxx00001` 起（`10180800001`、`12040500001`…）。
   > ⚠ 此前"人工/图号为主 + 引擎为辅"的判断**是错的**：图号/手填只占约 5.3%（`0CT.325.503`、`QGDB202206601` 等）。
   > 复刻重点因此是「**按分类取号**」，而不是"按类型绑规则"。
2. **物料主数据字段已经做过一轮**（`V70`）：物料 14 个 ERP 缺口通过 `meta_field` + `ext_json` 补齐（`FErpClsID`/`FCategoryID`/`FIsProduce`…），另有 `item_design_attr`（13 列）承载设计属性。**不要重复造字段**。
3. **真正的缺口在「编码路由 / 发放流水 / 人工编码校验」和「BOM 数量与类型」**——这四项是纯后端、可独立交付、且是上层（物料/BOM/ERP 下发）的基础。
4. **11 类物料当前共用一条 `PdmItem` 编码规则**（`ItemService.resolveCode` 写死），改规则对所有类型一起生效——这是「物料编码管理」最直接的缺口。
5. **BOM 只用了 `Design` 视图 + `Quote` 类型**（蓝本 79,105 行全是这一组合），所以「BOM 三视图」在新系统已够用；缺的是**行字段**（数量四兄弟、BOM 类型、工序路线、数据来源）。

> `PSEITEM.ORIGIN`：`1`=47,597 / `2`=47,548 / 空=20,626（自制/外购二值）。

### 2.3 BOM 取值

| 维度 | 取值分布 |
|---|---|
| `LBOMTYPE` | `Quote` = 79,105（**只有报价 BOM**） |
| `PVIEWTYPE` | `Design` = 79,105（**只有设计视图**） |

> 结论：蓝本此库未使用「制造/装配 BOM」「其它视图」，新系统三视图够用，不必扩。

## 三、逐域对照与差距

### 3.1 编码管理

| 能力 | 蓝本 | 新系统 | 状态 |
|---|---|---|---|
| 规则模型 | `CODERULE` 58 码段（树）+ `CODEKIND` 编码种类 | `code_rule` 整规则（`segments_json`，段类型 `TEXT/DATE/CLASS/SEQ`） | 粒度不同，但已能表达「分类码 + 流水」 |
| **按分类取号** | `CODES = 分类码 + 分类内独立流水`（94.7% 实证） | **已实现（T-CORE-07，`EXP-20261108-43`）**：规则 `PdmItemByClass` = `CLASS` + `SEQ(5)`；流水按 `code_sequence.scope_key = 分类编码` 独立计数 | 已补齐 |
| 按类型路由 | 按「对象类型 + 编码种类」 | `PdmItem:<itemType>` 路由，无专属规则回退 `PdmItem`（T-CORE-01） | 已补齐 |
| 发放流水 | `CODERES` 60,300（`CODES`/`ORDINAL`/`CODEKINDID`/`GENERATORPATH`） | `code_issue`（T-CORE-02） | 已补齐（缺 `CODEKINDID`/`GENERATORPATH`） |
| 人工编码 | `MaxOrderCodeLength=9` + `CodeMachineDenyChar` | `nexplm.coding.manual-pattern`（T-CORE-01） | 已补齐 |
| 权限 | 编码种类授权（`CodeKindManagement`） | `system.coding.read/manage`（V74） | 细粒度待业务（B20） |

### 3.2 物料/零部件主数据

| 能力 | 蓝本 | 新系统 | 差距 |
|---|---|---|---|
| 类型 | 11 类（`ITEMTYPE`） | 8 类枚举（产品/部件/零件/标准件/工装/量具/模具/外购件） | 蓝本的 CIS/服务/废料/外协/手工单未建枚举 |
| 核心字段 | `PSEBASEFORM` 51 列 | `item_master` 13 列 + `item_design_attr` 13 列 | 覆盖约 26 列 |
| 金蝶客制 | 23 个 | `V70` 已补 12 个 `meta_field`（`ext_json`） | 已实现，注意别重复 |

### 3.3 BOM

| 能力 | 蓝本 | 新系统 | 差距 |
|---|---|---|---|
| 行字段 | `PSEBOMLINE` 37 列 | `bom_line` 18 列 | **缺数量四兄弟、BOM 类型、工序路线、数据来源、10 个客制** |
| 数量 | `TOTALQTY/USEQTY/SURPLUSQTY/SUBUSEQTY` | `qty` + `loss_rate` | 语义不同（蓝本是"总用量/单台用量/剩余/子用量"） |
| 视图 | `PVIEWTYPE=Design` | `view_type`（DESIGN/…） | 够用 |
| 类型 | `LBOMTYPE=Quote` | 无独立类型 | **缺** |

## 四、执行顺序（T-CORE-01 ~ 06）

按「下层先做、每片可独立验证」排序，全部纯后端（前端复用现有页面即可）：

| 编号 | 任务 | 依据 | 交付与验收 | 状态 |
|---|---|---|---|---|
| **T-CORE-01** | 编码规则按物料类型路由 + 人工编码校验 | 3.1「只有 `PdmItem` 一条」「缺字符集/长度校验」 | `code_rule.object_type` 命中即用、否则回退 `PdmItem`；人工编码按 `nexplm.coding.manual-pattern`（默认 `^[A-Za-z0-9._\-]{1,64}$`）校验；`CodingRuleSmokeTest` 断言「配了类型规则→走它」「非法编码 400」「无规则回退」 | 本轮开工 |
| **T-CORE-02** | 编码发放流水（`code_issue`） | 3.1「`CODERES` 60,300 vs 无流水」 | 新表 + `CodeRuleService.next` 落流水 + `GET /system/coding/issues` 分页查询；断言「取号后能查到该码」 | **已完成（`EXP-20261108-34`）**：`V77` + `next(code, objectType)` + 查询接口；`CodingRuleSmokeTest` 6/6 |
| **T-CORE-03** | BOM 行扩展：数量四兄弟 + BOM 类型 + 工序路线 + 数据来源 | 3.3 | `V78` 加 6 列（`total_qty/surplus_qty/sub_use_qty/bom_type/item_route/data_source`），`BomService` 读写；`total_qty` 空表示按层级累乘 | **已完成（`EXP-20261108-35`）**：`BomLineExtSmokeTest` 1/1（往返/默认/负数 400） |
| **T-CORE-04** | 物料类型枚举补齐（CIS/服务/废料/外协/手工单） | 3.2 | `meta_enum_item` 补 5 类 + `ItemService` 校验自然放行；前端类型下拉自动出现 | **已完成（`EXP-20261108-36`）**：`V79` 补 5 类（类型 8→13），零 Java 改动，`ItemTypeEnumSmokeTest` 1/1 |
| **T-CORE-05** | 分类多分类支持（`item_classify` 关系表） | 3.2「66 件多分类」 | 新增关系表 + 归类接口支持多选 + `item_master.class_id` 保留为主分类；数据迁移脚本待 A3 写权限 | 待业务 D1 |
| **T-CORE-06** | 编码种类权限（蓝本 `CodeKindManagement`） | 3.1 | 按规则 code 授权的 `sys_role_rule`；待业务确认是否需要 | 待业务 |

## 五、明确不做

1. **不把 11 类物料都改成自动取号**：蓝本实测大量人工/图号编码，强行统一会改变现场习惯（违反 R4 不静默改语义）。
2. **不重建 `CODERULE` 的码段树模型**：新系统整规则 + `segments_json` 已能表达，粒度差异不影响现场使用（B19 已收口 16 个对象）。
3. **不加 BOM 的「制造/装配」类型分支**：蓝本实测只有 `Quote`，加了是无用复杂度。
4. **不重复补 `V70` 已覆盖的 12 个金蝶客制字段**。

## 六、取证缺口（待验证）

- `CODERULE` 58 码段如何聚合出「每个对象类型的完整格式」（`PARENTCODERULE` + `ORDERNUM` 递归，53 个根段分别属于哪些业务）——**待验证**，T-CORE-02 落流水后可用真实发放数据反推。
- `PSEBOMLINE$`（253,829）是否等价于版本快照——**待验证**。
- 蓝本 `Coding.setting` 的 `CodeMachineDenyChar`（跳码禁用字符）具体字符集——**待取证**（`Config/Coding.setting` 可读）。
