# 二、NexPLM 系统开发方案

> 定位：以 InforCenter PLM 的业务语义与功能覆盖为蓝本，用 Java 技术栈重构的**元数据驱动、API 优先、可私有化部署**的产品级 PLM。
> 本方案是后续所有编码工作的唯一依据；任何偏离需以 ADR（架构决策记录）形式补充到本文第 9 节。

---

## 1. 目标与设计原则

### 1.1 业务目标

| 目标 | 度量 |
|---|---|
| 功能覆盖 | 旧系统一级导航 13 个域、二级功能 120+ 项全部有对应实现；核心闭环（文档/变更/工艺/任务）端到端可用 |
| 数据兼容 | 支持旧库主数据迁移（组织、用户、物料、BOM、文档元数据、文件实物），迁移可校验、可回滚 |
| 性能 | BOM 展开 10,000 行 < 2s；文档列表 100 万条分页查询 < 800ms；并发 200 用户时 P95 < 1s |
| 可维护 | 新增对象类型/字段/审批流/表单**零代码**（配置即生效）；核心代码单元测试覆盖率 ≥ 70% |
| 可扩展 | 领域模块可独立演进；对外 OpenAPI + Webhook；集成新 ERP 只写映射适配器 |
| 合规 | 三员分立、密级、操作审计不可篡改、电子签名留痕、等保三级可支撑 |

### 1.2 设计原则（按优先级）

1. **语义保真，实现重写**：保留业务对象、状态、流程、权限的语义；不复刻旧表结构与反射机制。
2. **元数据是数据，不是文件**：一切模型/表单/菜单/规则入库、带版本、可校验、可灰度、可回滚。
3. **单一状态写入口**：状态只能通过"状态机命令"变更，禁止业务代码直接 UPDATE 状态字段。
4. **API 优先**：所有能力先有 REST 契约，再有 UI；UI 只是契约的消费者。
5. **默认安全**：默认拒绝、最小权限、字段级密级、审计全覆盖、密钥外部化。
6. **可观测**：每个请求有 traceId，每个关键状态迁移有事件，每个慢查询有指标。
7. **模块化单体优先**：先保证事务一致与交付效率，按领域边界切包，达到规模拐点再拆服务。
8. **一切可测试**：领域逻辑不依赖框架；数据访问用集成测试（Testcontainers）；关键流程用 E2E。

## 2. 与主流 PLM 概念的映射（确保"形似且神似"）

| NexPLM 概念 | Teamcenter | Windchill | Aras | 旧系统 | 说明 |
|---|---|---|---|---|---|
| `PlmObject` | Item / Dataset | WTPart / EPMDocument | Item | ENTITY | 所有业务对象根 |
| `ObjectType` | Item Type | Type | ItemType | `.model` EntityType | 元数据定义 |
| `Revision`（大版本） | ItemRevision | Revision | Revision | `EVERSION`(Letter) | A/B/C，受控 |
| `Iteration`（小版本） | Iteration | Iteration | — | `EMINORVERSION`/`CURITERATION` | 每次检入+1 |
| `Lifecycle` | Lifecycle | LifeCycle | LifeCycle | `STATEID` + `.life` | 状态机 |
| `Workflow` | Workflow | Workflow | Workflow | `WORKFLOWINFO` | BPMN |
| `BOM View` | BOM View Revision | BOM | BOM | `PVIEWTYPE`(Design/Process/Manufacture) | 多视图 |
| `Baseline` | Baseline | Baseline | — | `BASELINEOBJECT` | 冻结结构快照 |
| `Change (ECR/ECN/ECN)` | Change Notice | Change Request/Order | ECR/ECN | CMAPPLY/CMNOTICE | 变更 |
| `Vault` | Volume | Vault | Vault | `DocumentVault` | 电子仓 |
| `ACL` | Access Manager | ACL | Permission | OBJECTPERMISSION + ACTIONRULE | 权限 |
| `Classification` | Classification | Classification | Classification | CLASSIFY* | 分类与属性继承 |

**改进点**：Revision/Iteration 采用业界标准两层（旧系统 `EVERSION`+`CURITERATION` 语义重叠）；
BOM 采用"关系实体 + 视图 + 有效性"三元组（业界一致做法），而非靠字符串串接。

## 5. 核心机制设计

### 5.1 元数据引擎（系统的地基）

**目标**：对象类型、字段、关系、表单、菜单、能力位、权限策略全部由元数据描述，运行期生效，无需改代码。

**存储**（数据库，非文件）：
- `meta_entity`：`code`(如 `PseItem`)、`table_name`、`parent_code`(继承)、`capabilities`(能力位集合)、
  `version_policy`、`lifecycle_policy`、`phase_policy`、`schema_json`、`version_no`、`status`(DRAFT/PUBLISHED/DEPRECATED)。
- `meta_field`：`entity_code`、`code`、`value_type`（31 种语义类型的 Java 实现）、`data_type`、`length`、
  `required`、`default_value`、`enum_code`、`ref_entity`、`ref_field`、`ui_json`、`security_level`、`sort`。
- `meta_relation_type`：`code`、`src_entity`、`dst_entity`、`link_table`、`contain_sub`、`loop_check`、`seq_step`。
- `meta_enum` / `meta_enum_item`、`meta_form`（表单布局 JSON）、`meta_action`（动作定义）、
  `meta_menu`（导航树）、`meta_lifecycle`（状态机 JSON）。

**值类型体系（31 种语义类型 → Java 策略）**：

| 类别 | 类型 | 实现要点 |
|---|---|---|
| 标量 | DefaultObjectValue / DescriptionValue / BoolValue / DateTimeValue(LONG) / DateValue | 统一 `FieldHandler`，日期统一存 UTC 毫秒（`bigint`）避免时区问题 |
| 编码 | CodeValue | 走编码器，事务内发号，唯一校验 |
| 状态 | StateValue / StageValue | 只能由状态机服务写入 |
| 枚举 | EnumValue / MultiEnumValue / EnumRadioValue / LovListValue | 码表 + 多选存 JSON 数组 |
| 版本 | VersionValue / MinorVersionValue / MajorMinorVersionValue | 整型存储 + 格式化器（A..AZ/001） |
| 人员组织 | SingleUserValue / MultiUserValue / SingleGroupValue / CompanyValue / TaskPrincipalValue | 存 ID 数组，读时批量回填名称（防 N+1） |
| 引用 | ObjectIDValue / SubDataModelValue / PseItemNameCodeValue | 引用 + 类型多态（`FORMID` 等价物 = `subtype` + `ext_json`） |
| 位置 | PositionValue / SelectPositionValue | 目录节点 ID + 路径 |
| 文件 | FileUploadValue | 文件对象 ID 列表 |
| 编码规则 | ThickRuleValue / ThinRuleValue | 编码器段定义 |

**继承与扩展**：
- 继承采用 **JOINED**（`plm_object` 主表 + 领域子表），子类型字段落在子表；
- 客户化字段一律进 `plm_object.ext_json`（JSONB），由 `meta_field` 声明后自动出现在表单与查询；
  这样**加字段不改表**（旧系统必须改 `.model` + 重建表）。
- 需要索引的扩展字段：由元数据声明 `indexed=true`，后台任务创建表达式索引 `(ext_json->>'field')`。

**校验与发布**：
- 元数据变更走 JSON Schema 校验 + 引用完整性校验（字段引用的枚举/实体必须存在）+ 破坏性变更检测
  （删字段/改类型→要求迁移脚本）。
- 发布采用**版本快照**：`meta_entity.version_no` 递增，旧版本保留；前端按 `?metaVersion=` 拉取，支持灰度。

### 5.2 对象与版本模型

```
plm_object（主表，所有业务对象）
  id, object_type, master_id, code, name, company_id, org_id,
  owner_id, owner_group_id, security_level,
  lifecycle_state, phase_state, workflow_state,
  revision(int), iteration(int), is_latest(bool), released_at,
  ext_json, version(int 乐观锁), deleted, created_*/updated_*
  UNIQUE(object_type, code, revision, iteration) WHERE deleted=false
  INDEX(object_type, company_id, lifecycle_state), (master_id), (code), GIN(ext_json)
```

- 业务子表：`pse_item(object_id, item_type, unit, material, weight, ...)`、`doc_master(object_id, vault_id, file_ext, ...)`
  等，1:1 关联 `plm_object.id`。
- 版本三层次：
  - **Master（对象族）**：`master_id` 相同即同族（旧 `EUID`）。
  - **Revision（大版本）**：A/B/C，仅在"修订"或"发布后变更"时 +1，`iteration` 归 1。
  - **Iteration（小版本）**：每次检入 +1。
- 版本生成规则：`VersionPolicy` 元数据（`Letter|Number` + 间隔符），Java `VersionFormatter` 实现，
  单测覆盖 `A..Z, AA..AZ, BA..BZ`（修正旧系统 >AG 的缺陷）。
- 检入检出：`checkout_state/checkout_user/checkout_at` 软锁 + 过期清理任务（默认 8 小时，可配）。

### 5.3 关系与 BOM

- 通用关系：`plm_relation(id, relation_type, src_id, dst_id, seq, qty, attrs_json, company_id, ...)`；
  `relation_type` 元数据描述端点类型与约束（防环、级联、序号步长）。
- BOM 专用表 `pse_bom_line`（继承通用关系语义但强类型，便于性能与统计）：
  `id, parent_id, child_id, view_type(design/process/manufacture), seq, qty, unit, scrap_rate,
   substitute_group, effect_from, effect_to, attrs_json`。
- BOM 树读取：
  - 浅层（<5 层）：一次 `IN` 批量查 + 内存装配（避免 N+1）；
  - 深层/全展开：PG `WITH RECURSIVE`，按 `view_type` + 有效性过滤，结果流式返回（SSE 或分页）。
- BOM 编辑并发：以 `parent_id + view_type` 为粒度加乐观锁版本号，冲突时返回 409 + 差异。
- 基线（Baseline）：对 `plm_relation` 与关键字段做**不可变快照**（`baseline_object` + `baseline_bom_line`），
  支持"基线 vs 当前"的结构差异比较。
- 基线/替代件/有效性：与 BOM 解耦为独立能力，可被其他对象复用。

### 5.4 权限体系（对齐旧系统五层，表达力增强）

| 层 | 新设计 |
|---|---|
| 功能点 | `sys_permission(code, module, action, name)` + `sys_role_permission` + 注解 `@RequiresPerm("pdm.doc.create")` |
| 对象类型 | 元数据 `capabilities` 声明该类型是否受 `CREATE/EDIT/DELETE` 权限管控（等价 `ModelGroups.CreatePermission`） |
| 对象实例 | `sys_acl_entry(object_id, actor_type, actor_id, actions, expire_at, source)`；`actions` 为位集合（READ/WRITE/DELETE/GRANT/CHECKOUT/RELEASE...）；支持从父对象继承（`source=INHERITED`） |
| 规则权限 | `sys_permission_rule(object_type, expr_json, actions, priority)`，条件树支持 **AND/OR/NOT 嵌套**（修正旧系统扁平结构），内置条件：属主/组/编码/名称/类型/属性值/生命周期状态/阶段/父对象属性/关系类型/密级；求值器 `RuleEvaluator` 纯函数，可单测 |
| 数据隔离 | 统一 `DataScope` 拦截器：`company`（集团）+ `orgIsolation`（组隔离映射）+ `shareMapping`（共享视图）+ `owner`；作用于 MyBatis 查询条件（`@DataScope` 注解），并有"绕过"白名单（审计留痕） |
| 字段级密级 | `meta_field.security_level` + 用户 `security_level`；读取时裁剪或脱敏（序列化层拦截） |
| 三员分立 | 角色 `SYS_ADMIN`/`SEC_ADMIN`/`AUDITOR` 互斥；安全管理员管策略与密级、审计员只读审计；关键操作双人复核（可选） |

**默认拒绝**：Controller 无 `@RequiresPerm` 且无 `@PublicApi` 时，启动期扫描报错（fail-fast）。

### 5.5 工作流与生命周期

**分工**（解决旧系统三轨混乱）：

| 关注点 | 归属 | 字段 | 写入方 |
|---|---|---|---|
| 业务审批过程 | Flowable | （流程实例表） | Flowable 引擎 |
| 对象业务状态 | 生命周期状态机 | `lifecycle_state` | 状态机命令 `LifecycleService.transition()` |
| 阶段关口 | 阶段状态机 | `phase_state` | 阶段命令（可与流程节点绑定） |
| 流程概要态 | 流程适配层 | `workflow_state` | 流程监听器（RUNNING/APPROVED/REJECTED/CANCELED） |

- **Flowable 集成**：流程定义用 BPMN 2.0（可视化设计器用 bpmn-js 嵌入前端）。
  `wf_binding(object_type, process_key, phase_policy)` 决定对象走哪个流程。
- **业务插件**：`WorkflowPlugin` 接口（`beforeNode/afterNode/onComplete/onReject`）→ Spring Bean 注册，
  内置 `ChangeStatePlugin`、`ChangePhasePlugin`、`SendNotificationPlugin`、`ErpPublishPlugin`。
  替代旧系统 `.flowplugin` 的反射类名。
- **执行人解析**：`TaskActorResolver` SPI（`USER/ROLE/GROUP/GROUP_ROLE/CREATOR/PROJECT_ROLE/FORM_FIELD`），
  支持运行时按表单字段或项目角色解析（旧系统只能靠 `ACTORINFO` 文本）。
- **会签/加签/驳回/委托/超时**：全部映射到 Flowable 原生能力（多实例会签、加签 `addSign`、跳转驳回、
  委派 `delegateTask`、边界定时器超时催办）。**驳回目标节点**由流程变量指定，支持"回退到发起人/上一节点/指定节点"。
- **生命周期定义**（`meta_lifecycle.definition_json`）：
  ```json
  {"initial":"New","states":[{"code":"New","name":"新建","allFlow":true},
   {"code":"InWorkflow","name":"审批中"},{"code":"Released","name":"已发布"},
   {"code":"Obsolete","name":"已废弃"}],
   "transitions":[{"from":"New","to":"InWorkflow","action":"submit","guard":"hasPermission('RELEASE')"},
                  {"from":"InWorkflow","to":"Released","action":"approve"},
                  {"from":"InWorkflow","to":"New","action":"reject"},
                  {"from":"Released","to":"Obsolete","action":"obsolete"}]}
  ```
  守卫用受限表达式语言（SpEL + 白名单变量），**禁止任意脚本**（安全）。
- 状态迁移全部写 `state_change_log`（from/to/action/operator/reason/flow_instance_id），审计可追溯。

### 5.6 文件仓（替代 Vault + 分布式文件服务）

- 存储：MinIO（S3），`bucket=plm-vault`；对象键 = `sha256[0:2]/sha256[2:4]/sha256`（内容寻址、天然去重）。
- 表：`file_object(id, sha256, size, mime, ext, bucket, object_key, ref_count, created_at)`；
  `file_link(id, file_id, owner_object_id, file_role(MAIN/ATTACHMENT/VIEW/DERIVED), iteration, created_at)`。
- 上传：前端直传（预签名 PUT）+ 分片（>100MB）+ 秒传（先查 sha256）；服务端只做元数据与校验。
- 下载：预签名 GET（短期有效），下载行为写审计；支持水印（PDF 服务端叠加）与只读预览令牌。
- 检入：新迭代 → 新 `file_link` 行，旧行保留（版本可回溯）；主文件唯一性由 `file_role=MAIN` + `is_latest` 保证。
- 转换：上传后发 `FileConvertRequested` 事件 → 转换代理（外部）回写 `VIEW` 派生文件（PDF/PNG/glTF）；
  失败重试与死信队列；转换状态可见。
- 迁移：旧 `DOCFILEMODEL.FILEPATH + CURVOLUMEID` → 读取旧 Vault 物理文件 → 计算 sha256 → 入 MinIO → 建 `file_object/file_link`。
- 容量治理：冷热分层（低频对象转 MinIO 归档层）、引用计数归零的孤儿对象延迟清理（30 天）。

### 5.7 编码器

- `code_rule(id, code, name, segments_json, scope_json, status)`；
  `segments_json` = `[{"type":"CONST","value":"P"},{"type":"DATE","format":"yyyy"},{"type":"SEQ","width":4,"base":10,"reset":"YEAR"}]`。
- 发号：`code_sequence(rule_code, scope_key, current_no)` + `SELECT ... FOR UPDATE`（或 Redis 原子自增 + 落库校正），
  事务内发号，失败回滚不占号；支持"预占号"（`state=RESERVED`）与"作废回收"（`VOID`，不回收序号，避免重号）。
- 唯一性：`plm_object.code` 按 `object_type + company_id` 唯一；跨类型共享编码空间时用 `code_space` 元数据声明。
- 兼容旧规则：提供 `.coderule` 导入器（旧 `THICKRULE/THINRULE` → 新 `segments_json`）。

### 5.8 审计与合规

- `sys_audit_log`：append-only，按月分区；字段含 `trace_id, user_id, org_id, module, action, object_type,
  object_id, before_json, after_json, ip, ua, result, created_at`。
- **哈希链**：每行存 `prev_hash` + `hash = SHA256(prev_hash + 本行规范化内容)`，按天锚定（每日末哈希写 `audit_anchor`），
  满足"不可篡改"举证。
- 电子签名：`sys_signature(id, object_id, user_id, meaning, file_hash, signed_at, cert_serial)`；
  审批签署时对"对象版本 + 主文件哈希"签名，防事后替换。
- 三员审计视图：审计员只读、可导出；安全管理员可配策略但不可删日志（数据库层面 REVOKE DELETE）。

### 5.9 事件与集成

- 领域事件（进程内，`ApplicationEventPublisher`）→ 事务提交后发布（`@TransactionalEventListener(AFTER_COMMIT)`），
  保证"业务成功才发事件"。
- 跨进程事件（RabbitMQ）：exchange `plm.domain`（topic），routing key = `pdm.doc.released` 等；
  消费失败进死信队列 + 人工重放。
- 对外集成：
  - **ERP 适配器**：`ErpAdapter` 接口（`pushMaterial/pushBom/pushDoc/pushRouting/pullProject`），
    金蝶云星空为首个实现（WebAPI + 字段映射配置表 `itg_mapping`，替代 `ERPConfig.xml`）；
    映射配置可在界面维护、可试运行（dry-run）输出报文差异。
  - **OpenAPI**：`/openapi/v1/**` 独立鉴权（API Key + 作用域），限流与审计；Webhook 支持签名重试。
  - **SSO**：OAuth2/OIDC + LDAP/AD 双通道。

### 5.10 检索

- 默认：PG `tsvector` 生成列（code/name/description）+ GIN 索引，支持中英混合（`zhparser` 可选）。
- 扩展：`SearchProvider` 接口，可切 Elasticsearch（元数据驱动索引模板，字段级 `searchable`）。
- 高级查询（旧 `QueryMachine`）：元数据生成查询条件树 → 编译为安全 SQL（字段白名单 + 参数化），
  支持保存查询、共享查询、订阅。

## 9. 架构决策记录（ADR 摘要）

| # | 决策 | 理由 | 放弃的方案 |
|---|---|---|---|
| ADR-01 | 模块化单体优先，不直接微服务 | 事务一致性（BOM/变更/权限）与交付效率；边界已按领域切好 | 一开始拆 8 个微服务 |
| ADR-02 | 用 Flowable 而非自研工作流 | 会签/加签/委托/超时/驳回是成熟能力，自研成本与风险极高 | 复刻旧 `WORKFLOW*` 表与引擎 |
| ADR-03 | 元数据入库而非 XML 文件 | 可版本/校验/灰度/审计；避免改文件即改生产 | 复刻 `.model/.menu` 文件体系 |
| ADR-04 | 扩展字段用 JSONB | 客户化字段不改表；PG 表达式索引保证查询性能 | 每客户改表 / EAV 全表 |
| ADR-05 | 对象主表 + 领域子表（JOINED） | 兼顾通用能力（权限/版本/流程）与领域强类型 | 单表全字段 / 全 JSON |
| ADR-06 | MinIO 内容寻址 | 去重、秒传、不可变、易扩容 | 复刻 Vault 卷 + IP Range 选点 |
| ADR-07 | 三状态字段但单一写入口 | 保留旧语义（三轨）又消除不一致 | 合并为单字段（业务表达不足） |
| ADR-08 | 前端元数据驱动渲染 | 与后端元模型同源，避免前后端双写表单 | 每类型手写页面 |
| ADR-09 | 权限规则用嵌套条件树 + SpEL 白名单 | 表达力强于旧扁平 AND/OR，且可控安全 | 自由脚本（Groovy/JS） |
| ADR-10 | CAD 转换走外部代理 | CAD 解析非 Java 优势，隔离可替换 | Java 直接解析 DWG |

## 11. 交付标准（Definition of Done）

一个功能视为完成，必须同时满足：

1. 领域逻辑有单元测试（核心分支覆盖）、有集成测试（真实库）；
2. REST 契约已进 OpenAPI，前端 SDK 已更新；
3. 权限点已注册并在 UI 隐藏/后端校验双向生效；
4. 关键操作写审计，状态迁移写状态日志；
5. 有错误码与用户可读提示（中英）；
6. 通过该模块 E2E 主流程脚本；
7. 文档更新（模块说明 + 数据字典）；
8. 无 P0/P1 缺陷，静态扫描（SpotBugs/ESLint）零新增告警。
