# 六、系统探查记录（EXP）

> **用途**：把每次对 NexPLM（新系统）以及 PLMSOFT（旧系统蓝本）的 **代码 / 数据 / 环境** 探查集中沉淀，复盘时能还原"当时看到了什么、为什么这样决策"。
>
> **记录约定**
> 1. 每次探查结束**立即追加**一条，编号 `EXP-YYYYMMDD-NN`（同日递增），旧条目只增不删。
> 2. 结论被后续事实推翻时：新开一条说明新证据，并在旧条目「状态」列标注 `已被 EXP-xxx 推翻`。
> 3. 每条固定五段：**目标问题 → 范围与方法 → 关键发现（带 `路径:行号` 证据）→ 结论与决策 → 遗留与后续动作**。
> 4. 只写事实与证据；推测必须标「待验证」，不得混入结论。
> 5. 影响阶段交付的结论，同时回填 `03-分阶段实施计划.md` 的「已验证事实」。
> 6. 临时验证脚本用完即删（结论留在本文件，不靠脚本留存证据）。
>
> **与其它文档的分工**：本文件记「怎么查到的」（过程与证据）；`03-分阶段实施计划.md` 的「已验证事实」记「验证通过什么」；`00-现状分析报告.md` 记旧系统本身的静态结论。三者不互相抄写，只交叉引用。

## EXP-20261106-01 前端 BOM 界面与批量/序号入口勘察

**目标问题**：前端是否已有「批量改用量」「批量替换子件」「调整 BOM 序号」的入口？若没有，工具栏与表格的插入点在哪？

**范围与方法**：`frontend/src` 全量检索（`batch` / `update-qty` / `batch/replace` / `draggable` / `contextmenu` / `selection-change`），并逐个读取 `views/item/*`、`api/item.ts`、`router/index.ts`。

**关键发现**
1. BOM 界面全部集中在 `frontend/src/views/item/ItemDetailView.vue`，无独立 BOM 组件；BOM 是 `el-tabs` 的第一个页签（`ItemDetailView.vue:45`），树表用 `row-key="lineId"` + `:tree-props="{ children: 'children' }"` + `default-expand-all`。
2. `bomApi.move` 已在 `frontend/src/api/item.ts` 封装，但**全前端无调用点**；仓库无 `vuedraggable` / `sortablejs` / 任何 `@contextmenu` 右键菜单，故"拖拽调序号"实际未实现。
3. 「批量改用量」「批量替换」前端 0 命中：`/bom/batch/update-qty`、`/bom/batch/replace` 仅存在于后端 `BomController.java:99`、`:108` 与 `ItemSmokeTest`。
4. BOM 表无 `type="selection"` 列、无 `@selection-change`，即当时不具备多选能力。
5. 工具栏唯一定义处：`ItemDetailView.vue:46-66`；表格列定义 `:81-114`；行内操作（编辑/备选件/删除）`ItemDetailView.vue:104-110`。
6. 导入/导出、基线、替代件、BOM 展开/汇总均已在前端落地（同文件多 tab + 多弹窗），非缺口。

**结论与决策**
- 批量按钮插入工具栏（`ItemDetailView.vue:61` 之后），多选列加在表格首列，行操作追加「上移/下移」。
- 序号调整**不引入拖拽库**（离线环境装包成本 + 交互复杂度），改为按钮复用已封装的 `move` 接口，持久化语义一致。
- 批量结果统一用一个弹窗展示「成功/跳过计数 + 逐行原因」，原因文本做 HTML 转义后再 `dangerouslyUseHTMLString` 渲染。

**遗留与后续动作**
- 已全部落地并在 `03-分阶段实施计划.md` 的 P3 条目中登记；新的集成用例见 `ItemSmokeTest#bomBatchUpdateQtyAndReplace`、`#bomMoveReorderAndDuplicateGuard`。
- 若后续确实要拖拽交互，只需在现有 `onMoveBom` 之上接一层拖拽事件，无需改后端。

## EXP-20261106-02 后端 BOM 代码清单与缓存现状

**目标问题**：BOM 能力散落在哪些后端文件？是否已有缓存可复用/需要失效？

**范围与方法**：`backend/plm-platform/src/main/java/com/nexplm/platform/item/` 目录遍历 + 全仓库检索 `caffeine|redis|@EnableCaching|spring-boot-starter-cache`。

**关键发现**
1. 入口：`api/BomController.java`（tree / add / update / remove / move / batch-update-qty / batch-replace / validate / summary / rollup / export / import-preview / import / where-used）、`api/BomBaselineController.java`、`api/BomAlternateController.java`、`api/BomDtos.java`。
2. 服务：`service/BomService.java`（31.5 KB，核心）、`BomExcelService.java`、`BomBaselineService.java`、`BomAlternateService.java`、`BomViews.java`（视图口径唯一来源：DESIGN / PROCESS / MANUFACTURE）。
3. 持久化：`mapper/BomLineMapper.java` 仅 `extends BaseMapper`，**无 MyBatis XML**；展开/汇总直接用 `JdbcTemplate` 手写递归 CTE。
4. **BOM 全链路无缓存**：pom 无 caffeine/redis 依赖，无 `@EnableCaching`，`BomService` 内无缓存字段。项目内仅两处内存缓存且与 BOM 无关：`metadata/service/MetaService.java:71`、`lifecycle/service/LifecycleService.java:50`（均为 `ConcurrentHashMap`）。
5. 树展开是**逐层查询**（`BomService.childrenOf`，`ORDER BY b.line_no, b.id`），即 N+1：每层每个父件一次 SQL。

**结论与决策**
- 性能优化先量后改：不预先加缓存，先压测（见 EXP-20261106-06）。实测 10,520 行树展开 351ms，落在 2s 预算内，故**暂不引入结构缓存**，避免过早引入一致性负担（BOM 行任意写操作都要失效缓存）。
- 若未来单树规模上到 5 万行，优先把 `childrenOf` 的逐层查询改成"整树一次递归 CTE + 内存组装"，再考虑缓存。

**遗留与后续动作**
- 缓存失效策略（写操作 → 按 rootId 失效）留到确有必要时再设计，无 TODO 阻塞。

## EXP-20261106-03 `bom_line` 表结构与序号唯一性

**目标问题**：用「两次 `move` 互换 `line_no`」实现上移/下移，是否会撞唯一索引？

**范围与方法**：读 `backend/plm-app/src/main/resources/db/migration/V11__item.sql` 建表段。

**关键发现**
1. 建表：`V11__item.sql:77-95`，`line_no int NOT NULL DEFAULT 10`，`version` 乐观锁字段。
2. 唯一索引只有 `uk_bom_line (parent_object_id, view_type, child_object_id)`（`V11__item.sql:95`），**不包含 `line_no`**。
3. `BomService.move` 只传 `newLineNo`（`newParentId` 为 null）时不会触发换父校验，直接更新 `line_no` 与 `version`。

**结论与决策**
- 两次 `move` 互换 `line_no` 安全：中间态两行同 `line_no` 不违反约束，排序由 `ORDER BY line_no, id` 保证稳定。
- 前端 `onMoveBom` 依此实现，成功后重新 `loadBom` 而不是本地改数组，避免与服务端排序口径漂移。

**遗留与后续动作**
- 无。若将来给 `line_no` 加唯一索引，必须改成一侧先置临时值的三步交换。

## EXP-20261106-04 批量接口契约与校验语义

**目标问题**：批量改用量/批量替换的真实请求字段、校验分支与返回结构，前端如何对齐？

**范围与方法**：读 `api/BomDtos.java:146-163` 与 `service/BomService.java:355-468`。

**关键发现**
1. `BomBatchQtyReq(lineIds @NotNull, qty, lossRate, unit)`；`BomBatchReplaceReq(fromChildId @NotNull, toChildId @NotNull, viewType, parentIds)`；两者返回 `BomBatchResult(total, updated, skipped, messages)`（`BomDtos.java:146-163`）。
2. 改用量（`BomService.java:355-393`）：`qty/lossRate/unit` **三者全空 → 400**；`qty <= 0 → 400`；SQL 用 `COALESCE(?, 列)` 只覆盖非空字段；每行先判 `inSubtree(rootId, line.parentObjectId, view)`，不属于该树的行 **不修改**，`skipped++` 且写入 `messages`「BOM 行不属于该零部件的结构」；行不存在同样跳过。
3. 批量替换（`BomService.java:400-468`）：`fromChildId == toChildId → 400`；按 `child_object_id + view_type` 拉候选行，逐行判越权、已存在重复（文案「目标父件下已存在该子件」，前端断言用「已存在」）、`ensureNoCycle` 成环，命中即 `skipped++`。
4. 因此"跳过"不是异常，而是**批量语义的一部分**：部分成功必须回显原因，前端不能只看 HTTP 200。

**结论与决策**
- 前端弹窗只提交被勾选的字段（`null` 表示不改），并把 `updated/skipped/messages` 原样呈现，避免"看起来成功其实全跳过"。
- 测试断言与文案对齐：重复原因断言用「已存在」子串，越权断言用 `updated=0 / skipped=N`。

**遗留与后续动作**
- 已知局限：批量改用量不支持按百分比调整、不支持按父件过滤（`parentIds` 只在替换侧提供）。若业务需要，扩展 DTO 而非新增接口。

## EXP-20261106-06 性能压测造数可行性

**目标问题**：要验证「10,000 行 BOM 展开 < 2s」，能否绕过接口直接造数？需要哪些必填列？

**范围与方法**：读 `db/migration/V1__baseline.sql:321-354`（`plm_object`）与 `V11__item.sql:10-23`（`item_master`）。

**关键发现**
1. `plm_object` 必填列：`object_type, master_id, code, name, company_id, lifecycle_state`；其余有默认值（`ext_json` 默认 `{}`、`is_latest` 默认 true 等），且**无外键**，可任意指定 id 段。
2. `item_master` 必填：`object_id, item_type`（`unit` 默认 `EA`）。
3. `bom_line` 无外键约束，`parent_object_id`/`child_object_id` 直接存 `plm_object.id`。
4. 遂可 `INSERT ... SELECT FROM generate_series(...)` 在库内一次生成上万个节点与行。

**结论与决策**
- 压测走 SQL 造数 + MockMvc 真实接口计时（含 JSON 序列化），避免上万次 HTTP 调用把被测耗时淹没。
- 结构取 4 层「总成 → 20 部件 → 各 25 子部件 → 各 20 零件」= 10,521 节点 / 10,520 行。
- 实测（`BomPerformanceTest`）：树展开 351ms、BOM 展开 375ms、汇总 `leafOnly=true` 202ms；汇总返回 10,000 行、首行 `totalQty=1`，证明叶子口径未漏算。

**遗留与后续动作**
- 该用例固定跑在内嵌 PG 上，CI 耗时可接受（约 18s）。未覆盖"并发 200 请求"场景，压测细化留到 P10。

## EXP-20261106-07 本机测试与构建命令坑

**目标问题**：在 Windows + PowerShell 环境下，NexPLM 后端测试/前端构建的可靠命令是什么？

**范围与方法**：反复试跑 `mvn` 各参数组合与 `npm run build`，记录失败形态。

**关键发现**
1. `mvn -o -pl plm-app -Dtest=… test` → `Could not find artifact com.nexplm:plm-common`：单模块运行不会先构建兄弟模块，**必须加 `-am`** 走反应堆。
2. `mvn -o -DskipTests install` → `maven-install-plugin:3.1.3` 未缓存且离线，失败；因此不能用 install 预装兄弟模块。
3. 用 `-Dtest=类名#方法` 指定用例时，其它模块无匹配用例会让 surefire 报 `No tests matching pattern … were executed!`，需 `-Dsurefire.failIfNoSpecifiedTests=false`。
4. PowerShell 下该参数**必须加引号**（`"-Dsurefire.failIfNoSpecifiedTests=false"`），否则被拆成 `-Dsurefire` + `.failIfNoSpecifiedTests=false`，报 `Unknown lifecycle phase ".failIfNoSpecifiedTests=false"`。
5. 前端校验命令为 `npm run build`（= `vue-tsc --noEmit && vite build`），项目**未配 ESLint**，故"构建通过"即类型检查通过。

**结论与决策**
- 后端测试标准命令（可复用于文档与 CI）：
  ```powershell
  cd NexPLM/backend
  mvn -o -pl plm-app -am "-Dtest=ItemSmokeTest" "-Dsurefire.failIfNoSpecifiedTests=false" test
  ```
- 全量：`mvn -o -pl plm-app -am test`（当前 29 个用例：12 单测 + 17 集成）。

**遗留与后续动作**
- 无。CI 若在 Linux 下运行可去掉引号，但保留 `-am` 与 `-Dsurefire.failIfNoSpecifiedTests=false` 更稳。

## EXP-20261106-08 Flowable 版本选型与集成实测

**目标问题**：P4 要集成工作流引擎，选哪个 Flowable 版本能在 Spring Boot 3.3.5 / Java 17 上跑通？表结构与流程定义如何与现有 Flyway、classpath 结构共存？

**范围与方法**：读根 `pom.xml` 版本属性；`Invoke-WebRequest` 取 `flowable-spring-boot-starter-process` 的 `maven-metadata.xml` 与 7.1.0 的 pom；`mvn -pl plm-platform -am -DskipTests compile`（联网）验证解析；随后写测试实跑，观察引擎日志。

**关键发现**

## EXP-20261106-09 加签动态加实例与委托模型

**目标问题**：① 会签进行中如何给节点动态追加审批人？② 「委托他人办理」该改任务 assignee 还是只在业务层放行？

**范围与方法**：运行时会签实例的 `act_ru_execution` 快照；下载 `flowable-engine-7.1.0-sources.jar` 阅读 `AddMultiInstanceExecutionCmd` 源码；核对 `sys_user / sys_user_role / sys_user_group / sys_user_org / sys_group_role` 关系表。

**关键发现**
1. 会签运行时的执行树（实测 `act_ru_execution`）：
   ```
   流程实例执行   act_id_=null       is_scope_=t  is_active_=t   (id = processInstanceId)
     └ 多实例根   act_id_=countersign is_mi_root_=t is_active_=f
         ├ 实例子执行 …             is_mi_root_=f is_active_=t  ← task.executionId 指向这里
         └ 实例子执行 …
   ```
2. `AddMultiInstanceExecutionCmd` 的 `searchForMultiInstanceActivity(activityId, parentExecutionId, …)` 是**从传入执行的子执行里递归**找 `isMultiInstanceRoot` 的执行。因此：
   - 传 `task.getExecutionId()`（实例子执行）→ 其子执行无 miRoot → 报 `No multi instance execution found for activity id countersign`；
   - 传多实例根自身 → 同样找不到（引擎只看子执行）；
   - **必须传多实例根的父执行**（本例即流程实例执行）。
3. 该方法对并行多实例会把根执行 `setActive(true)/setScope(false)`，随后 `planContinueMultiInstanceOperation` 新实例；`nrOfInstances` 自增，故「全票」完成条件仍成立。
4. 用户与组织/组/角色都是**多对多**：`sys_user_org`、`sys_user_group`、`sys_user_role`、`sys_group_role`；`sys_user` 表**没有 org_id 列**，按组织解析执行人必须走 `sys_user_org`，且组织含子树要用 `sys_org.path` 前缀。
5. `TaskQuery` 支持 `or() … endOr()` 组合多个 `taskAssignee`，可用于「本人 + 委托给我的人」合并待办。

**结论与决策**
- 加签：`multiInstanceRootParent(task)` 沿 `act_ru_execution.parent_id_` 上溯到 `is_mi_root_=true` 的执行，返回其父执行 id；这样也兼容子流程内嵌套会签。
- 委托**不改任务 assignee**，只在两处放行：① 待办查询合并「生效委托给我的 owner」的任务；② 办理/驳回/加签的归属校验允许受托人操作，并在意见里加「[代 XXX 办理]」标记。好处是委托到期或撤销后立即恢复原状，无需回写引擎数据。

**遗留与后续动作**
- 委托按 `processKey` 限定已在解析时校验；按对象类型/组织限定未做。
- 超时催办需打开 `flowable.async-executor-activate` 并配定时器，属 P4 后续项。

## EXP-20261106-10 已办与当前活动节点的查询口径

**目标问题**：「我的已办」「我发起的流程」分别该查引擎历史表还是业务表？当前活动节点怎么取？

**范围与方法**：核对 Flowable 7.1 的历史表（`act_hi_taskinst`）与运行时任务表（`act_ru_task`）列名，实跑 `HistoryService` 查询验证。

**关键发现**
1. 已办用 `historyService.createHistoricTaskInstanceQuery().taskAssignee(userId).finished()`，排序 `orderByHistoricTaskInstanceEndTime().desc()`；`HistoricTaskInstance` 提供 `getDurationInMillis()` 与 `getDeleteReason()`（驳回/撤回后为删除原因），无需自己算耗时。
2. 当前活动节点一次批量 SQL 取：`SELECT proc_inst_id_, name_ FROM act_ru_task WHERE proc_inst_id_ IN (…) ORDER BY create_time_`；`act_ru_task` 的进程实例列是 `proc_inst_id_`、名称列是 `name_`（注意带下划线后缀，与业务表命名不同）。

**结论与决策**

## EXP-20261106-11 插件/签名/巡检/催办的四项实现口径

**目标问题**：① 流程完成后如何安全驱动业务副作用？② 电子签名怎样才「可核验」？③ 巡检与催办如何做成可反复执行的幂等操作？

**范围与方法**：读 `LifecycleService.transition`（自有 `@Transactional`）；核对 `doc_master.main_file_id` 与 `file_object.sha256`；对照 Flowable 运行时/历史表列名；实跑测试验证。

**关键发现**
1. **插件不能直接在主流程事务里跑**：`LifecycleService.transition` 自身带 `@Transactional`，它抛异常会穿过其代理边界把当前事务标记 rollback-only，导致流程提交失败。改为「事务内注册 `afterCommit` 回调 → 每个插件用 `REQUIRES_NEW` 独立事务执行，异常只 warn」，主流程提交成功后才执行业务副作用。
2. **签名摘要链路**：`doc_master.main_file_id → file_object.sha256`（`file_object` 上有 `uk_file_object_sha` 唯一索引，同一内容只存一份）。非文档对象在 `doc_master` 无行，摘要留空、核验结果为 `UNKNOWN`，而不是报错。
3. **巡检判定口径**：「引擎是否还有实例」看 `act_ru_execution.proc_inst_id_` 是否存在；「终态是完成还是终止」看 `ACT_HI_PROCINST.delete_reason_`（有删除原因=TERMINATED，无=COMPLETED）。
4. **催办幂等**：同一 `task_id` 在窗口内已有 `REMIND` 即跳过；时间窗用 PG 的 `make_interval(hours => ?)`，避免字符串拼 `interval` 的类型问题。
5. **踩坑（NPE→500）**：空签名列表时 `currentFileShas` 返回 `Map.of()`，随后 `currentShas.get(row.fileId())` 中 `fileId` 为 null；`Map.of()` 的 `get(null)` **抛 NPE**（HashMap 则返回 null）。修复为返回 `HashMap` 并对 `fileId == null` 单独判断。

**结论与决策**
- 业务插件定位为「尽力而为的副作用」：不阻断流程、独立事务、失败留日志；需要强一致的业务动作必须显式设计为重试任务。
- 电子签名只存「签名时刻的摘要」，核验结果查询时实时计算，不把易过期状态落库。
- 巡检 `fix=true` 只自动修正可判定的漂移（孤儿 link 置终态），生命周期类问题只报告，避免自动改错业务状态。
- 催办做成可被外部调度反复调用的幂等接口，而非内置定时器（暂不启用 Flowable async executor）。

**遗留与后续动作**
- `SendNotification` 插件待 P8 通知模块（消费 `wf_comment` 的 `REMIND`/`APPROVE`）；`ErpPublish` 待 P6；bpmn-js 设计器与前端工作流页面未做。

## EXP-20261106-13 变更申请接入工作流的接口边界与回写口径

**目标问题**：P5 要让「ECR 提交 → 发起审批 → 归档/撤回回写申请状态」，落地前必须确认：① 现有 `WorkflowService.start` 对业务对象有哪些硬校验；② 不在 `plm_object` 表里的业务对象（ECR）在待办/已办/实例列表里能否显示编码与名称；③ 插件回写与实际状态可见性之间的时序。

**范围与方法**：只读通读 `WorkflowService.java`（发起、待办、已办、实例、绑定选路、签名）、`WfPluginRegistry.java`、`LifecycleAdvancePlugin.java`、`V15__workflow.sql`、`V18__change.sql`；对照 `WorkflowSmokeTest` 既有断言；实跑 `ChangeSmokeTest` 验证（内嵌 PG + Flowable）。

**关键发现**
1. **发起流程强制要求对象在 `plm_object`**：原 `WorkflowService.start` 第一行 `requireObject(req.objectId())`，SQL 为 `SELECT COUNT(1) FROM plm_object WHERE id = ? AND deleted = false`。变更申请存于 `chg_ecr`（`V18__change.sql:17-40`），不在 `plm_object`，直接发起必然 404 `OBJ.NOT_FOUND`。
2. **`wf_instance_link` 对 `object_id` 无外键**：`V15__workflow.sql:35-50` 只有 `object_type varchar(64)` + `object_id bigint` 与索引，故「关联非 plm_object 对象」在存储层本就合法，缺的只是服务层判定。
3. **编码/名称依赖 `LEFT JOIN plm_object`**：待办/已办/实例的 `code`、`name` 全部来自 `o.code`/`o.name`（原 `WorkflowService.java:363/442/476/750` 附近的实例、我发起、对象实例、loadLinks 四处）。非 plm_object 对象即使能发起，列表上的对象列也会是空。
4. **条件绑定上下文同样只读 `plm_object`**：`bindingContext` 只 SELECT `plm_object` 快照 + `ext_json`，ECR 拿到的上下文为空 Map（`{}` 条件仍能命中，但无法按状态/类型分流）。
5. **`LifecycleAdvancePlugin` 只按 id 取生命周期**（原 `:76-78` `SELECT lifecycle_state FROM plm_object WHERE id = ?`），不带 `object_type`。ECR 与 plm_object 都是雪花 id，碰撞概率极低但不为零，属可消除的风险面。
6. **插件的 afterCommit 时序决定了响应体口径**：`WfPluginRegistry.java:39-50` 在事务内注册 `afterCommit`，故 `ChgService.submit` 返回的 `detail()`（事务内取）仍是 `SUBMITTED`，插件跑完后再 GET 才是 `REVIEWING`。前端因此必须在提交后重拉详情，否则状态与流程实例不同屏。
7. **测试坑：全局 `non_null` 序列化**：`plm-app/src/main/resources/application.yml:28` 配了 `default-property-inclusion: non_null`，空字段被**省略**而非输出 null；`JsonNode.path("approvedAt").isNull()` 对「字段不存在」返回 false，撤回用例因此误报失败，必须改查库（`SELECT COUNT(1) ... approved_at IS NOT NULL`）。
8. **既有 `ecnProblemAndExecutionFlow` 用例曾用 `UPDATE chg_ecr SET status='APPROVED'` 绕过审批**（原注释「审批流尚未与变更打通」）。打通后已改为真实走「提交 → 初审 → 会签 → APPROVED」，顺带覆盖了集成链路。

**结论与决策**
- 不为 ECR 造 `plm_object` 影子行（会造成双写与状态二义），改为**按类型兜底**：`requireObject(objectType, objectId)` 对 `ChgEcr` 查 `chg_ecr`；四处展示 SQL 改为 `COALESCE(o.code, ce.code)`/`COALESCE(o.name, ce.title)`，join 条件用 `AND l.object_type <> 'ChgEcr'` 与 `= 'ChgEcr'` 互斥，避免同一 id 两个来源都命中。
- `bindingContext` 补 `ChgEcr` 的 `objectType/code/name/changeType/priority/status`，使 `condition_json` 可按 ECR 状态或变更类型选不同流程（当前只注册一条 `{}` 兜底）。
- 流程与业务状态的分工定死：**`ChgService` 只负责「提交」这一业务动作**（`DRAFT→SUBMITTED` 并发起流程），**`ChgWorkflowPlugin` 只负责流程事件回写**（`→REVIEWING` / `→APPROVED` / `→DRAFT`），回写只接受 `SUBMITTED/REVIEWING` 两个在途状态，已批准或已关闭的单据不被迟到事件回退。

## EXP-20261106-14 变更三套状态机能否复用 P1 的元数据生命周期

**目标问题**：P5 任务 7 要求把 ECR / ECN / Problem 三套阶段状态机改成「元数据定义」。落地前必须确认：① P1 已有的 `meta_lifecycle` 是否够通用、能否承载非 `plm_object` 的单据状态机；② 既有「生命周期设计器」的编辑行为会不会破坏自定义字段；③ P1 的状态迁移执行链路能否直接复用。

**范围与方法**：只读核对 `V1__baseline.sql` 建表、`LifecycleService`（解析/列表/保存校验）、`LifecycleController`（权限与路由）、前端 `LifecycleView.vue`（表单回写）；对照 `V18__change.sql` 的状态字段现状；实跑 `ChangeSmokeTest`（含新增的元数据改动用例）验证运行时确实读元数据。

**关键发现**
1. **`meta_lifecycle` 是通用定义表**：`V1__baseline.sql:307-318` 只有 `code/name/type/definition_json/version_no/status`，`type` 默认 `'MAIN'` 但唯一索引在 `code` 上（`:318`）。
2. **代码里没有任何按 `type` 过滤的查询**：`LifecycleService.java:61-64` 的 `listDefinitions()` 是全表 `orderByAsc(code)`，设计器因此会自然列出所有状态机——新增 `type='CHG'` 的三行无需改前端即可被编辑。
3. **解析器只认固定字段**：`LifecycleService.java:35-43` 的 `StateDef(code,name,allFlow)` / `TransitionDef(from,to,action,label)`，`:86` 的 `parse` 忽略未知字段；保存时 `updateDefinition` 也是同一套校验。→ 在状态上塞 `mainEditable` 之类的自定义标记，**运行期读得到，但会被一次「设计器保存」抹掉**。
4. **设计器确实只回写三列**：`LifecycleView.vue:47-48` 的「允许发起任意流程」开关绑 `row.allFlow`，`:122` 新增状态也是 `{code,name,allFlow}`。→ 依赖自定义标记的设计会在设计器保存后悄悄失效。
5. **P1 的执行链路不能直接复用**：`LifecycleService` 的迁移是更新 `plm_object.lifecycle_state` 并写 `plm_state_log`（按 `plm_object.id`），而 ECR/ECN/Problem 在 `chg_*` 表里、状态列是 `status`。可复用「定义」，不可复用「执行」。

**结论与决策**
- 复用 `meta_lifecycle` 承载三套状态机（`type='CHG'`，code = `CHG_ECR`/`CHG_ECN`/`CHG_PROBLEM`），复用现成设计器与审计；**不新建状态机表**。
- 不依赖自定义状态标记，改用**派生规则**：可编辑主档 = 状态等于 `initial`；可调整关联对象 = 状态等于 `initial` 或是 `submit`/`review` 迁移的终点。这样设计器随意保存也不会改变行为。
- 只读定义、不自建执行链路：新增 `ChgStateMachine` 负责「解析 + 判定 + 取目标状态」，实际 UPDATE 仍由各业务服务/插件执行（保持 `chg_*` 表自己的 `updated_at/updated_by` 语义）。
- **不做缓存**：状态机只在写操作时读一行主键查询，换来设计器改完即时生效；相比缓存省掉一条失效通知链路。
- 自迁移（`from == to`）用于表达「该状态允许此动作但不改状态」：已通知状态下再下发通知、执行中重复执行。

**遗留与后续动作**
- 变更三套状态机目前**没有状态变更流水表**（时间线靠 `wf_comment`/`chg_*` 时间戳派生）。若需要「谁在何时把状态从 A 改到 B」的强审计，可在 `ChgStateMachine.require` 统一落一张 `chg_state_log`；是否落地待产品确认。
- 设计器页面把 `CHG_*` 与对象生命周期混在一块展示；若要区分，需要给 `LifecycleView` 加 type 分组（当前无影响，未改）。

## EXP-20261106-15 P6 工艺表基线与工艺路线数据模型

**目标问题**：P6 工艺（CAPP）开工前要确认：① 基线是否已有工艺相关表可复用；② 新增表的公司/权限/编号惯例；③ 新建数据的坑位（主键、唯一索引）。

**结论与决策**
- 工艺路线按「主档 + 工序」两张表落地；工序**整表替换**保存（一次事务删旧插新），前端不做差异比对，避免并发下的行级 diff 逻辑。

**遗留与后续动作**

## EXP-20261106-16 工序序号重建为何必须「删表重插」

**目标问题**：P6-2 要做「序号重建」（把乱掉的工序号一键规整为 10/20/30）和工序上移/下移。改号有两种实现：原地 `UPDATE seq_no`，或读出后重插。落地前确认哪种在唯一约束下不会中途失败。

**范围与方法**：核对 V21 建表索引；构造 5/7/9 的乱序数据实跑 `CappSmokeTest.resequenceAndCraftOwner`；对比两种实现的执行顺序。

**关键发现**
1. **唯一索引是行级的**：`V21__capp_routing.sql` 中 `CREATE UNIQUE INDEX uk_capp_step_seq ON capp_routing_step (routing_id, seq_no)`，同一条路线内工序号不可重复，但索引检查发生在**每条语句提交时**（PostgreSQL 普通唯一索引非 DEFERRABLE）。
2. **原地改号会中途撞键**：把 5→10、7→20、9→30 按顺序 UPDATE 时，第一条把 seq_no 改成 10 的瞬间若已有另一行是 10（或先改的那行恰好等于后改的目标）就立刻违反唯一约束。常见规避是「先整体加偏移再改回」两步 UPDATE，但仍要额外记住原值。
3. **删表重插天然无冲突**：读出旧工序（含名称/类型/工时/工作中心）→ `DELETE` 该路线全部工序 → 按新序号逐行 `insertStep`。因为旧行已全部消失，中间态没有任何唯一键压力；顺带修复历史脏号（如 0、负数、重复序）。
4. **代价可接受**：工序行没有外部引用（P6-1 阶段没有其它表引用 `capp_routing_step.id`），主键变化不影响任何关联；单条路线工序通常 < 50 行，重插成本可忽略。
5. **工艺分工的落点**：确认「分工」应落在主档（谁维护这条路线）而不是工序（工序已有 `work_center` 表示在哪个车间/工作中心加工），故 V22 只加 `capp_routing.owner_id`，默认取创建人。

**结论与决策**
- 序号重建一律「读旧 → 删 → 按序重插」，不写原地 UPDATE 版本（可读性更好、无中间态风险）。
- 前端上移/下移在**本地**交换并顺带按 `(index+1)*10` 赋号，保存时走已有的整表替换，不新增后端排序接口。
- 工序行若未来被外部引用（如工步、检验项），需要改为「保留 id 的两阶段改号」或给唯一索引加 `DEFERRABLE`；当前不预留。

**遗留与后续动作**
- `capp_routing_step.id` 在主键变化下不可作为历史标识；P6-4 工艺卡片如果要把「卡片行」绑定到具体工序，应绑定 `(routing_id, seq_no)` 语义键而不是 step id，或届时改造为稳定 id。
- 工序级排序权重目前只有 `seq_no`；若将来需要「插入半步」（如 15），可直接沿用 10 步进并在重建时压缩。

## EXP-20261106-17 工艺卡片模板版本化与导出口径

**目标问题**：P6-4 工艺卡片的 DoD 有两条硬要求——「模板修改后历史卡片版式不串」「导出 PDF/Excel」。落地前要定：① 模板版本怎么存（能否照搬工艺路线的版本策略）；② 卡片怎么做到不被后续改版影响；③ 导出用什么技术、中文字体有无坑；④ 卡片行数据从哪来、精度怎么统一。

**范围与方法**：对比 `V21__capp_routing.sql` 的唯一索引与 `CappRoutingService.copy` 的取号方式；核对 `plm-platform/pom.xml` 的 POI 能力；实现 `V24__capp_card.sql` + `CappCardService` + `CappCardExcelService` 后跑 `CappSmokeTest#cardTemplateVersioningAndExport`（内嵌 PG + 真实 POI 读回）。

**关键发现**
1. **工艺路线的「版本」不能直接照搬**：`V21__capp_routing.sql` 的唯一键是 `(company_id, code)`，`CappRoutingService.copy` 复制时用 `nextCode` **另取新编码**（`RT-000002`），`version_no` 只是「同一零件的第几条路线」。模板要的是「同码多版本并存」，因此唯一键必须是 `(company_id, code, version_no)`（`V24__capp_card.sql:47`），发布只把同族其它 `RELEASED` 置 `ARCHIVED`，不覆盖旧行。
2. **卡片改「双快照」才能真正不串**：卡片落库时既记 `template_code/template_version`（追溯出自哪版），也把版式整份复制进 `capp_card.layout_json`（`V24__capp_card.sql:61`）；工序行同样快照到 `rows_json`（`V24__capp_card.sql:67`）。导出只读卡片自身（`CappCardExcelService`），完全不回查模板表——所以模板改版、甚至旧版本行被清理，都不影响历史卡片。
3. **jsonb 的 `?` 操作符与 JDBC 占位符同名冲突**：统计「非合计行数」时若写 `e ? '__summary__'` 或 `e->>?`，`?` 会被 JDBC 当成参数占位符，导致参数错位/语法错误。改用包含判断 `NOT (e @> '{"__summary__":"true"}'::jsonb)`（`CappCardService.java:295`），既避开了占位符，也走 GIN 友好的 jsonb 比较。
4. **PDF 不是必须现在就上**：`plm-platform/pom.xml` 已有 `poi-ooxml 5.2.5`（compile 作用域，`plm-app` 测试可直接用 `XSSFWorkbook` 读回），导出 xlsx 零新增依赖且中文无障碍（字体名设「宋体」+ 字符串单元格即可）。PDF 需引 openpdf/PDFBox 并嵌入中文字体，字体路径在本机与容器不一致，风险高于收益。
5. **行按列投影成字符串快照，精度统一**：`CappCardService.java:449` 的 `buildRows` 依模板列把工序投影为「列键 → 字符串」，数值统一 `setScale(2)`；末行追加 `__summary__` 合计行（`CappCardService.java:50`），导出时加粗（`CappCardExcelService.java:92`）。这样「页面预览」与「Excel 导出」看到的数字逐字节一致，不会出现页面 1 位小数、Excel 3 位小数。
6. **卡片行绑语义键而非 step id**：行快照按 `(routing_id, seq_no)` 语义生成（承接 EXP-20261106-16 的遗留），因为序号重建会物理删除并重插工序行，`capp_routing_step.id` 不稳定。

**结论与决策**
- 模板：同码多版本 + 「另存新版本」改版 + 发布归档同族旧版；只有 `RELEASED` 模板能生成卡片（草稿版式还在改，没有稳定基线）。
- 卡片：双快照；「重新生成」只刷新 `rows_json` 并补齐表头默认值，用户手填的表头值保留。
- 导出：本阶段只做 xlsx（DoD 的 Excel 一半），PDF 单列为 P6-4b；不引入 PDF 依赖。
- 行渲染与 Excel 渲染共用同一份 `rows_json` 与 `layout_json`，前端预览即导出效果，减少「导出后才发现版式错」的返工。

**遗留与后续动作**
- **PDF 导出未做**（DoD 的「PDF」尚未满足）：需评估 openpdf + 中文字体嵌入，或退化为「前端打印/浏览器另存 PDF」。
- 卡片单元格级手改未做：目前只能覆盖表头 `fieldValues`，明细行是路线投影的只读快照。
- 卡片无状态机（视为草稿态）：发布/签审待接 `meta_lifecycle`，届时照 P5-8 的 `ChgStateMachine` 模式。

## EXP-20261106-18 工时定额该不该落快照

**目标问题**：P6-6 工时定额要满足「工时汇总与工序工时一致，公式改动可重算」。落地前要定：① 定额结果要不要像工艺卡片那样落一份快照表；② 多套规则（通用/按工序类型/按工作中心）如何互相优先；③ 单件与批量两个口径怎么切。

**范围与方法**：对比 P6-4 卡片「必须冻结版式」的理由；梳理工艺定额通行算法（准备工时按批一次、单件工时随件数线性）；实现 `V25__capp_time_rule.sql` + `CappTimeService` 后跑 `CappSmokeTest#timeRuleMatchingAndCalc` 与真实 HTTP 联调。

**关键发现**
1. **定额不能落快照，方向和卡片恰好相反**：卡片是「文档」，版式必须冻结（EXP-20261106-17）；定额是「当前规则下的测算值」，一旦落表就出现「路线改了但定额还是旧值」的双份数据漂移。故 `GET /capp/time-calc` 只读实时算（`CappTimeService#calc`），DoD 的「公式改动可重算」天然成立，无需重算按钮。
2. **规则优先级要可解释**：三类规则并存（通用 / 按工序类型 / 按工作中心）。用「工作中心精确 +2、工序类型精确 +1」打分取最高，同分时 `priority` 小者优先（`score` / `match` 方法）。这样「工作中心+类型」规则必然压过单维度规则，而 `priority` 只用来解同档冲突，不需要用户理解复杂的匹配树。
3. **准备工时与单件工时必须分开返回**：准备工时按批一次、单件工时随件数线性，混成一个「总工时」会让前端无法正确乘批量。接口分别给 `totalSetupEffective`（准备合计）、`singlePieceMinutes`（单件合计，不含准备）、`batchMinutes`（= 准备合计 + 单件 × 批量），前端只展示不重算。
4. **校验顺序的坑**：写过 `factor(value)` 把 `<= 0` 兜底成 1 再用于校验，导致 `setupFactor=0` 被静默接受（`CappSmokeTest` 实跑报 `Status expected:<400> but was:<200>`）。正确做法是**校验入参原值**（`req.setupFactor() != null && signum() <= 0 → 400`），兜底只用于 null 缺省。
5. **未命中也必须是显式结果**：没有规则时按原值算并返回 `unmatchedSteps` 计数与 `ruleCode=null`，前端标「未命中（按原值）」。否则用户会误以为「试算没生效」而去找 bug。

**结论与决策**
- 定额只存规则、不存结果；改规则/改路线后重新查询即生效。
- 规则匹配用「精确度打分 + priority 解冲突」，不做正则/表达式求值（当前业务不需要，且可解释性更重要）。
- 接口一次返回三个口径 + 命中详情，前端零计算。
- 单件工时口径**不含**准备工时（工艺惯例），批量工时才含；这一条写进迁移注释与 DTO 注释，避免后续理解反。

**遗留与后续动作**
- 定额暂未反向写入工艺路线/卡片（试算结果不落库），若后续要「卡片上打印定额工时」，应让卡片生成时调用同一 `calc` 并把结果作为行快照的一列，而不是另建定额表。
- 规则暂无生效区间与版本（改了就影响所有历史试算）；若需要「按年度定额」需加 `effect_from/effect_to`。
- 批量默认值目前固定 1，规则里的 `batch_qty` 只作参考展示，未自动带入试算。

## EXP-20261106-19 卡片 PDF 导出的中文字体方案

**目标问题**：P6-4b 要补上 DoD 里的「导出 PDF」。PDF 生成库有 OpenPDF/PDFBox/iText7 三条路，而中文是这类导出的传统坑：不嵌字体在别的机器上就是一排方块或问号。要定：① 用哪个库；② 中文字体从哪来（打包内置 vs 系统探测 vs 配置）；③ 找不到字体时怎么办。

**范围与方法**：核对项目现有依赖（只有 `poi-ooxml`，无任何 PDF 库）；验证中央仓库能否解析 `openpdf`；实现 `CappCardPdfService` 后跑 `CappSmokeTest#cardTemplateVersioningAndExport` 的 PDF 分支与真实 HTTP 导出，检查字节流里是否有 `FontFile` 与 `%%EOF`。

**关键发现**
1. **OpenPDF 可用且 API 与老 iText 一致**：`com.github.librepdf:openpdf:1.3.39` 补齐后 `mvn compile` 直接通过，包名仍是 `com.lowagie.text`（`Document` / `PdfPTable` / `BaseFont`），无需学习新 API；对 JDK 17 无额外适配。
2. **中文字体必须 embed，且 `.ttc` 要带索引**：`BaseFont.createFont("C:/Windows/Fonts/simsun.ttc,0", BaseFont.IDENTITY_H, BaseFont.EMBEDDED)`——不带 `,0` 索引时 OpenPDF 无法从 TrueType Collection 里取字体。用 `IDENTITY_H` 才能走 Unicode 编码，中文不依赖 GBK 码表。
3. **字体来源不能硬编码**：开发机是 Windows（宋体/雅黑/黑体），容器多是 Linux（Noto CJK / 文泉驿 / AR PL），仓库又不适合放几十 MB 的字体二进制。最终采用「配置优先 + 系统探测 + 明确报错」三段式：`nexplm.capp.pdf.font-path`（可带 `,0` 索引）→ 8 个常见路径依次探测 → 都没有则返回 400 提示配置路径。
4. **绝不生成「看起来成功」的乱码 PDF**：字体缺失时若用默认 Helvetica 兜底，接口会返回 200 但内容全是方块，比报错更难排查。因此缺失字体一律 400 + 明确文案。
5. **PDF 与 xlsx 必须同源**：两者都只读卡片的快照（`layout_json` / `field_values` / `rows_json`），不各自回查模板/路线，否则「Excel 改了版式、PDF 还是老样子」这类分叉迟早出现。
6. **测试要能在无字体环境跑**：`CappSmokeTest` 的 PDF 分支用 `assumeTrue`——200 时校验 `%PDF` 头与长度，非 200 且消息含「中文字体」则跳过；这样本机（有宋体）真跑通、CI/容器（可能无字体）也不会假红。

**结论与决策**
- PDF 用 OpenPDF 1.3.39，不引 PDFBox（后者加载 CJK 字体与 CMap 更繁琐）。
- 字体走「配置 + 探测」，配置项 `nexplm.capp.pdf.font-path`；生产容器部署时须在镜像内装中文字体或挂载字体文件并配该变量。
- 页面用 A4 横向（工艺卡片列多），表头字段区与明细表分两块渲染（表头信息栏 + 明细表），视觉上与传统工艺卡一致。

**遗留与后续动作**
- 生产环境字体未纳入部署脚本：`deploy/` 需要补「安装 fonts-noto-cjk 或挂载 .ttf + 设置 NEXPLM_CAPP_PDF_FONT_PATH」的说明与 compose 变量（已在 `deploy/README.md` 第 6 条补上）。
- 表头字段区与明细表是两块独立表格，列不对齐（Excel 版是同表）；若业务要求严格对齐需要改成单表 + 合并单元格，工作量较大。
- 跨页表头重复已补：明细表 `setHeaderRows(1)`，工序多的卡片翻页后仍带列名（原实现漏设，第 2 页起是无列名数字）。

## EXP-20261106-20 工步该绑工序行 id 还是工序号

**目标问题**：P6-2 补齐「工步子表」时，工步必须指向所属工序。可选的关联键有两个：`capp_routing_step.id`（物理主键）与 `(routing_id, seq_no)`（语义键）。选错的代价是**每次序号重建后工步全部变孤儿**，且这种错误在功能测试里很容易漏掉（只测「新建-查询」不会暴露）。

**范围与方法**：回看 EXP-20261106-16 的结论（序号重建是「删表重插」，换号必然换 id）；实现 `V26__capp_substep.sql` + `CappRoutingService` 的写入/迁移逻辑，跑 `CappSmokeTest#substepsAndProcessTree` 实测「5/7 重建为 10/20」后工步是否仍在，并验证复制路线是否带工步。

**关键发现**
1. **必须绑语义键**：`capp_routing_step.id` 是 `IdWorker` 每次重插新生成，`resequence` / `replaceSteps` 都是「DELETE 后重插」，因此任何按 id 关联的子表在重建后必然悬空。工步改为 `(routing_id, step_seq_no, seq_no)` 三元唯一，工序号变了只需显式迁移，语义清晰。
2. **迁移不能靠 UPDATE 改号**：`uk_capp_substep_seq(routing_id, step_seq_no, seq_no)` 在「5→10、7→20」这类互换中会中途撞唯一键（与工序重建同一个坑）。做法一致：整表读出 → 清空 → 按新工序号重插。
3. **工步随工序整表替换提交**：`StepSaveReq` 增加 `substeps`，服务端在重写工序时先清空该路线的工步再按提交内容重建。好处是「改工序号/删工序」不会残留孤儿工步；代价是前端编辑工步必须与工序在同一次保存里提交（抽屉只改本地草稿，不单独请求后端）。
4. **过程树不建表、不缓存**：`process-tree` 直接复用 `detail` 的数据再聚合 `substepCount` / `substepMinutes`。多一份「树表」就多一处可能与工序表不一致的数据；而树的规模（几十道工序）完全不需要缓存。
5. **工时对得上是隐性需求**：工步拆分的意义是「把工序工时落到动作上」，所以树节点额外给 `substepMinutes`（工步工时之和），让用户能一眼看出工步工时与工序工时是否吻合（差额往往是漏填工步）。

**结论与决策**
- 工步绑 `(routing_id, step_seq_no, seq_no)`，所有可能改工序号的操作（`replaceSteps` / `resequence` / `copy`）都必须显式迁移或复制工步。
- 工步不单独暴露 CRUD 接口（随路线整表替换），避免「工序删了但工步还在」的中途态。
- 过程树是只读派生视图，不落库。

**遗留与后续动作**
- 工步与工序工时暂无一致性校验（不阻断保存，只在树上显示差额）；是否要「工步工时之和 ≠ 工序工时」时告警需业务确认。
- 卡片（P6-4）暂未支持「按工步展开行」，如需工步级工艺卡，应在 `CappCardService.buildRows` 里按 substep 展开而不是给卡片加新列。
- 工步默认自带 `resource_id`（可覆盖工序级），但卡片列目前只取工序级资源名称；工步级资源尚未进入卡片渲染。

## EXP-20261106-21 成册要不要给卡片挂「册号」，齐套哪些项该算失败

**目标问题**：P6-5 有两个容易想当然的点：① 成册与卡片的关系能不能简化成「卡片有个册号字段」；② 齐套性检查里哪些缺失应该拦住用户（FAIL），哪些只是提醒（WARN）。两者都直接影响数据模型与用户信任度——一次误判 FAIL 会让「检查」变成狼来了。

**范围与方法**：对照 P6-4 卡片模型的字段设计；梳理工艺实务中「一个零件的工艺包」构成（路线 → 工序 → 工步 + 卡片 + 工时）；实现 `V27__capp_card_volume.sql` + `CappVolumeService` 后跑 `CappSmokeTest#volumeAndCompleteness` 与真实 HTTP 联调（建册、页序、跨零件、成册 PDF）。

**关键发现**
1. **不能给卡片挂册号**：同一张工序卡在实务中会被不同册引用（「机加工分册」与「总装分册」都含同一张卡）。单值册号会把关系写死，且无法表达页序。正确建模是 `capp_card_volume_item(volume_id, card_id, seq_no)` 的多对多。
2. **页序必须是册内属性**：同一张卡在不同册里页序不同，所以 `seq_no` 只能放条目表，且要 `uk(volume_id, seq_no)`（防两页同号）与 `uk(volume_id, card_id)`（防同册重复）。
3. **跨零件混装必须拦在保存时**：成册是「一个零件的工艺包」，混进别的零件，打印出来零件信息与卡片对不上，属于最难自查的错误。保存时校验 `card.object_id == volume.object_id`，直接 400。
4. **齐套的 FAIL 要极窄**：只有「没有工艺路线」「路线里没有工序」代表工艺根本不存在，才 FAIL；「路线未发布」「工时为 0」「资源未绑」「没拆工步」「没生成卡片」都只是「工艺还没写完」，一律 WARN。否则用户天天看到红叉会直接无视这个功能。
5. **空册不能发布**：发布意味着「装订确定」，空册发布后再改就违背语义；`release` 前校验 `cards` 非空。
6. **成册 PDF 复用单卡渲染**：把单卡渲染抽成 `renderCard(document, card, font)`，单卡导出与成册导出共用；成册只多一层「封页 + 目录 + 每张卡 newPage()」。不引 PDF 合并库，避免多一个依赖与多一次字节拷贝。
7. **页码不做**：目录页码需要两遍渲染（先排版拿页数再回填），成本高而工艺卡的目录实际很少看页码；用「页序 10/20/30」替代，与册内 `seq_no` 一一对应。

**结论与决策**
- 成册用 `volume + item` 多对多，页序属条目；卡片不感知册。
- 齐套 FAIL 仅限「无路线 / 无工序」，其余 WARN；`ready = failCount == 0`。
- 成册 PDF 复用单卡渲染函数，不引入 PDF 合并依赖。
- `GET /capp/cards` 增加 `objectId` 过滤，供成册选择卡片时复用分页接口。

**遗留与后续动作**
- 成册暂无「封面模板」与「页码/骑缝章」等排版要素，前者需要类似卡片模板的版式配置。
- 齐套检查没有「一键补卡」动作（如按缺失的已发布路线批量生成卡片）；如需要应在 P6 收尾时补一个批量生成入口。
- 册状态只有 DRAFT/RELEASED，无签审；若要纳入变更流程，应接 `meta_lifecycle`（与卡片状态机一并设计）。
- P6 剩余：质量规划（P6-8）与 ERP 下发接口（P6-9）未开始。

## EXP-20261106-22 控制计划该引用字典还是内联特性；下发预留做到哪一步算够

**目标问题**：P6-8/P6-9 两个「边界题」。质量规划：控制计划的「受控特性」应该全部来自检验项字典（强引用），还是允许行内自由填写？下发：计划写的是「与 ERP 的工艺下发接口**预留**（P9 实现）」，那本阶段到底要做到哪一步才算合格——不做到位后面接 ERP 要推倒重来，做过头又是在没有 ERP 契约的情况下瞎猜。

**范围与方法**：对照计划 P6 第 8/9 条与 DoD；梳理质量实务中控制计划的填法（一行 = 工序 + 特性 + 规格 + 测量 + 抽样 + 控制方法 + 反应计划）；实现 `V28__capp_quality.sql`、`V29__capp_erp_dispatch.sql` 与对应服务后，跑 `CappSmokeTest#qualityPlanAndErpDispatch` 与真实 HTTP 联调。

**关键发现**
1. **强引用字典会让填表变成维护字典**：真实控制计划里大量特性是一次性的（某工序某个尺寸），强制先建字典再引用，用户会绕过系统用 Excel。因此 `item_id` 设计为**可选**，选中时只带出 `spec/method/gauge` 默认值，行上的值才是权威。
2. **字典改动不得篡改历史计划**：如果行只存 `item_id`、展示时联查字典，那么字典改了规格，已发布计划的历史记录就跟着变——质量记录不允许这种「追溯性变化」。行内联值是唯一符合审计要求的做法。
3. **行要绑工序号并快照工序名**：绑 `step_seq_no` 与工步一致（序号重建不脱离）；再存一份 `step_name` 快照，工序改名后历史计划仍显示当时的工序名，与「版式快照」同一思路。
4. **骨架行能省掉最痛的一步**：控制计划通常 10~40 行且与工序一一对应，如果只能新建空表再手填行号，几乎必然出错。`rows` 为空时按路线工序自动生成骨架（一工序一行），用户只需填特性。
5. **下发预留的「够」是三条**：① 载荷契约（要下发什么）② 快照落库（当初发了什么）③ 取数与回执入口（P9 怎么接）。缺任何一条后面都要改表；而 ERP 侧的字段映射、认证、幂等、重试全部属于 P9，本阶段做就是猜。
6. **载荷必须固化而不是实时拼装**：下发是「某一时刻的口径」，路线后面改了甚至归档了，必须还能回答「当初发了什么」。因此 `payload_json` 落 jsonb + `payload_sha` 便于 ERP 侧做幂等；测试用「两次读取 `generatedAt` 不变」证明读的是快照。
7. **只允许下发已发布路线**：草稿还在改，下发出去的工艺会被产线当权威执行，属于不可挽回的错误。

**结论与决策**
- 控制计划行内联特性值，字典只做默认值来源；发布前强制每行都有受控特性。
- 下发只做「载荷 + 快照 + 取数/回执」，明确不实现真实 ERP 契约（P9）。
- 下发状态位预留 PENDING/SENT/FAILED/VOID，P9 适配器接上后无需改表结构。

**遗留与后续动作**
- P9 必须补：ERP 字段映射表、认证方式、幂等键（可直接用 `payload_sha`）、失败重试与回执对账、下发范围与「变更后是否重新下发」的策略。
- 控制计划暂无版本化（发布后不可改，改需新建一份）；若需要「一零件多版本控制计划并存」，参考卡片模板的同码多版本方案。
- 控制计划与卡片/成册尚未联动（成册里不含控制计划）；若客户要求「工艺包 = 卡片 + 控制计划」，应在成册条目里增加 `item_type` 区分。
- P6 九项至此全部完成；下一步是整体回归与演示准备。

**范围与方法**：读 `docs/02-数据模型设计.md:247` 的旧系统 `prj_task_output(task_id, object_id, output_type, required)` 定义；核对本系统三类对象的实际落地表（`V1__baseline.sql` 的 `plm_object` 通用基表 `object_type='PdmDoc'/'PdmItem'`；`V24__capp_card.sql:52` 的 `capp_card` 独立表，且有 `object_id` 指向零件）；核对 `V2__seed.sql:68` 的 DEFAULT_LIFECYCLE 状态码；实现 `V34__project_deliverable.sql` + `ProjectDeliverableService` 后跑 `ProjectDeliverableSmokeTest` 与真实 HTTP 联调。

**关键发现**
1. **三类对象不在同一张表**：文档/零部件是 `plm_object` 的不同 `object_type` 行，工艺卡片在 `capp_card`（本身没有 `lifecycle_state`，只有模板有 `status`）。要「一个任务挂任意类型」，只能用 `object_type + object_id` 多态，无法建单一外键。
2. **不能存 code/name 快照**：本系统对象改名是常态（同一 master 多 revision），快照会让「交付物列表」与「对象详情」长期不一致。代价是缺件时回查不到——因此 `resolveObjects` 刻意**不过滤 deleted**，软删的行仍返回编码/名称，否则缺件提示只能显示雪花 ID，等于没提示。
3. **生命周期状态是驼峰**：`Draft`/`InWorkflow`/`Released`/`Obsolete`（`V2__seed.sql:68` 的 DEFAULT_LIFECYCLE），不是全大写；判定必须写 `Released`/`Obsolete`，用 `RELEASED` 会把所有对象误判为未发布。
4. **旧系统只有 `required` 一个开关**，没有「输入是否必需」的概念；本系统输入项只用于追溯上游来源，不参与齐套——否则「上游还没交」会被算成本任务缺件。
5. **缺件计数按交付物行而非对象去重**：联调实测同一物料挂到两个任务后软删，看板 `missingTotal = 2`。这是对的——「谁少了东西」必须按任务算。

**结论与决策**
- 交付物 = `prj_task_output(company_id, task_id, output_type INPUT/OUTPUT, object_type DOC/ITEM/CAPP_CARD, object_id, required, remark)`，唯一键 `(task_id, output_type, object_type, object_id)`（同对象可同时是输入与输出），软删。
- 齐套口径 FAIL 极窄：`MISSING`（对象已删/不存在）与 `OBSOLETE`（`lifecycle_state=Obsolete`）算缺件；`UNRELEASED`（存在但未发布）只提醒；工艺卡片无生命周期，存在即 `OK`。
- 项目 `ready = missingTotal == 0`；任务 `ready = missingCount == 0`；无交付物的任务视为齐套（「没要求」≠「不齐套」）。
- 提交审核加齐套守卫：`submit` 前校验必需 OUTPUT，有缺件抛 `PRJ.DELIVERABLE.INCOMPLETE`(409)；未声明任何必需交付物直接放行，避免拦住 P7-3 已上线的任务。
- 不新增权限点，沿用 `prj.project.read/write`。

**遗留与后续动作**
- 交付物不参与项目进度汇总（进度仍按叶子任务加权）；若要「按交付物计权重」，需改 `ProjectTaskService#recalcProgress`。
- 无批量挂接，也不能按项目模板预置交付物清单——等 P7-6 项目模板立项时一起做（模板里定义每类任务的输出物）。
- 输入项没有「来源任务」关系（只依赖对象，不知道谁该产出它）；P7-8 门户若要「上游未交预警」，需补 `source_task_id` 或按对象反查任务。
