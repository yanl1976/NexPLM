# 六、系统探查记录（EXP）

> **用途**：把每次对 NexPLM（新系统）以及 PLMSOFT（旧系统蓝本）的 **代码 / 数据 / 环境** 探查集中沉淀，复盘时能还原"当时看到了什么、为什么这样决策"。
>
> **记录约定**
> 1. 每次探查结束**立即追加**一条，编号 `EXP-YYYYMMDD-NN`（同日递增），旧条目只增不删。
> 2. 结论被后续事实推翻时：新开一条说明新证据，并在旧条目「状态」列标注 `已被 EXP-xxx 推翻`。
> 3. 每条固定五段：**目标问题 → 范围与方法 → 关键发现（带 `路径:行号` 证据）→ 结论与决策 → 遗留与后续动作**。
> 4. 只写事实与证据；推测必须标「待验证」，不得混入结论。
> 5. 影响阶段交付的结论，同时回填 `03-分阶段实施计划.md` 的「已验证事实」。
> 6. 临时验证脚本用完即删（结论留在本文件，不靠脚本留存证据）。
>
> **与其它文档的分工**：本文件记「怎么查到的」（过程与证据）；`03-分阶段实施计划.md` 的「已验证事实」记「验证通过什么」；`00-现状分析报告.md` 记旧系统本身的静态结论。三者不互相抄写，只交叉引用。

## EXP-20261106-01 前端 BOM 界面与批量/序号入口勘察

**目标问题**：前端是否已有「批量改用量」「批量替换子件」「调整 BOM 序号」的入口？若没有，工具栏与表格的插入点在哪？

**范围与方法**：`frontend/src` 全量检索（`batch` / `update-qty` / `batch/replace` / `draggable` / `contextmenu` / `selection-change`），并逐个读取 `views/item/*`、`api/item.ts`、`router/index.ts`。

**关键发现**
1. BOM 界面全部集中在 `frontend/src/views/item/ItemDetailView.vue`，无独立 BOM 组件；BOM 是 `el-tabs` 的第一个页签（`ItemDetailView.vue:45`），树表用 `row-key="lineId"` + `:tree-props="{ children: 'children' }"` + `default-expand-all`。
2. `bomApi.move` 已在 `frontend/src/api/item.ts` 封装，但**全前端无调用点**；仓库无 `vuedraggable` / `sortablejs` / 任何 `@contextmenu` 右键菜单，故"拖拽调序号"实际未实现。
3. 「批量改用量」「批量替换」前端 0 命中：`/bom/batch/update-qty`、`/bom/batch/replace` 仅存在于后端 `BomController.java:99`、`:108` 与 `ItemSmokeTest`。
4. BOM 表无 `type="selection"` 列、无 `@selection-change`，即当时不具备多选能力。
5. 工具栏唯一定义处：`ItemDetailView.vue:46-66`；表格列定义 `:81-114`；行内操作（编辑/备选件/删除）`ItemDetailView.vue:104-110`。
6. 导入/导出、基线、替代件、BOM 展开/汇总均已在前端落地（同文件多 tab + 多弹窗），非缺口。

**结论与决策**
- 批量按钮插入工具栏（`ItemDetailView.vue:61` 之后），多选列加在表格首列，行操作追加「上移/下移」。
- 序号调整**不引入拖拽库**（离线环境装包成本 + 交互复杂度），改为按钮复用已封装的 `move` 接口，持久化语义一致。
- 批量结果统一用一个弹窗展示「成功/跳过计数 + 逐行原因」，原因文本做 HTML 转义后再 `dangerouslyUseHTMLString` 渲染。

**遗留与后续动作**
- 已全部落地并在 `03-分阶段实施计划.md` 的 P3 条目中登记；新的集成用例见 `ItemSmokeTest#bomBatchUpdateQtyAndReplace`、`#bomMoveReorderAndDuplicateGuard`。
- 若后续确实要拖拽交互，只需在现有 `onMoveBom` 之上接一层拖拽事件，无需改后端。

## EXP-20261106-02 后端 BOM 代码清单与缓存现状

**目标问题**：BOM 能力散落在哪些后端文件？是否已有缓存可复用/需要失效？

**范围与方法**：`backend/plm-platform/src/main/java/com/nexplm/platform/item/` 目录遍历 + 全仓库检索 `caffeine|redis|@EnableCaching|spring-boot-starter-cache`。

**关键发现**
1. 入口：`api/BomController.java`（tree / add / update / remove / move / batch-update-qty / batch-replace / validate / summary / rollup / export / import-preview / import / where-used）、`api/BomBaselineController.java`、`api/BomAlternateController.java`、`api/BomDtos.java`。
2. 服务：`service/BomService.java`（31.5 KB，核心）、`BomExcelService.java`、`BomBaselineService.java`、`BomAlternateService.java`、`BomViews.java`（视图口径唯一来源：DESIGN / PROCESS / MANUFACTURE）。
3. 持久化：`mapper/BomLineMapper.java` 仅 `extends BaseMapper`，**无 MyBatis XML**；展开/汇总直接用 `JdbcTemplate` 手写递归 CTE。
4. **BOM 全链路无缓存**：pom 无 caffeine/redis 依赖，无 `@EnableCaching`，`BomService` 内无缓存字段。项目内仅两处内存缓存且与 BOM 无关：`metadata/service/MetaService.java:71`、`lifecycle/service/LifecycleService.java:50`（均为 `ConcurrentHashMap`）。
5. 树展开是**逐层查询**（`BomService.childrenOf`，`ORDER BY b.line_no, b.id`），即 N+1：每层每个父件一次 SQL。

**结论与决策**
- 性能优化先量后改：不预先加缓存，先压测（见 EXP-20261106-06）。实测 10,520 行树展开 351ms，落在 2s 预算内，故**暂不引入结构缓存**，避免过早引入一致性负担（BOM 行任意写操作都要失效缓存）。
- 若未来单树规模上到 5 万行，优先把 `childrenOf` 的逐层查询改成"整树一次递归 CTE + 内存组装"，再考虑缓存。

**遗留与后续动作**
- 缓存失效策略（写操作 → 按 rootId 失效）留到确有必要时再设计，无 TODO 阻塞。

## EXP-20261106-03 `bom_line` 表结构与序号唯一性

**目标问题**：用「两次 `move` 互换 `line_no`」实现上移/下移，是否会撞唯一索引？

**范围与方法**：读 `backend/plm-app/src/main/resources/db/migration/V11__item.sql` 建表段。

**关键发现**
1. 建表：`V11__item.sql:77-95`，`line_no int NOT NULL DEFAULT 10`，`version` 乐观锁字段。
2. 唯一索引只有 `uk_bom_line (parent_object_id, view_type, child_object_id)`（`V11__item.sql:95`），**不包含 `line_no`**。
3. `BomService.move` 只传 `newLineNo`（`newParentId` 为 null）时不会触发换父校验，直接更新 `line_no` 与 `version`。

**结论与决策**
- 两次 `move` 互换 `line_no` 安全：中间态两行同 `line_no` 不违反约束，排序由 `ORDER BY line_no, id` 保证稳定。
- 前端 `onMoveBom` 依此实现，成功后重新 `loadBom` 而不是本地改数组，避免与服务端排序口径漂移。

**遗留与后续动作**
- 无。若将来给 `line_no` 加唯一索引，必须改成一侧先置临时值的三步交换。

## EXP-20261106-04 批量接口契约与校验语义

**目标问题**：批量改用量/批量替换的真实请求字段、校验分支与返回结构，前端如何对齐？

**范围与方法**：读 `api/BomDtos.java:146-163` 与 `service/BomService.java:355-468`。

**关键发现**
1. `BomBatchQtyReq(lineIds @NotNull, qty, lossRate, unit)`；`BomBatchReplaceReq(fromChildId @NotNull, toChildId @NotNull, viewType, parentIds)`；两者返回 `BomBatchResult(total, updated, skipped, messages)`（`BomDtos.java:146-163`）。
2. 改用量（`BomService.java:355-393`）：`qty/lossRate/unit` **三者全空 → 400**；`qty <= 0 → 400`；SQL 用 `COALESCE(?, 列)` 只覆盖非空字段；每行先判 `inSubtree(rootId, line.parentObjectId, view)`，不属于该树的行 **不修改**，`skipped++` 且写入 `messages`「BOM 行不属于该零部件的结构」；行不存在同样跳过。
3. 批量替换（`BomService.java:400-468`）：`fromChildId == toChildId → 400`；按 `child_object_id + view_type` 拉候选行，逐行判越权、已存在重复（文案「目标父件下已存在该子件」，前端断言用「已存在」）、`ensureNoCycle` 成环，命中即 `skipped++`。
4. 因此"跳过"不是异常，而是**批量语义的一部分**：部分成功必须回显原因，前端不能只看 HTTP 200。

**结论与决策**
- 前端弹窗只提交被勾选的字段（`null` 表示不改），并把 `updated/skipped/messages` 原样呈现，避免"看起来成功其实全跳过"。
- 测试断言与文案对齐：重复原因断言用「已存在」子串，越权断言用 `updated=0 / skipped=N`。

**遗留与后续动作**
- 已知局限：批量改用量不支持按百分比调整、不支持按父件过滤（`parentIds` 只在替换侧提供）。若业务需要，扩展 DTO 而非新增接口。

## EXP-20261106-06 性能压测造数可行性

**目标问题**：要验证「10,000 行 BOM 展开 < 2s」，能否绕过接口直接造数？需要哪些必填列？

**范围与方法**：读 `db/migration/V1__baseline.sql:321-354`（`plm_object`）与 `V11__item.sql:10-23`（`item_master`）。

**关键发现**
1. `plm_object` 必填列：`object_type, master_id, code, name, company_id, lifecycle_state`；其余有默认值（`ext_json` 默认 `{}`、`is_latest` 默认 true 等），且**无外键**，可任意指定 id 段。
2. `item_master` 必填：`object_id, item_type`（`unit` 默认 `EA`）。
3. `bom_line` 无外键约束，`parent_object_id`/`child_object_id` 直接存 `plm_object.id`。
4. 遂可 `INSERT ... SELECT FROM generate_series(...)` 在库内一次生成上万个节点与行。

**结论与决策**
- 压测走 SQL 造数 + MockMvc 真实接口计时（含 JSON 序列化），避免上万次 HTTP 调用把被测耗时淹没。
- 结构取 4 层「总成 → 20 部件 → 各 25 子部件 → 各 20 零件」= 10,521 节点 / 10,520 行。
- 实测（`BomPerformanceTest`）：树展开 351ms、BOM 展开 375ms、汇总 `leafOnly=true` 202ms；汇总返回 10,000 行、首行 `totalQty=1`，证明叶子口径未漏算。

**遗留与后续动作**
- 该用例固定跑在内嵌 PG 上，CI 耗时可接受（约 18s）。未覆盖"并发 200 请求"场景，压测细化留到 P10。

## EXP-20261106-07 本机测试与构建命令坑

**目标问题**：在 Windows + PowerShell 环境下，NexPLM 后端测试/前端构建的可靠命令是什么？

**范围与方法**：反复试跑 `mvn` 各参数组合与 `npm run build`，记录失败形态。

**关键发现**
1. `mvn -o -pl plm-app -Dtest=… test` → `Could not find artifact com.nexplm:plm-common`：单模块运行不会先构建兄弟模块，**必须加 `-am`** 走反应堆。
2. `mvn -o -DskipTests install` → `maven-install-plugin:3.1.3` 未缓存且离线，失败；因此不能用 install 预装兄弟模块。
3. 用 `-Dtest=类名#方法` 指定用例时，其它模块无匹配用例会让 surefire 报 `No tests matching pattern … were executed!`，需 `-Dsurefire.failIfNoSpecifiedTests=false`。
4. PowerShell 下该参数**必须加引号**（`"-Dsurefire.failIfNoSpecifiedTests=false"`），否则被拆成 `-Dsurefire` + `.failIfNoSpecifiedTests=false`，报 `Unknown lifecycle phase ".failIfNoSpecifiedTests=false"`。
5. 前端校验命令为 `npm run build`（= `vue-tsc --noEmit && vite build`），项目**未配 ESLint**，故"构建通过"即类型检查通过。

**结论与决策**
- 后端测试标准命令（可复用于文档与 CI）：
  ```powershell
  cd NexPLM/backend
  mvn -o -pl plm-app -am "-Dtest=ItemSmokeTest" "-Dsurefire.failIfNoSpecifiedTests=false" test
  ```
- 全量：`mvn -o -pl plm-app -am test`（当前 29 个用例：12 单测 + 17 集成）。

**遗留与后续动作**
- 无。CI 若在 Linux 下运行可去掉引号，但保留 `-am` 与 `-Dsurefire.failIfNoSpecifiedTests=false` 更稳。

## EXP-20261106-08 Flowable 版本选型与集成实测

**目标问题**：P4 要集成工作流引擎，选哪个 Flowable 版本能在 Spring Boot 3.3.5 / Java 17 上跑通？表结构与流程定义如何与现有 Flyway、classpath 结构共存？

**范围与方法**：读根 `pom.xml` 版本属性；`Invoke-WebRequest` 取 `flowable-spring-boot-starter-process` 的 `maven-metadata.xml` 与 7.1.0 的 pom；`mvn -pl plm-platform -am -DskipTests compile`（联网）验证解析；随后写测试实跑，观察引擎日志。

**关键发现**

## EXP-20261106-09 加签动态加实例与委托模型

**目标问题**：① 会签进行中如何给节点动态追加审批人？② 「委托他人办理」该改任务 assignee 还是只在业务层放行？

**范围与方法**：运行时会签实例的 `act_ru_execution` 快照；下载 `flowable-engine-7.1.0-sources.jar` 阅读 `AddMultiInstanceExecutionCmd` 源码；核对 `sys_user / sys_user_role / sys_user_group / sys_user_org / sys_group_role` 关系表。

**关键发现**
1. 会签运行时的执行树（实测 `act_ru_execution`）：
   ```
   流程实例执行   act_id_=null       is_scope_=t  is_active_=t   (id = processInstanceId)
     └ 多实例根   act_id_=countersign is_mi_root_=t is_active_=f
         ├ 实例子执行 …             is_mi_root_=f is_active_=t  ← task.executionId 指向这里
         └ 实例子执行 …
   ```
2. `AddMultiInstanceExecutionCmd` 的 `searchForMultiInstanceActivity(activityId, parentExecutionId, …)` 是**从传入执行的子执行里递归**找 `isMultiInstanceRoot` 的执行。因此：
   - 传 `task.getExecutionId()`（实例子执行）→ 其子执行无 miRoot → 报 `No multi instance execution found for activity id countersign`；
   - 传多实例根自身 → 同样找不到（引擎只看子执行）；
   - **必须传多实例根的父执行**（本例即流程实例执行）。
3. 该方法对并行多实例会把根执行 `setActive(true)/setScope(false)`，随后 `planContinueMultiInstanceOperation` 新实例；`nrOfInstances` 自增，故「全票」完成条件仍成立。
4. 用户与组织/组/角色都是**多对多**：`sys_user_org`、`sys_user_group`、`sys_user_role`、`sys_group_role`；`sys_user` 表**没有 org_id 列**，按组织解析执行人必须走 `sys_user_org`，且组织含子树要用 `sys_org.path` 前缀。
5. `TaskQuery` 支持 `or() … endOr()` 组合多个 `taskAssignee`，可用于「本人 + 委托给我的人」合并待办。

**结论与决策**
- 加签：`multiInstanceRootParent(task)` 沿 `act_ru_execution.parent_id_` 上溯到 `is_mi_root_=true` 的执行，返回其父执行 id；这样也兼容子流程内嵌套会签。
- 委托**不改任务 assignee**，只在两处放行：① 待办查询合并「生效委托给我的 owner」的任务；② 办理/驳回/加签的归属校验允许受托人操作，并在意见里加「[代 XXX 办理]」标记。好处是委托到期或撤销后立即恢复原状，无需回写引擎数据。

**遗留与后续动作**
- 委托按 `processKey` 限定已在解析时校验；按对象类型/组织限定未做。
- 超时催办需打开 `flowable.async-executor-activate` 并配定时器，属 P4 后续项。

## EXP-20261106-10 已办与当前活动节点的查询口径

**目标问题**：「我的已办」「我发起的流程」分别该查引擎历史表还是业务表？当前活动节点怎么取？

**范围与方法**：核对 Flowable 7.1 的历史表（`act_hi_taskinst`）与运行时任务表（`act_ru_task`）列名，实跑 `HistoryService` 查询验证。

**关键发现**
1. 已办用 `historyService.createHistoricTaskInstanceQuery().taskAssignee(userId).finished()`，排序 `orderByHistoricTaskInstanceEndTime().desc()`；`HistoricTaskInstance` 提供 `getDurationInMillis()` 与 `getDeleteReason()`（驳回/撤回后为删除原因），无需自己算耗时。
2. 当前活动节点一次批量 SQL 取：`SELECT proc_inst_id_, name_ FROM act_ru_task WHERE proc_inst_id_ IN (…) ORDER BY create_time_`；`act_ru_task` 的进程实例列是 `proc_inst_id_`、名称列是 `name_`（注意带下划线后缀，与业务表命名不同）。

**结论与决策**

## EXP-20261106-11 插件/签名/巡检/催办的四项实现口径

**目标问题**：① 流程完成后如何安全驱动业务副作用？② 电子签名怎样才「可核验」？③ 巡检与催办如何做成可反复执行的幂等操作？

**范围与方法**：读 `LifecycleService.transition`（自有 `@Transactional`）；核对 `doc_master.main_file_id` 与 `file_object.sha256`；对照 Flowable 运行时/历史表列名；实跑测试验证。

**关键发现**
1. **插件不能直接在主流程事务里跑**：`LifecycleService.transition` 自身带 `@Transactional`，它抛异常会穿过其代理边界把当前事务标记 rollback-only，导致流程提交失败。改为「事务内注册 `afterCommit` 回调 → 每个插件用 `REQUIRES_NEW` 独立事务执行，异常只 warn」，主流程提交成功后才执行业务副作用。
2. **签名摘要链路**：`doc_master.main_file_id → file_object.sha256`（`file_object` 上有 `uk_file_object_sha` 唯一索引，同一内容只存一份）。非文档对象在 `doc_master` 无行，摘要留空、核验结果为 `UNKNOWN`，而不是报错。
3. **巡检判定口径**：「引擎是否还有实例」看 `act_ru_execution.proc_inst_id_` 是否存在；「终态是完成还是终止」看 `ACT_HI_PROCINST.delete_reason_`（有删除原因=TERMINATED，无=COMPLETED）。
4. **催办幂等**：同一 `task_id` 在窗口内已有 `REMIND` 即跳过；时间窗用 PG 的 `make_interval(hours => ?)`，避免字符串拼 `interval` 的类型问题。
5. **踩坑（NPE→500）**：空签名列表时 `currentFileShas` 返回 `Map.of()`，随后 `currentShas.get(row.fileId())` 中 `fileId` 为 null；`Map.of()` 的 `get(null)` **抛 NPE**（HashMap 则返回 null）。修复为返回 `HashMap` 并对 `fileId == null` 单独判断。

**结论与决策**
- 业务插件定位为「尽力而为的副作用」：不阻断流程、独立事务、失败留日志；需要强一致的业务动作必须显式设计为重试任务。
- 电子签名只存「签名时刻的摘要」，核验结果查询时实时计算，不把易过期状态落库。
- 巡检 `fix=true` 只自动修正可判定的漂移（孤儿 link 置终态），生命周期类问题只报告，避免自动改错业务状态。
- 催办做成可被外部调度反复调用的幂等接口，而非内置定时器（暂不启用 Flowable async executor）。

**遗留与后续动作**
- `SendNotification` 插件待 P8 通知模块（消费 `wf_comment` 的 `REMIND`/`APPROVE`）；`ErpPublish` 待 P6；bpmn-js 设计器与前端工作流页面未做。

## EXP-20261106-13 变更申请接入工作流的接口边界与回写口径

**目标问题**：P5 要让「ECR 提交 → 发起审批 → 归档/撤回回写申请状态」，落地前必须确认：① 现有 `WorkflowService.start` 对业务对象有哪些硬校验；② 不在 `plm_object` 表里的业务对象（ECR）在待办/已办/实例列表里能否显示编码与名称；③ 插件回写与实际状态可见性之间的时序。

**范围与方法**：只读通读 `WorkflowService.java`（发起、待办、已办、实例、绑定选路、签名）、`WfPluginRegistry.java`、`LifecycleAdvancePlugin.java`、`V15__workflow.sql`、`V18__change.sql`；对照 `WorkflowSmokeTest` 既有断言；实跑 `ChangeSmokeTest` 验证（内嵌 PG + Flowable）。

**关键发现**
1. **发起流程强制要求对象在 `plm_object`**：原 `WorkflowService.start` 第一行 `requireObject(req.objectId())`，SQL 为 `SELECT COUNT(1) FROM plm_object WHERE id = ? AND deleted = false`。变更申请存于 `chg_ecr`（`V18__change.sql:17-40`），不在 `plm_object`，直接发起必然 404 `OBJ.NOT_FOUND`。
2. **`wf_instance_link` 对 `object_id` 无外键**：`V15__workflow.sql:35-50` 只有 `object_type varchar(64)` + `object_id bigint` 与索引，故「关联非 plm_object 对象」在存储层本就合法，缺的只是服务层判定。
3. **编码/名称依赖 `LEFT JOIN plm_object`**：待办/已办/实例的 `code`、`name` 全部来自 `o.code`/`o.name`（原 `WorkflowService.java:363/442/476/750` 附近的实例、我发起、对象实例、loadLinks 四处）。非 plm_object 对象即使能发起，列表上的对象列也会是空。
4. **条件绑定上下文同样只读 `plm_object`**：`bindingContext` 只 SELECT `plm_object` 快照 + `ext_json`，ECR 拿到的上下文为空 Map（`{}` 条件仍能命中，但无法按状态/类型分流）。
5. **`LifecycleAdvancePlugin` 只按 id 取生命周期**（原 `:76-78` `SELECT lifecycle_state FROM plm_object WHERE id = ?`），不带 `object_type`。ECR 与 plm_object 都是雪花 id，碰撞概率极低但不为零，属可消除的风险面。
6. **插件的 afterCommit 时序决定了响应体口径**：`WfPluginRegistry.java:39-50` 在事务内注册 `afterCommit`，故 `ChgService.submit` 返回的 `detail()`（事务内取）仍是 `SUBMITTED`，插件跑完后再 GET 才是 `REVIEWING`。前端因此必须在提交后重拉详情，否则状态与流程实例不同屏。
7. **测试坑：全局 `non_null` 序列化**：`plm-app/src/main/resources/application.yml:28` 配了 `default-property-inclusion: non_null`，空字段被**省略**而非输出 null；`JsonNode.path("approvedAt").isNull()` 对「字段不存在」返回 false，撤回用例因此误报失败，必须改查库（`SELECT COUNT(1) ... approved_at IS NOT NULL`）。
8. **既有 `ecnProblemAndExecutionFlow` 用例曾用 `UPDATE chg_ecr SET status='APPROVED'` 绕过审批**（原注释「审批流尚未与变更打通」）。打通后已改为真实走「提交 → 初审 → 会签 → APPROVED」，顺带覆盖了集成链路。

**结论与决策**
- 不为 ECR 造 `plm_object` 影子行（会造成双写与状态二义），改为**按类型兜底**：`requireObject(objectType, objectId)` 对 `ChgEcr` 查 `chg_ecr`；四处展示 SQL 改为 `COALESCE(o.code, ce.code)`/`COALESCE(o.name, ce.title)`，join 条件用 `AND l.object_type <> 'ChgEcr'` 与 `= 'ChgEcr'` 互斥，避免同一 id 两个来源都命中。
- `bindingContext` 补 `ChgEcr` 的 `objectType/code/name/changeType/priority/status`，使 `condition_json` 可按 ECR 状态或变更类型选不同流程（当前只注册一条 `{}` 兜底）。
- 流程与业务状态的分工定死：**`ChgService` 只负责「提交」这一业务动作**（`DRAFT→SUBMITTED` 并发起流程），**`ChgWorkflowPlugin` 只负责流程事件回写**（`→REVIEWING` / `→APPROVED` / `→DRAFT`），回写只接受 `SUBMITTED/REVIEWING` 两个在途状态，已批准或已关闭的单据不被迟到事件回退。

## EXP-20261106-14 变更三套状态机能否复用 P1 的元数据生命周期

**目标问题**：P5 任务 7 要求把 ECR / ECN / Problem 三套阶段状态机改成「元数据定义」。落地前必须确认：① P1 已有的 `meta_lifecycle` 是否够通用、能否承载非 `plm_object` 的单据状态机；② 既有「生命周期设计器」的编辑行为会不会破坏自定义字段；③ P1 的状态迁移执行链路能否直接复用。

**范围与方法**：只读核对 `V1__baseline.sql` 建表、`LifecycleService`（解析/列表/保存校验）、`LifecycleController`（权限与路由）、前端 `LifecycleView.vue`（表单回写）；对照 `V18__change.sql` 的状态字段现状；实跑 `ChangeSmokeTest`（含新增的元数据改动用例）验证运行时确实读元数据。

**关键发现**
1. **`meta_lifecycle` 是通用定义表**：`V1__baseline.sql:307-318` 只有 `code/name/type/definition_json/version_no/status`，`type` 默认 `'MAIN'` 但唯一索引在 `code` 上（`:318`）。
2. **代码里没有任何按 `type` 过滤的查询**：`LifecycleService.java:61-64` 的 `listDefinitions()` 是全表 `orderByAsc(code)`，设计器因此会自然列出所有状态机——新增 `type='CHG'` 的三行无需改前端即可被编辑。
3. **解析器只认固定字段**：`LifecycleService.java:35-43` 的 `StateDef(code,name,allFlow)` / `TransitionDef(from,to,action,label)`，`:86` 的 `parse` 忽略未知字段；保存时 `updateDefinition` 也是同一套校验。→ 在状态上塞 `mainEditable` 之类的自定义标记，**运行期读得到，但会被一次「设计器保存」抹掉**。
4. **设计器确实只回写三列**：`LifecycleView.vue:47-48` 的「允许发起任意流程」开关绑 `row.allFlow`，`:122` 新增状态也是 `{code,name,allFlow}`。→ 依赖自定义标记的设计会在设计器保存后悄悄失效。
5. **P1 的执行链路不能直接复用**：`LifecycleService` 的迁移是更新 `plm_object.lifecycle_state` 并写 `plm_state_log`（按 `plm_object.id`），而 ECR/ECN/Problem 在 `chg_*` 表里、状态列是 `status`。可复用「定义」，不可复用「执行」。

**结论与决策**
- 复用 `meta_lifecycle` 承载三套状态机（`type='CHG'`，code = `CHG_ECR`/`CHG_ECN`/`CHG_PROBLEM`），复用现成设计器与审计；**不新建状态机表**。
- 不依赖自定义状态标记，改用**派生规则**：可编辑主档 = 状态等于 `initial`；可调整关联对象 = 状态等于 `initial` 或是 `submit`/`review` 迁移的终点。这样设计器随意保存也不会改变行为。
- 只读定义、不自建执行链路：新增 `ChgStateMachine` 负责「解析 + 判定 + 取目标状态」，实际 UPDATE 仍由各业务服务/插件执行（保持 `chg_*` 表自己的 `updated_at/updated_by` 语义）。
- **不做缓存**：状态机只在写操作时读一行主键查询，换来设计器改完即时生效；相比缓存省掉一条失效通知链路。
- 自迁移（`from == to`）用于表达「该状态允许此动作但不改状态」：已通知状态下再下发通知、执行中重复执行。

**遗留与后续动作**
- 变更三套状态机目前**没有状态变更流水表**（时间线靠 `wf_comment`/`chg_*` 时间戳派生）。若需要「谁在何时把状态从 A 改到 B」的强审计，可在 `ChgStateMachine.require` 统一落一张 `chg_state_log`；是否落地待产品确认。
- 设计器页面把 `CHG_*` 与对象生命周期混在一块展示；若要区分，需要给 `LifecycleView` 加 type 分组（当前无影响，未改）。

## EXP-20261106-15 P6 工艺表基线与工艺路线数据模型

**目标问题**：P6 工艺（CAPP）开工前要确认：① 基线是否已有工艺相关表可复用；② 新增表的公司/权限/编号惯例；③ 新建数据的坑位（主键、唯一索引）。

**结论与决策**
- 工艺路线按「主档 + 工序」两张表落地；工序**整表替换**保存（一次事务删旧插新），前端不做差异比对，避免并发下的行级 diff 逻辑。

**遗留与后续动作**

## EXP-20261106-16 工序序号重建为何必须「删表重插」

**目标问题**：P6-2 要做「序号重建」（把乱掉的工序号一键规整为 10/20/30）和工序上移/下移。改号有两种实现：原地 `UPDATE seq_no`，或读出后重插。落地前确认哪种在唯一约束下不会中途失败。

**范围与方法**：核对 V21 建表索引；构造 5/7/9 的乱序数据实跑 `CappSmokeTest.resequenceAndCraftOwner`；对比两种实现的执行顺序。

**关键发现**
1. **唯一索引是行级的**：`V21__capp_routing.sql` 中 `CREATE UNIQUE INDEX uk_capp_step_seq ON capp_routing_step (routing_id, seq_no)`，同一条路线内工序号不可重复，但索引检查发生在**每条语句提交时**（PostgreSQL 普通唯一索引非 DEFERRABLE）。
2. **原地改号会中途撞键**：把 5→10、7→20、9→30 按顺序 UPDATE 时，第一条把 seq_no 改成 10 的瞬间若已有另一行是 10（或先改的那行恰好等于后改的目标）就立刻违反唯一约束。常见规避是「先整体加偏移再改回」两步 UPDATE，但仍要额外记住原值。
3. **删表重插天然无冲突**：读出旧工序（含名称/类型/工时/工作中心）→ `DELETE` 该路线全部工序 → 按新序号逐行 `insertStep`。因为旧行已全部消失，中间态没有任何唯一键压力；顺带修复历史脏号（如 0、负数、重复序）。
4. **代价可接受**：工序行没有外部引用（P6-1 阶段没有其它表引用 `capp_routing_step.id`），主键变化不影响任何关联；单条路线工序通常 < 50 行，重插成本可忽略。
5. **工艺分工的落点**：确认「分工」应落在主档（谁维护这条路线）而不是工序（工序已有 `work_center` 表示在哪个车间/工作中心加工），故 V22 只加 `capp_routing.owner_id`，默认取创建人。

**结论与决策**
- 序号重建一律「读旧 → 删 → 按序重插」，不写原地 UPDATE 版本（可读性更好、无中间态风险）。
- 前端上移/下移在**本地**交换并顺带按 `(index+1)*10` 赋号，保存时走已有的整表替换，不新增后端排序接口。
- 工序行若未来被外部引用（如工步、检验项），需要改为「保留 id 的两阶段改号」或给唯一索引加 `DEFERRABLE`；当前不预留。

**遗留与后续动作**
- `capp_routing_step.id` 在主键变化下不可作为历史标识；P6-4 工艺卡片如果要把「卡片行」绑定到具体工序，应绑定 `(routing_id, seq_no)` 语义键而不是 step id，或届时改造为稳定 id。
- 工序级排序权重目前只有 `seq_no`；若将来需要「插入半步」（如 15），可直接沿用 10 步进并在重建时压缩。

## EXP-20261106-17 工艺卡片模板版本化与导出口径

**目标问题**：P6-4 工艺卡片的 DoD 有两条硬要求——「模板修改后历史卡片版式不串」「导出 PDF/Excel」。落地前要定：① 模板版本怎么存（能否照搬工艺路线的版本策略）；② 卡片怎么做到不被后续改版影响；③ 导出用什么技术、中文字体有无坑；④ 卡片行数据从哪来、精度怎么统一。

**范围与方法**：对比 `V21__capp_routing.sql` 的唯一索引与 `CappRoutingService.copy` 的取号方式；核对 `plm-platform/pom.xml` 的 POI 能力；实现 `V24__capp_card.sql` + `CappCardService` + `CappCardExcelService` 后跑 `CappSmokeTest#cardTemplateVersioningAndExport`（内嵌 PG + 真实 POI 读回）。

**关键发现**
1. **工艺路线的「版本」不能直接照搬**：`V21__capp_routing.sql` 的唯一键是 `(company_id, code)`，`CappRoutingService.copy` 复制时用 `nextCode` **另取新编码**（`RT-000002`），`version_no` 只是「同一零件的第几条路线」。模板要的是「同码多版本并存」，因此唯一键必须是 `(company_id, code, version_no)`（`V24__capp_card.sql:47`），发布只把同族其它 `RELEASED` 置 `ARCHIVED`，不覆盖旧行。
2. **卡片改「双快照」才能真正不串**：卡片落库时既记 `template_code/template_version`（追溯出自哪版），也把版式整份复制进 `capp_card.layout_json`（`V24__capp_card.sql:61`）；工序行同样快照到 `rows_json`（`V24__capp_card.sql:67`）。导出只读卡片自身（`CappCardExcelService`），完全不回查模板表——所以模板改版、甚至旧版本行被清理，都不影响历史卡片。
3. **jsonb 的 `?` 操作符与 JDBC 占位符同名冲突**：统计「非合计行数」时若写 `e ? '__summary__'` 或 `e->>?`，`?` 会被 JDBC 当成参数占位符，导致参数错位/语法错误。改用包含判断 `NOT (e @> '{"__summary__":"true"}'::jsonb)`（`CappCardService.java:295`），既避开了占位符，也走 GIN 友好的 jsonb 比较。
4. **PDF 不是必须现在就上**：`plm-platform/pom.xml` 已有 `poi-ooxml 5.2.5`（compile 作用域，`plm-app` 测试可直接用 `XSSFWorkbook` 读回），导出 xlsx 零新增依赖且中文无障碍（字体名设「宋体」+ 字符串单元格即可）。PDF 需引 openpdf/PDFBox 并嵌入中文字体，字体路径在本机与容器不一致，风险高于收益。
5. **行按列投影成字符串快照，精度统一**：`CappCardService.java:449` 的 `buildRows` 依模板列把工序投影为「列键 → 字符串」，数值统一 `setScale(2)`；末行追加 `__summary__` 合计行（`CappCardService.java:50`），导出时加粗（`CappCardExcelService.java:92`）。这样「页面预览」与「Excel 导出」看到的数字逐字节一致，不会出现页面 1 位小数、Excel 3 位小数。
6. **卡片行绑语义键而非 step id**：行快照按 `(routing_id, seq_no)` 语义生成（承接 EXP-20261106-16 的遗留），因为序号重建会物理删除并重插工序行，`capp_routing_step.id` 不稳定。

**结论与决策**
- 模板：同码多版本 + 「另存新版本」改版 + 发布归档同族旧版；只有 `RELEASED` 模板能生成卡片（草稿版式还在改，没有稳定基线）。
- 卡片：双快照；「重新生成」只刷新 `rows_json` 并补齐表头默认值，用户手填的表头值保留。
- 导出：本阶段只做 xlsx（DoD 的 Excel 一半），PDF 单列为 P6-4b；不引入 PDF 依赖。
- 行渲染与 Excel 渲染共用同一份 `rows_json` 与 `layout_json`，前端预览即导出效果，减少「导出后才发现版式错」的返工。

**遗留与后续动作**
- **PDF 导出未做**（DoD 的「PDF」尚未满足）：需评估 openpdf + 中文字体嵌入，或退化为「前端打印/浏览器另存 PDF」。
- 卡片单元格级手改未做：目前只能覆盖表头 `fieldValues`，明细行是路线投影的只读快照。
- 卡片无状态机（视为草稿态）：发布/签审待接 `meta_lifecycle`，届时照 P5-8 的 `ChgStateMachine` 模式。

## EXP-20261106-18 工时定额该不该落快照

**目标问题**：P6-6 工时定额要满足「工时汇总与工序工时一致，公式改动可重算」。落地前要定：① 定额结果要不要像工艺卡片那样落一份快照表；② 多套规则（通用/按工序类型/按工作中心）如何互相优先；③ 单件与批量两个口径怎么切。

**范围与方法**：对比 P6-4 卡片「必须冻结版式」的理由；梳理工艺定额通行算法（准备工时按批一次、单件工时随件数线性）；实现 `V25__capp_time_rule.sql` + `CappTimeService` 后跑 `CappSmokeTest#timeRuleMatchingAndCalc` 与真实 HTTP 联调。

**关键发现**
1. **定额不能落快照，方向和卡片恰好相反**：卡片是「文档」，版式必须冻结（EXP-20261106-17）；定额是「当前规则下的测算值」，一旦落表就出现「路线改了但定额还是旧值」的双份数据漂移。故 `GET /capp/time-calc` 只读实时算（`CappTimeService#calc`），DoD 的「公式改动可重算」天然成立，无需重算按钮。
2. **规则优先级要可解释**：三类规则并存（通用 / 按工序类型 / 按工作中心）。用「工作中心精确 +2、工序类型精确 +1」打分取最高，同分时 `priority` 小者优先（`score` / `match` 方法）。这样「工作中心+类型」规则必然压过单维度规则，而 `priority` 只用来解同档冲突，不需要用户理解复杂的匹配树。
3. **准备工时与单件工时必须分开返回**：准备工时按批一次、单件工时随件数线性，混成一个「总工时」会让前端无法正确乘批量。接口分别给 `totalSetupEffective`（准备合计）、`singlePieceMinutes`（单件合计，不含准备）、`batchMinutes`（= 准备合计 + 单件 × 批量），前端只展示不重算。
4. **校验顺序的坑**：写过 `factor(value)` 把 `<= 0` 兜底成 1 再用于校验，导致 `setupFactor=0` 被静默接受（`CappSmokeTest` 实跑报 `Status expected:<400> but was:<200>`）。正确做法是**校验入参原值**（`req.setupFactor() != null && signum() <= 0 → 400`），兜底只用于 null 缺省。
5. **未命中也必须是显式结果**：没有规则时按原值算并返回 `unmatchedSteps` 计数与 `ruleCode=null`，前端标「未命中（按原值）」。否则用户会误以为「试算没生效」而去找 bug。

**结论与决策**
- 定额只存规则、不存结果；改规则/改路线后重新查询即生效。
- 规则匹配用「精确度打分 + priority 解冲突」，不做正则/表达式求值（当前业务不需要，且可解释性更重要）。
- 接口一次返回三个口径 + 命中详情，前端零计算。
- 单件工时口径**不含**准备工时（工艺惯例），批量工时才含；这一条写进迁移注释与 DTO 注释，避免后续理解反。

**遗留与后续动作**
- 定额暂未反向写入工艺路线/卡片（试算结果不落库），若后续要「卡片上打印定额工时」，应让卡片生成时调用同一 `calc` 并把结果作为行快照的一列，而不是另建定额表。
- 规则暂无生效区间与版本（改了就影响所有历史试算）；若需要「按年度定额」需加 `effect_from/effect_to`。
- 批量默认值目前固定 1，规则里的 `batch_qty` 只作参考展示，未自动带入试算。

## EXP-20261106-19 卡片 PDF 导出的中文字体方案

**目标问题**：P6-4b 要补上 DoD 里的「导出 PDF」。PDF 生成库有 OpenPDF/PDFBox/iText7 三条路，而中文是这类导出的传统坑：不嵌字体在别的机器上就是一排方块或问号。要定：① 用哪个库；② 中文字体从哪来（打包内置 vs 系统探测 vs 配置）；③ 找不到字体时怎么办。

**范围与方法**：核对项目现有依赖（只有 `poi-ooxml`，无任何 PDF 库）；验证中央仓库能否解析 `openpdf`；实现 `CappCardPdfService` 后跑 `CappSmokeTest#cardTemplateVersioningAndExport` 的 PDF 分支与真实 HTTP 导出，检查字节流里是否有 `FontFile` 与 `%%EOF`。

**关键发现**
1. **OpenPDF 可用且 API 与老 iText 一致**：`com.github.librepdf:openpdf:1.3.39` 补齐后 `mvn compile` 直接通过，包名仍是 `com.lowagie.text`（`Document` / `PdfPTable` / `BaseFont`），无需学习新 API；对 JDK 17 无额外适配。
2. **中文字体必须 embed，且 `.ttc` 要带索引**：`BaseFont.createFont("C:/Windows/Fonts/simsun.ttc,0", BaseFont.IDENTITY_H, BaseFont.EMBEDDED)`——不带 `,0` 索引时 OpenPDF 无法从 TrueType Collection 里取字体。用 `IDENTITY_H` 才能走 Unicode 编码，中文不依赖 GBK 码表。
3. **字体来源不能硬编码**：开发机是 Windows（宋体/雅黑/黑体），容器多是 Linux（Noto CJK / 文泉驿 / AR PL），仓库又不适合放几十 MB 的字体二进制。最终采用「配置优先 + 系统探测 + 明确报错」三段式：`nexplm.capp.pdf.font-path`（可带 `,0` 索引）→ 8 个常见路径依次探测 → 都没有则返回 400 提示配置路径。
4. **绝不生成「看起来成功」的乱码 PDF**：字体缺失时若用默认 Helvetica 兜底，接口会返回 200 但内容全是方块，比报错更难排查。因此缺失字体一律 400 + 明确文案。
5. **PDF 与 xlsx 必须同源**：两者都只读卡片的快照（`layout_json` / `field_values` / `rows_json`），不各自回查模板/路线，否则「Excel 改了版式、PDF 还是老样子」这类分叉迟早出现。
6. **测试要能在无字体环境跑**：`CappSmokeTest` 的 PDF 分支用 `assumeTrue`——200 时校验 `%PDF` 头与长度，非 200 且消息含「中文字体」则跳过；这样本机（有宋体）真跑通、CI/容器（可能无字体）也不会假红。

**结论与决策**
- PDF 用 OpenPDF 1.3.39，不引 PDFBox（后者加载 CJK 字体与 CMap 更繁琐）。
- 字体走「配置 + 探测」，配置项 `nexplm.capp.pdf.font-path`；生产容器部署时须在镜像内装中文字体或挂载字体文件并配该变量。
- 页面用 A4 横向（工艺卡片列多），表头字段区与明细表分两块渲染（表头信息栏 + 明细表），视觉上与传统工艺卡一致。

**遗留与后续动作**
- 生产环境字体未纳入部署脚本：`deploy/` 需要补「安装 fonts-noto-cjk 或挂载 .ttf + 设置 NEXPLM_CAPP_PDF_FONT_PATH」的说明与 compose 变量（已在 `deploy/README.md` 第 6 条补上）。
- 表头字段区与明细表是两块独立表格，列不对齐（Excel 版是同表）；若业务要求严格对齐需要改成单表 + 合并单元格，工作量较大。
- 跨页表头重复已补：明细表 `setHeaderRows(1)`，工序多的卡片翻页后仍带列名（原实现漏设，第 2 页起是无列名数字）。

## EXP-20261106-20 工步该绑工序行 id 还是工序号

**目标问题**：P6-2 补齐「工步子表」时，工步必须指向所属工序。可选的关联键有两个：`capp_routing_step.id`（物理主键）与 `(routing_id, seq_no)`（语义键）。选错的代价是**每次序号重建后工步全部变孤儿**，且这种错误在功能测试里很容易漏掉（只测「新建-查询」不会暴露）。

**范围与方法**：回看 EXP-20261106-16 的结论（序号重建是「删表重插」，换号必然换 id）；实现 `V26__capp_substep.sql` + `CappRoutingService` 的写入/迁移逻辑，跑 `CappSmokeTest#substepsAndProcessTree` 实测「5/7 重建为 10/20」后工步是否仍在，并验证复制路线是否带工步。

**关键发现**
1. **必须绑语义键**：`capp_routing_step.id` 是 `IdWorker` 每次重插新生成，`resequence` / `replaceSteps` 都是「DELETE 后重插」，因此任何按 id 关联的子表在重建后必然悬空。工步改为 `(routing_id, step_seq_no, seq_no)` 三元唯一，工序号变了只需显式迁移，语义清晰。
2. **迁移不能靠 UPDATE 改号**：`uk_capp_substep_seq(routing_id, step_seq_no, seq_no)` 在「5→10、7→20」这类互换中会中途撞唯一键（与工序重建同一个坑）。做法一致：整表读出 → 清空 → 按新工序号重插。
3. **工步随工序整表替换提交**：`StepSaveReq` 增加 `substeps`，服务端在重写工序时先清空该路线的工步再按提交内容重建。好处是「改工序号/删工序」不会残留孤儿工步；代价是前端编辑工步必须与工序在同一次保存里提交（抽屉只改本地草稿，不单独请求后端）。
4. **过程树不建表、不缓存**：`process-tree` 直接复用 `detail` 的数据再聚合 `substepCount` / `substepMinutes`。多一份「树表」就多一处可能与工序表不一致的数据；而树的规模（几十道工序）完全不需要缓存。
5. **工时对得上是隐性需求**：工步拆分的意义是「把工序工时落到动作上」，所以树节点额外给 `substepMinutes`（工步工时之和），让用户能一眼看出工步工时与工序工时是否吻合（差额往往是漏填工步）。

**结论与决策**
- 工步绑 `(routing_id, step_seq_no, seq_no)`，所有可能改工序号的操作（`replaceSteps` / `resequence` / `copy`）都必须显式迁移或复制工步。
- 工步不单独暴露 CRUD 接口（随路线整表替换），避免「工序删了但工步还在」的中途态。
- 过程树是只读派生视图，不落库。

**遗留与后续动作**
- 工步与工序工时暂无一致性校验（不阻断保存，只在树上显示差额）；是否要「工步工时之和 ≠ 工序工时」时告警需业务确认。
- 卡片（P6-4）暂未支持「按工步展开行」，如需工步级工艺卡，应在 `CappCardService.buildRows` 里按 substep 展开而不是给卡片加新列。
- 工步默认自带 `resource_id`（可覆盖工序级），但卡片列目前只取工序级资源名称；工步级资源尚未进入卡片渲染。

## EXP-20261106-21 成册要不要给卡片挂「册号」，齐套哪些项该算失败

**目标问题**：P6-5 有两个容易想当然的点：① 成册与卡片的关系能不能简化成「卡片有个册号字段」；② 齐套性检查里哪些缺失应该拦住用户（FAIL），哪些只是提醒（WARN）。两者都直接影响数据模型与用户信任度——一次误判 FAIL 会让「检查」变成狼来了。

**范围与方法**：对照 P6-4 卡片模型的字段设计；梳理工艺实务中「一个零件的工艺包」构成（路线 → 工序 → 工步 + 卡片 + 工时）；实现 `V27__capp_card_volume.sql` + `CappVolumeService` 后跑 `CappSmokeTest#volumeAndCompleteness` 与真实 HTTP 联调（建册、页序、跨零件、成册 PDF）。

**关键发现**
1. **不能给卡片挂册号**：同一张工序卡在实务中会被不同册引用（「机加工分册」与「总装分册」都含同一张卡）。单值册号会把关系写死，且无法表达页序。正确建模是 `capp_card_volume_item(volume_id, card_id, seq_no)` 的多对多。
2. **页序必须是册内属性**：同一张卡在不同册里页序不同，所以 `seq_no` 只能放条目表，且要 `uk(volume_id, seq_no)`（防两页同号）与 `uk(volume_id, card_id)`（防同册重复）。
3. **跨零件混装必须拦在保存时**：成册是「一个零件的工艺包」，混进别的零件，打印出来零件信息与卡片对不上，属于最难自查的错误。保存时校验 `card.object_id == volume.object_id`，直接 400。
4. **齐套的 FAIL 要极窄**：只有「没有工艺路线」「路线里没有工序」代表工艺根本不存在，才 FAIL；「路线未发布」「工时为 0」「资源未绑」「没拆工步」「没生成卡片」都只是「工艺还没写完」，一律 WARN。否则用户天天看到红叉会直接无视这个功能。
5. **空册不能发布**：发布意味着「装订确定」，空册发布后再改就违背语义；`release` 前校验 `cards` 非空。
6. **成册 PDF 复用单卡渲染**：把单卡渲染抽成 `renderCard(document, card, font)`，单卡导出与成册导出共用；成册只多一层「封页 + 目录 + 每张卡 newPage()」。不引 PDF 合并库，避免多一个依赖与多一次字节拷贝。
7. **页码不做**：目录页码需要两遍渲染（先排版拿页数再回填），成本高而工艺卡的目录实际很少看页码；用「页序 10/20/30」替代，与册内 `seq_no` 一一对应。

**结论与决策**
- 成册用 `volume + item` 多对多，页序属条目；卡片不感知册。
- 齐套 FAIL 仅限「无路线 / 无工序」，其余 WARN；`ready = failCount == 0`。
- 成册 PDF 复用单卡渲染函数，不引入 PDF 合并依赖。
- `GET /capp/cards` 增加 `objectId` 过滤，供成册选择卡片时复用分页接口。

**遗留与后续动作**
- 成册暂无「封面模板」与「页码/骑缝章」等排版要素，前者需要类似卡片模板的版式配置。
- 齐套检查没有「一键补卡」动作（如按缺失的已发布路线批量生成卡片）；如需要应在 P6 收尾时补一个批量生成入口。
- 册状态只有 DRAFT/RELEASED，无签审；若要纳入变更流程，应接 `meta_lifecycle`（与卡片状态机一并设计）。
- P6 剩余：质量规划（P6-8）与 ERP 下发接口（P6-9）未开始。

## EXP-20261106-22 控制计划该引用字典还是内联特性；下发预留做到哪一步算够

**目标问题**：P6-8/P6-9 两个「边界题」。质量规划：控制计划的「受控特性」应该全部来自检验项字典（强引用），还是允许行内自由填写？下发：计划写的是「与 ERP 的工艺下发接口**预留**（P9 实现）」，那本阶段到底要做到哪一步才算合格——不做到位后面接 ERP 要推倒重来，做过头又是在没有 ERP 契约的情况下瞎猜。

**范围与方法**：对照计划 P6 第 8/9 条与 DoD；梳理质量实务中控制计划的填法（一行 = 工序 + 特性 + 规格 + 测量 + 抽样 + 控制方法 + 反应计划）；实现 `V28__capp_quality.sql`、`V29__capp_erp_dispatch.sql` 与对应服务后，跑 `CappSmokeTest#qualityPlanAndErpDispatch` 与真实 HTTP 联调。

**关键发现**
1. **强引用字典会让填表变成维护字典**：真实控制计划里大量特性是一次性的（某工序某个尺寸），强制先建字典再引用，用户会绕过系统用 Excel。因此 `item_id` 设计为**可选**，选中时只带出 `spec/method/gauge` 默认值，行上的值才是权威。
2. **字典改动不得篡改历史计划**：如果行只存 `item_id`、展示时联查字典，那么字典改了规格，已发布计划的历史记录就跟着变——质量记录不允许这种「追溯性变化」。行内联值是唯一符合审计要求的做法。
3. **行要绑工序号并快照工序名**：绑 `step_seq_no` 与工步一致（序号重建不脱离）；再存一份 `step_name` 快照，工序改名后历史计划仍显示当时的工序名，与「版式快照」同一思路。
4. **骨架行能省掉最痛的一步**：控制计划通常 10~40 行且与工序一一对应，如果只能新建空表再手填行号，几乎必然出错。`rows` 为空时按路线工序自动生成骨架（一工序一行），用户只需填特性。
5. **下发预留的「够」是三条**：① 载荷契约（要下发什么）② 快照落库（当初发了什么）③ 取数与回执入口（P9 怎么接）。缺任何一条后面都要改表；而 ERP 侧的字段映射、认证、幂等、重试全部属于 P9，本阶段做就是猜。
6. **载荷必须固化而不是实时拼装**：下发是「某一时刻的口径」，路线后面改了甚至归档了，必须还能回答「当初发了什么」。因此 `payload_json` 落 jsonb + `payload_sha` 便于 ERP 侧做幂等；测试用「两次读取 `generatedAt` 不变」证明读的是快照。
7. **只允许下发已发布路线**：草稿还在改，下发出去的工艺会被产线当权威执行，属于不可挽回的错误。

**结论与决策**
- 控制计划行内联特性值，字典只做默认值来源；发布前强制每行都有受控特性。
- 下发只做「载荷 + 快照 + 取数/回执」，明确不实现真实 ERP 契约（P9）。
- 下发状态位预留 PENDING/SENT/FAILED/VOID，P9 适配器接上后无需改表结构。

**遗留与后续动作**
- P9 必须补：ERP 字段映射表、认证方式、幂等键（可直接用 `payload_sha`）、失败重试与回执对账、下发范围与「变更后是否重新下发」的策略。
- 控制计划暂无版本化（发布后不可改，改需新建一份）；若需要「一零件多版本控制计划并存」，参考卡片模板的同码多版本方案。
- 控制计划与卡片/成册尚未联动（成册里不含控制计划）；若客户要求「工艺包 = 卡片 + 控制计划」，应在成册条目里增加 `item_type` 区分。
- P6 九项至此全部完成；下一步是整体回归与演示准备。

**范围与方法**：读 `docs/02-数据模型设计.md:247` 的旧系统 `prj_task_output(task_id, object_id, output_type, required)` 定义；核对本系统三类对象的实际落地表（`V1__baseline.sql` 的 `plm_object` 通用基表 `object_type='PdmDoc'/'PdmItem'`；`V24__capp_card.sql:52` 的 `capp_card` 独立表，且有 `object_id` 指向零件）；核对 `V2__seed.sql:68` 的 DEFAULT_LIFECYCLE 状态码；实现 `V34__project_deliverable.sql` + `ProjectDeliverableService` 后跑 `ProjectDeliverableSmokeTest` 与真实 HTTP 联调。

**关键发现**
1. **三类对象不在同一张表**：文档/零部件是 `plm_object` 的不同 `object_type` 行，工艺卡片在 `capp_card`（本身没有 `lifecycle_state`，只有模板有 `status`）。要「一个任务挂任意类型」，只能用 `object_type + object_id` 多态，无法建单一外键。
2. **不能存 code/name 快照**：本系统对象改名是常态（同一 master 多 revision），快照会让「交付物列表」与「对象详情」长期不一致。代价是缺件时回查不到——因此 `resolveObjects` 刻意**不过滤 deleted**，软删的行仍返回编码/名称，否则缺件提示只能显示雪花 ID，等于没提示。
3. **生命周期状态是驼峰**：`Draft`/`InWorkflow`/`Released`/`Obsolete`（`V2__seed.sql:68` 的 DEFAULT_LIFECYCLE），不是全大写；判定必须写 `Released`/`Obsolete`，用 `RELEASED` 会把所有对象误判为未发布。
4. **旧系统只有 `required` 一个开关**，没有「输入是否必需」的概念；本系统输入项只用于追溯上游来源，不参与齐套——否则「上游还没交」会被算成本任务缺件。
5. **缺件计数按交付物行而非对象去重**：联调实测同一物料挂到两个任务后软删，看板 `missingTotal = 2`。这是对的——「谁少了东西」必须按任务算。

**结论与决策**
- 交付物 = `prj_task_output(company_id, task_id, output_type INPUT/OUTPUT, object_type DOC/ITEM/CAPP_CARD, object_id, required, remark)`，唯一键 `(task_id, output_type, object_type, object_id)`（同对象可同时是输入与输出），软删。
- 齐套口径 FAIL 极窄：`MISSING`（对象已删/不存在）与 `OBSOLETE`（`lifecycle_state=Obsolete`）算缺件；`UNRELEASED`（存在但未发布）只提醒；工艺卡片无生命周期，存在即 `OK`。
- 项目 `ready = missingTotal == 0`；任务 `ready = missingCount == 0`；无交付物的任务视为齐套（「没要求」≠「不齐套」）。
- 提交审核加齐套守卫：`submit` 前校验必需 OUTPUT，有缺件抛 `PRJ.DELIVERABLE.INCOMPLETE`(409)；未声明任何必需交付物直接放行，避免拦住 P7-3 已上线的任务。
- 不新增权限点，沿用 `prj.project.read/write`。

**遗留与后续动作**
- 交付物不参与项目进度汇总（进度仍按叶子任务加权）；若要「按交付物计权重」，需改 `ProjectTaskService#recalcProgress`。
- 无批量挂接，也不能按项目模板预置交付物清单——等 P7-6 项目模板立项时一起做（模板里定义每类任务的输出物）。
- 输入项没有「来源任务」关系（只依赖对象，不知道谁该产出它）；P7-8 门户若要「上游未交预警」，需补 `source_task_id` 或按对象反查任务。

## EXP-20261106-24 工时按天记还是按块记；谁能改谁不能审；项目实际工时含不含待审批

**目标问题**：P7-5 要求「工时填报与审批；项目资源负荷（简化）」。四个决定会长期固化：① 工时记录粒度（按「工时块」还是按「人+天+任务」）；② 谁有权改、谁有权审（项目经理能不能替人改工时、能不能审自己）；③ 项目实际工时算不算待审批；④ 负荷率的分母怎么来。

**范围与方法**：对照 `docs/00-现状分析报告.md:186` 的旧系统「工时填报」与 `docs/03` P7 第 6 条；设计 `V35__project_timesheet.sql` 与 `ProjectTimesheetService` 后跑 `ProjectTimesheetSmokeTest`、真实 HTTP 联调，并把跨用户的审批/越权场景都跑了一遍。

**关键发现**
1. **按「工时块」记会让审批列表不可核**：一天在同一任务上干两三段是常态，若每段一条记录，一个 20 人项目一周就是几百条待审，没人会认真看；按「人+天+任务」一条、多段写备注，审批列表才在一屏内。唯一键 `(task_id, user_id, work_date)` 直接把这个口径固化成约束。
2. **能审 ≠ 能改**：项目经理必须能审批，但替人改工时等于篡改考勤。因此 `update/delete/submit` 都只允许 `user_id = 当前用户`，审批接口才看 `prj.project.write`。
3. **不能审批自己**：自审是审计缺陷，不是"简化流程"。服务层对 `user_id == 审批人` 直接 409；联调里业务用户（有 `prj.project.write`）审自己也被拦。
4. **待审批不能算实际工时**：`SUBMITTED` 只是"已填未审"，把它算进项目实际工时会让周报数字随填报动作波动；因此汇总返回 `approvedHours` 与 `pendingHours` 两个口径，负荷只用前者。
5. **发现一个既有缺陷：`@PreAuthorize` 拒绝返回 500 而不是 403**。方法级鉴权在 Controller 调用前由 AOP 抛 `AccessDeniedException`，它先进入 `@RestControllerAdvice`，被 `com.nexplm.common` 的 `Exception` 兜底 handler 吞成 500——前端会把「没权限」当成「服务端坏了」。`plm-common` 是零依赖底座、不引 spring-security，故在 `plm-platform/security` 加 `@Order(HIGHEST_PRECEDENCE)` 的专门 advice 转 403。
6. **批量审批必须整批原子**：部分通过会造成"同一批里有的算了有的没算"，对账时最难查；实现上循环调用单条 approve，任何一条不合法整体回滚。

**结论与决策**
- 表 `prj_timesheet`：`company_id + project_id`（冗余，任务不跨项目）+ `task_id + user_id + work_date + hours(0.5~24) + work_type(NORMAL/OVERTIME) + status`，唯一键含任务/人/日，软删。
- 状态机 `DRAFT → SUBMITTED → APPROVED / REJECTED`；只有 DRAFT/REJECTED 能改删，编辑后回落 DRAFT；APPROVED 不再允许改。
- 工时只能填「今天及以前」（未来日期 400）；单日 0~24h 上限。
- 汇总口径：实际工时 = APPROVED 之和，`SUBMITTED` 单列待审批，`REJECTED` 单列驳回。
- 资源负荷（简化）= 已审批工时 / (期间周数 × 40h)，不接节假日日历。
- 权限：填报 `isAuthenticated`；审批 `prj.project.write`；列表接口对没有 `prj.project.write` 的人强制 `userId = 当前用户`（传别人的 userId 会被覆盖）。

**遗留与后续动作**
- 没有节假日/调休日历，负荷率是粗估；P7-7 做日历排程时把工作日历接进来，容量分母改为真实工作日。
- 工时不带费率，无法直接出人力成本；若要"项目人力成本"，需加 `rate`（人/角色/年月）与审批后计价。
- 审批是内置的两态简单审批，没接 `wf_*` 流程引擎；若客户要求多级审批/会签，应改为发起工作流（`PROJECT_ROLE` 执行人解析器已在 P4 预留）。
- 工时与任务进度无联动：填了工时不会推进 `progress`（进度仍靠 P7-3 的提交/审核），这是刻意的——工时是投入，进度是产出。

## EXP-20261106-25 模板里存绝对日期还是相对偏移；模板编码谁生成；立项后模板还跟项目有关系吗

**目标问题**：P7-6 要求「项目模板与文件夹模板：立项自动生成目录结构与任务」。四个决定：① 模板任务的日期怎么表达；② WBS 编码由前端填还是服务端生成；③ 模板与已立项项目是「引用」还是「快照」；④ 目录模板在模板阶段用什么路径（物化路径依赖 id）。

**范围与方法**：对照 `docs/03` P7 第 2 条与 `V32__project_task.sql` 的 WBS 实现；设计 `V36__project_template.sql` 与 `ProjectTemplateService` 后跑 `ProjectTemplateSmokeTest`、真实 HTTP 联调（建模板 → 编任务/目录 → 立项 → 校验日期与树）。

**关键发现**
1. **模板里存绝对日期毫无意义**：同一模板这个月立项和下个月立项，计划起止应该整体平移。必须存「相对开工日第几天 + 工期」，立项时才换算。项目计划结束日也就能由 `max(offset + duration)` 直接推出（联调用例：offset 5 + 工期 5 → 12-10）。
2. **编码让前端填必然撞键**：模板任务是表格编辑，用户插一行、拖一行，手填 `1.2` 极易重复。沿用 P7-2 `resequence` 的思路：前端只传 `parentWbsCode`，服务端按数组顺序生成 `1 / 2 / 2.1`，并校验父编码必须在本数组更靠前出现（天然挡住"先引用后定义"）。
3. **立项必须是快照，不是引用**：如果项目保留 `template_id`，模板一改所有历史项目的 WBS 都会变——项目一旦立项就是独立实体。因此生成完立刻落成 `prj_task`/`prj_project_folder`，不保留任何模板引用；联调里"删除模板后项目任务仍在"就是这个口径的直接结果。
4. **目录模板只能用逻辑路径**：物化路径 `/{id}/` 依赖新 id，模板阶段还没有 id。模板存 `parent_path`（`/`、`/01-设计文档/`），立项时按父路径深度排序逐级插入，边插边把「逻辑路径 → 新 id / 物化路径」记进 map。
5. **模板明细要物理删**：`uk(template_id, wbs_code)` 是部分唯一索引，整表替换若用软删会立刻撞键；模板明细属于草稿数据、也没有历史追溯价值，直接 `DELETE` 最干净（主档仍软删）。
6. **停用的模板不能立项**：停用意味着"不再用这个骨架"，但已立项项目完全不受影响（快照），所以只用 `enabled=false` 挡住新增，不做删除。

**结论与决策**
- `prj_template`（主档，`PT-000001` 自增）+ `prj_template_task`（`start_offset`/`duration_days`/`wbs_code`）+ `prj_template_folder`（`parent_path` 逻辑路径）。
- 任务与目录都用「整表替换」接口（`PUT /prj/templates/{id}/tasks|folders`），编码/顺序由服务端算。
- 立项接口 `POST /prj/projects/from-template`：复用 `ProjectService.create`（含 `PJ-` 取号与校验），再灌任务与目录，整体一个事务。
- 生成的项目 `status=DRAFT`、任务 `NOT_STARTED`、`progress=0`，与手工立项一致。
- 新增项目文档目录表 `prj_project_folder`（物化路径 + parent_id），不塞进 `ws_folder`——后者是「我的/公共/组空间」语义，塞项目目录会把两套权限模型搅在一起。

**遗留与后续动作**
- 模板未做版本化：模板改了就是改了，没有"v1/v2"；若客户要求"模板变更留痕"，需加 `prj_template_version` 或接 `meta_lifecycle`。
- 目录只建了 `prj_project_folder` 骨架，尚未与文档归档/`ws_folder` 打通（文档挂目录、目录权限继承都还没做）。
- 模板不含「默认交付物清单」与「成员角色」：P7-4 的 `prj_task_output` 可以扩成模板项（模板任务 → 默认输出物类型），成员角色可参照 `prj_member.role` 预置。当前生成的项目成员为空，需手工加。
- 没有「从已有项目另存为模板」，而这是顾问最常用的建模板方式；实现可复用 `instantiate` 的反向逻辑（读项目任务/目录写回模板）。

## EXP-20261106-26 日历拖拽改期的三个口径，以及 queryForList 取 date 列的静默陷阱

**目标问题**：P7-7 要求「日历排程 / 甘特拖拽」。要定：① 日历上放哪些任务；② 拖动父任务/子任务时谁跟着动；③ 只改时间还是也改依赖关系；④ 实现路径上怎么读 `date` 列才不会静默算错。

**范围与方法**：对照 `docs/03` P7 第 5 条与 `V32__project_task.sql`；新增 `calendar` + `reschedule` 两个接口与 `ProjectCalendarView.vue`；先跑 `ProjectCalendarSmokeTest`，再做真实 HTTP 联调（拖子任务、拖父任务、拉长、非法区间四种）。

**关键发现**
1. **未排期任务不进日历**：日历靠 `plan_start/plan_end` 定位，没有日期的任务没有位置。强行画在"今天"会让人以为已排期。查未排期任务用 WBS 看板，日历接口只返回"与查询区间相交且已排期"的任务。
2. **拖父任务级联、拖子任务不动祖先**：父条是"承诺"，子条是"执行"。拖父任务时子任务必须跟着走（否则父子区间立刻矛盾，甘特图裂开）；拖子任务时若回头改父承诺，等于把上周评审过的计划悄悄改掉。因此只做「向下级联」，不做「向上汇总」，也不动项目 `plan_start/plan_end`。
3. **改期不碰依赖边**：`prj_task_dep` 表达的是语义关系（FS/SS/FF/SF + lag），拖时间不改变"谁该等谁"。若要实现"沿依赖自动顺排"，那是另一套排程算法（CPM），不应混进拖拽接口。
4. **拉长与平移要分开算**：`delta = 新 planStart − 旧 planStart`。`delta != 0` 才级联平移子树；只是右侧拉长工期（`delta == 0`）时子任务原地不动——联调用例专门验证了"父任务拉到 12-20 而子任务仍停在 12-13"。
5. **`queryForList` 取 `date` 列会返回 `java.sql.Date`**：代码里 `task.get("plan_start") instanceof LocalDate` 判 false → `oldStart=null` → `delta=0` → 子树一帧都没动，但接口返回 200、父任务日期还是对的，属于典型的静默错误。改为用 `RowMapper` 显式 `rs.getObject("plan_start", LocalDate.class)`。**同类代码在做日期差值计算前都要用 RowMapper，不要依赖 `queryForList` 的运行时类型。**

**结论与决策**
- `GET /prj/projects/{id}/calendar?from&to`：返回与区间相交的已排期任务（扁平 + `ownerName`），默认本月；前端按月网格自行展开到每一天（跨天任务每天都出现）。
- `POST /prj/tasks/{id}/reschedule{planStart,planEnd}`：校验 `planEnd >= planStart`（400），更新自身 `plan_start/plan_end/duration_days`，再按 `delta` 用递归 CTE 平移整棵子树（`date + int`）。`duration_days = 新 end − 新 start + 1`。
- 前端 `/project/:id/calendar`：月视图 6×7 网格、状态着色、HTML5 拖拽（拖任务条到另一天即平移，跨天任务在每一天都可拖）；无 `prj.project.write` 的人拖拽被拦。

**遗留与后续动作**
- 没有"沿依赖自动顺排"（CPM/关键路径），拖一个任务不会推动后继任务。
- 日历不显示工时、里程碑不特殊渲染（里程碑 `plan_start == plan_end`，视觉上只是一个单日 chip）。
- 项目计划起止不随任务改期自动伸缩，若任务被拖出项目区间，项目甘特范围靠 `board` 的 `rangeStart/rangeEnd`（按任务 min/max 实时算）兜住，但项目主档的 `plan_start/plan_end` 仍是原值。
- 拖拽为整条平移，不支持拖两端改工期（要改工期走任务编辑对话框）；未做冲突检测（同一人被排了两个并行任务不会提示）。

## EXP-20261106-27 门户三视图各自回答什么问题；时间进度与"落后"的口径；聚合怎么不做 N+1

**目标问题**：P7-8 要求「项目门户：我的项目/项目经理/领导三视图（卡片 + 列表）」。要定：① 三视图是不是同一份数据的三种排版；② "落后"怎么判（用什么分母）；③ 逾期任务/待审工时/成员数这些附加指标怎么取才不拖垮列表；④ 实现上有没有踩到框架坑。

**范围与方法**：对照 `docs/03` P7 第 7 条与 `V31/V32/V35` 的表结构；新增 `ProjectPortalService` 三个接口与 `ProjectPortalView.vue`；跑 `ProjectPortalSmokeTest` 与真实 HTTP 联调（构造一个"已到期、任务逾期、有待审工时"的落后项目）。

**关键发现**
1. **三视图不是同一份数据的三种排版**，回答的是三个问题，指标口径必须不同：
   - 我的项目 → "我要做什么"：`myTaskCount` / `myOpenTaskCount` 只算 `owner_id = 我` 的任务，不是项目任务总量（否则第一屏全是与我无关的数字）；
   - 我管理的项目 → "快不快"：进度 vs 时间进度 + 逾期任务 + 待审工时（卡住的活在哪）；
   - 公司组合 → "盘子怎么样"：状态分布、平均进度、到期未结项数、风险清单。
2. **时间进度 = (今天 − 计划开始) / (计划结束 − 计划开始)，clamp 到 0~100**；计划起止没填全就返回 `null`，不猜。用 0 或 100 假装有结论会让"没排期的项目"永远显示为落后/超前。
3. **不能只凭"有逾期任务"判落后**：项目进度由 P7-2 的任务汇总写回，一个项目可能有 DONE 任务把进度抬到 60%，但同时又有逾期任务。所以判定用 `deviation = progress − timeProgress`，`deviation <= 0` 或存在逾期任务才进风险清单；排序按 deviation 升序、逾期数降序，取前 10。
4. **列表页必须避免 N+1**：任务统计（task/done/overdue）、待审工时、成员数各用一条 `GROUP BY project_id` 聚合，再在 Java 里用 Map 拼到项目行上。项目千级时这是 4 条 SQL，而不是 4×N 条。
5. **`JdbcTemplate.query(sql, lambda, args)` 的 lambda 若表达式有返回值，会和 `ResultSetExtractor` 重载撞车**，编译报「对 query 的引用不明确」；必须显式 `(RowCallbackHandler)` 强转（本阶段踩过 3 处）。
6. **聚合查询统一按列位置读**（第 1 列恒为 `project_id`，后 3 列为指标），否则每个 SQL 都要记不同列名，容易像第一次实现那样写出 `rs.getInt(1 + 0 + 1)` 这类错误。

**结论与决策**
- `GET /prj/portal/my-projects`：我是经理或成员（`prj_member`）的未结项项目，按计划结束日升序；带 `myTaskCount/myOpenTaskCount/manager/member`。

## EXP-20261106-28 质量问题"打回"是退回同一轮还是开新一轮；验证阶段能不能改措施

**目标问题**：P8-1 要求质量问题「登记 → 责任分派 → 多轮整改 → 验证关闭」。要定：① 验证不通过时是打回原措施还是开启新一轮；② 提交验证的前置校验卡到什么程度；③ 验证过程中措施还能不能改；④ 登记时能不能顺手分派。

**范围与方法**：对照 `docs/03` P8 第 1 条与 DoD「一个质量问题走完两轮整改并关闭」；设计 `V37__quality_issue.sql` + `QualityIssueService`，跑 `QualityIssueSmokeTest` 与真实 HTTP 联调（把两轮整改完整走一遍）。

**关键发现**
1. **打回必须开新一轮，而不是把同一条措施打回**：第 1 轮的遏制措施与第 2 轮的根因分析是两类工作、两个责任人可能都不同；如果复用同一批行，第 1 轮做过什么就查不出来了。所以措施表带 `round_no`，验证不通过时 `issue.round_no + 1`，旧轮次原样保留，前端按轮次分组展示。
2. **提交验证的前置校验要卡紧**：① 必须已分派责任人（否则验证人找不到人）；② 当前轮次至少 1 条措施；③ 当前轮措施必须全部 DONE。少了任何一条，验证人点进去只能干等或来回问。
3. **验证阶段冻结措施**：`VERIFYING` 状态下新增/修改/删除措施一律 409。边审边改的结论不可信；确需补充应先由验证人打回（开新一轮）再改。
4. **登记即可分派**：现场登记时往往当场就知道责任人，允许 `POST /qlt/issues` 直接带 `ownerId` 并落到 `ASSIGNED`，避免"先建一条再点一次分派"这种无意义的两步。
5. **状态只能走动作**：保存接口没有 `status`/`roundNo` 字段，状态迁移全靠 assign/submit/verify 三个动作，前端改不了状态机。
6. **有措施即进入整改中**：`ASSIGNED` 只表示"派了人"，加第一条措施后自动转 `IN_PROGRESS`，让列表上的状态与真实工作量对齐。

**结论与决策**
- `qlt_issue`：`code(QI-000001)` + `source/severity/status/round_no` + 可选 `object_type/object_id/object_code`（关联物料/文档）+ `project_id/supplier_id` + `owner_id/due_date` + `verify_by/verify_at/verify_note`。
- `qlt_issue_action`：`issue_id + round_no + action_type(CONTAINMENT/ROOT_CAUSE/CORRECTIVE/PREVENTIVE/VERIFY) + content + owner + due_date + status(PENDING/DONE) + done_at`。
- 动作接口：`assign`、`actions`（增删改）、`actions/{id}/done?done=`、`submit`、`verify{passed,note}`；验证不通过时 `note` 必填（400）。
- 列表支持 `keyword/status/severity/source/ownerId/overdue`，排序「未关闭在前 → 期限升序 → id 倒序」；`overdue` 由服务端算（`due_date < 今天 且未关闭`），已关闭的问题不会再被算成超期。
- 权限 `qlt.issue.read/write` 已注册并授予 `SYS_ADMIN`/`BUSINESS`。

**遗留与后续动作**
- 8D 模板不可配（P8-2 做）：当前措施类型是固定五类，没有"D1~D8 模板 + 每个节点的必填项"。
- 没有"超期自动提醒/升级"（P9 通知通道做好后接）。
- 质量问题与不合格品/NCR、返工返修单、供应商评级的联动都还没有；`supplier_id` 字段先留了位。
- 附件（现场照片、检验报告）未挂接，需要等文档中心的对象关联能力；目前只能用 `description` 记文字。

## EXP-20261106-29 8D 模板要不要建"步骤实例表"；同一轮重复应用模板怎么挡；质量看板的关闭率按什么口径算

**目标问题**：P8-2 要求「8D 模板可配 + 质量看板」。要定：① 模板步骤落地到问题上是另建一张"步骤实例表"，还是直接写成措施；② 一键应用被点两次（或验证打回后又点一次）该怎么处理；③ 看板关闭率/趋势/超期的统计口径；④ 期间过滤怎么避免时区坑。

**范围与方法**：先盘 P8-1 已有的两张表与既有规则（`backend/plm-app/src/main/resources/db/migration/V37__quality_issue.sql`、`backend/plm-platform/src/main/java/com/nexplm/platform/quality/service/QualityIssueService.java:290-320` 的提交验证校验），据此设计 `V38__quality_8d_template.sql` + `QualityTemplateService` / `QualityDashboardService`，再用 `QualityTemplateSmokeTest#applyTemplatePerRound` 跑「建模板 → 应用 → 同轮防重 → 打回后新一轮再应用 → 看板口径 → 删模板」全链路。

**关键发现**
1. **不建"步骤实例表"**：P8-1 已经定死"提交验证要求当前轮措施全部 DONE"（`QualityIssueService.java` 提交校验分支）。若再建 `qlt_issue_step`，完成度要在步骤表与措施表各算一遍，还会出现"步骤完成但措施没写"或反之的两套真相。步骤本质就是"要做的一件事"的标题，直接落 `qlt_issue_action` 即可，快照语义天然成立（`QualityTemplateService.java:218` 的 INSERT）。
2. **同轮重复应用必须有闸口**：一键按钮点两次就生成两份重复措施，责任人分不清删哪份。`qlt_issue` 只有 `template_id` 不足以判断——模板在打回后的下一轮还可以再用（轮次变了是合法场景）。因此 V38 加 `template_round`（`V38__quality_8d_template.sql:48-51`），应用时记「哪一轮用过哪个模板」，同轮同模板 409（`QualityTemplateService.java:203-210`）。
3. **应用时机要挡两头**：`CLOSED` 应用没意义、`VERIFYING` 应用等于边审边改（与 P8-1「验证中冻结措施」冲突），两者都 409（`QualityTemplateService.java:197-202`）；`OPEN`/`ASSIGNED` 应用后推进到 `IN_PROGRESS`，与"加措施即整改中"的既有规则一致。
4. **关闭率按全量快照，不按期间**：按期间算（期间内已关闭 / 期间内登记）会被当期新登记的问题永远压低，看起来像质量突然恶化，其实是口径问题。故 `closedRate = 已关闭 / 全部`（`QualityDashboardService.java:49`），期间只影响趋势窗口；`avgCloseDays` 也只统计已关闭且有关闭时间的，未关闭不按今天估算（否则老问题会拖着平均天数虚高）。
5. **趋势按月补齐空月**：`TREND_MONTHS = 6`（`QualityDashboardService.java:29`）默认近 6 个月，服务端把没有数据的月份补 0 返回，前端不必再做空月对齐；月内过滤用 `reported_at::date / closed_at::date` 闭区间（`QualityDashboardService.java:81-90`），**不用时点比较**——`timestamptz` 与时点参数比较会被服务端/驱动时区平移，跨时区部署时会差一天。

**结论与决策**
- 模板主档 `qlt_issue_template`（`DT-000001` 取号、`template_type` 8D/CUSTOM、`enabled` 停用即不能应用、软删）+ 步骤表 `qlt_issue_template_item`（`item_code` 模板内唯一、`action_type` 复用措施五类、`prompt` 预填提示语、`required`、`sort_no`）；步骤整表替换保存（先 DELETE 再插，`sort_no` 默认 `(index+1)*10`）。
- 应用接口 `POST /qlt/issues/{id}/apply-template`：生成措施的 `content = "[D3] 提示语"`（无提示语用步骤名），`owner_id` 默认取问题责任人，状态 `PENDING`；生成后写回 `template_id/template_code/template_round`。
- 看板 `GET /qlt/dashboard?from&to`：6 张 KPI（总数/未关闭/已关闭/关闭率/超期/平均关闭天数）+ 状态·来源·严重度分布 + 月度趋势（新增/关闭/净增）+ 责任人负荷 TOP5（只算未关闭，先按未关闭数再按超期数排，`QualityDashboardService.java:126`）。
- 权限 `qlt.template.read/write` 入 V38 并授予 `SYS_ADMIN`/`BUSINESS`；应用模板走 `qlt.issue.write`。

**遗留与后续动作**
- 模板暂无"版本"概念：改步骤即时生效于之后的应用，已生成措施是快照不受影响；若将来要给老问题上"模板改版留痕"，再补 `version_no`。
- 模板步骤的 `required` 只作展示与提示，**未在提交验证时单独卡**（P8-1 的"当前轮全部 DONE"已覆盖实质约束）；若业务要求"必填步骤不得删"，需在 `deleteAction` 里按模板步骤反查，暂不做。
- 看板目前只有"数量口径"，没有"金额/工时/不良率"等质量成本指标（缺数据源）。
- 质量看板未做导出（xlsx）；超期提醒/升级仍等 P9 通知通道。

## EXP-20261106-30 体系文件放通用文档层还是独立建模；模板怎么变成约束；发布口径与文件夹可改性

**目标问题**：P8-3 要求「IATF16949 体系文件：模板 + 文件夹 + 版本 + 审批 + 审核记录」，DoD 是「体系文件按模板生成并审批发布」。要定：① 体系文件是否直接复用 `doc_master`/`plm_object`（通用文档层）；② 模板里的"章节骨架"是摆设还是硬约束；③ 发布/修订的口径（版本号、生效日、下次评审日、历史怎么留）；④ 文件夹 code 能否改；⑤ `docs/02` 里 `tf_object` 设计稿是否照搬。

**范围与方法**：读 `backend/plm-app/src/main/resources/db/migration/V5__doc.sql`、`V8__doc_classify.sql`、`V1__baseline.sql` 的 `plm_object`/`file_link` 定义，读 `doc/service/DocService.java` 与 `change/service/ChgExecService.java` 的升版路径，比对 `docs/02-数据模型设计.md:250` 的 `tf_object` 设计稿；再据此设计 `V39__sys_doc.sql` + `SysDocService`，用 `SysDocSmokeTest#templateGenerateApproveRevise` 跑「建文件夹→建模板→按模板生成→提交→驳回→发布→修订→发布 v2→作废」全链路验证。

**关键发现**
1. **通用文档层没有受控语义**：`doc_master`（`V5__doc.sql:8-20`）只有 `doc_type/vault_id/file_ext/main_file_id` 等，编号/名称/状态/版本全在通用主表 `plm_object`（`V1__baseline.sql:321-351`：`code/name/lifecycle_state/revision/iteration/is_latest/released_at`）。**没有版本表**——版本就是同 `master_id` 的多行 `plm_object`（`doc/service/DocService.java:39` 类注释）。也没有"受控/非受控、发放回收、作废留档、评审周期"任何字段。
2. **通用文档升版只有一条路**：`change/service/ChgExecService.java:229`（变更执行 REVISE 复制 `revision+1`、旧行 `is_latest=false`）。doc 模块自身没有 publish/revise 接口，状态迁移只能走 `POST /objects/{id}/transitions`。体系文件"改一句条款"就走变更单，代价与业务实际不匹配。
3. **`docs/02` 早就规划了独立对象**：`docs/02-数据模型设计.md:250` 的 `tf_object`（`object_id, template_id, folder_id, version_no`）就是体系文件独立建模的思路，只是从未落库。本轮按它落地，没有推翻原设计。
4. **"模板"若只做提示就等于没有模板**：模板给的是章节骨架，若不校验，用户按模板生成后仍可能空着章节提交，审批人只能驳回再等。故把 `required` 写进章节快照，**提交审批时逐章校验内容非空**，这是"按模板生成"唯一的硬约束点。
5. **发布口径必须落版本快照，否则历史会被覆盖**：主档一行只有一个 `version_no` 与 `sections`，若不留快照，修订后旧版本正文就没了（体系文件审核恰恰要查历史版本）。故 V39 增加 `sys_doc_version`，发布时写快照，修订只把主档状态回 `DRAFT` 且 `version_no+1`。
6. **文件夹 `code` 不能改**：`path` 由 `code` 逐级拼成（`/QP/WI`），改 code 要递归重算整棵子树路径；收益（改个编码）远小于风险（路径脏掉后子树过滤全错）。改为：code 创建后不可改（400），只允许改名/排序。

**结论与决策**
- 独立建模 4 张表（`sys_doc_folder` / `sys_doc_template` / `sys_doc` / `sys_doc_version`），**不动 `plm_object` 与 `doc_master`**；正文先落 `sections jsonb`（章节化，便于按模板生成与逐章审批），文件中心通过预留 `file_id` 后续挂接（待接入）。

- 模板删除不影响已生成文件（文件里是自己的章节快照）；有发布版本记录的文件只能作废不能删。
- 权限 `qlt.sysdoc.read/write`（与 `qlt.*` 前缀一致，自动随 V37/V38 的批量授权口径授予 SYS_ADMIN/BUSINESS）。

**遗留与后续动作**

## EXP-20261106-31 体系审核要不要自建整改流程；检查表与审核的关系；关闭审核卡什么条件

**目标问题**：P8-3 第 2 条要求「体系文件 … + 审核记录」，P8-1 已有质量问题 8D 闭环。要定：① 审核发现的不符合项是自己一套整改，还是复用质量问题；② 检查表在模型里是什么地位（可选附件还是审核的实体）；③ 审核能不能在"有未关闭发现项"时关闭；④ 不符合项的关闭条件；⑤ 审核与体系文件之间要不要强关联。

**范围与方法**：先看 P8-1/P8-2 已有能力（`V37__quality_issue.sql`、`V38__quality_8d_template.sql`、`QualityIssueService` 的状态机与校验、`QualityTemplateService.applyToIssue`），确认 `qlt_issue.source` 是否已含审核来源（`V37__quality_issue.sql:28` 枚举含 `AUDIT`，前端 `frontend/src/api/quality.ts:14` 已译为"审核"）；据此设计 `V40__qlt_audit.sql` + `QltAuditService`，用 `QltAuditSmokeTest#auditPlanToIssueClosedLoop` 跑「计划→检查表→开始→不符合项→转问题→8D 关闭→关闭不符合项→关闭审核」全链路。

**关键发现**
1. **整改流程不该重建**：`qlt_issue` 已有「多轮整改 + 提交验证(要求当前轮全 DONE) + 验证打回开新一轮 + 8D 模板一键生成措施」，且 `source=AUDIT` 早在 V37 就预留了。审核侧若再建一套整改表，等于让同一个不符合项在两处各改一份，责任人也对不上——结论：**不符合项只做"登记 + 转出"，整改闭环完全复用 P8-1**（`QltAuditService.java:370` 调 `issueService.create`）。
2. **检查表必须是审核的实体，不是附件**：若允许空检查表就"开始审核"，审核沦为只填结论的表单。故 `start` 要求 `itemCount > 0`（`QltAuditService.java:264`），检查项带条款号与证据，详情直接算 OK/NG/NA 统计。
3. **"关闭审核"是最容易被滥用的动作**：发现项还没整改就把审核关掉，是内审/外审最常见的失效点。故 `close` 拒绝存在 `status='OPEN'` 的不符合项（`QltAuditService.java:278`）。
4. **不符合项关闭要有证据链**：只有"已转问题 且 该问题已 CLOSED"才允许关闭（`QltAuditService.java:399`）。这样审核台账上的"已关闭"必然对应一个验证通过的质量问题，可反查。
5. **转出后不符合项只读**：整改内容以质量问题为准，审核侧只留 `issue_code` 往回看（更新/删除一律 409），否则两边描述会漂移。

**结论与决策**

## EXP-20261106-32 供应商评级维度写死还是可配；总分与等级怎么算；确认时状态联动到哪一步

**目标问题**：P8 第 3 条要求「供应商准入与评级（可配字段）」。要定：① 评级维度（质量/交付/价格/服务）写死成列，还是做成可配方案；② 总分口径（直接加总、还是按满分折算）；③ 等级阈值放哪（固定四档 vs 可配档位）；④ 方案改了以后历史评级怎么办；⑤ 确认评级时供应商状态要不要跟着变（PENDING→QUALIFIED？D 级→SUSPENDED？）；⑥ V41 预留的 `sup_supplier.attrs jsonb` 要不要用来存配置。

**范围与方法**：先看 V41 留下的扩展位（`backend/plm-app/src/main/resources/db/migration/V41__supplier.sql:36` 的 `attrs jsonb`）与 P8-2 8D 模板"生成即快照"的先例（`EXP-20261106-29` 关键发现 1），再设计 `V42__sup_rating.sql` + `SupplierRatingService`，用 `SupplierRatingSmokeTest#ratingSchemeSnapshotAndSuspend` 跑「建方案（权重合计校验）→ 发起评级（漏维度/超满分/周期格式/同周期重复）→ 改草稿重算 → 确认回写 → 方案改维度后历史不变 → D 级暂停」全链路。

**关键发现**
1. **维度必须可配，不能写死成列**：外协看过程能力、物流看时效与货损、服务类看响应，写死字段就只能改代码适配客户。故 `sup_rate_scheme`（方案）+ `sup_rate_dim`（维度：code/name/weight/max_score/enabled）两张表（`V42__sup_rating.sql:22`、`:41`），`attrs jsonb` 保持"供应商自身扩展属性"语义，不拿来做配置（配置要跨供应商共享，塞进每家一行等于复制 N 份）。
2. **权重合计必须等于 100**：否则"总分"会随方案漂移（80 分制的方案与 100 分制的方案不能横向比较）。服务层在 `normalizeDims` 里精确比较，不等即 400（`SupplierRatingService.java:412`）。前端同样提示 `权重合计 x / 100` 并禁用保存。
3. **总分按比例折算，不能直接加总**：维度满分可配（有的客户用 5 分制），因此 `总分 = Σ(得分/满分 × 权重)`（`SupplierRatingService.java:548` 的 `recompute`），保留 2 位小数；实测 90/80/70/60 打 40/30/20/10 权重得 80.00 → B 级。
4. **等级阈值存 jsonb 而非四列**：档位数与阈值都属业务可配（有的客户只分 A/B/C）。`grade_rule` 存 `[{"grade":"A","min":90}...]`，写入前按 `min` 降序排序（`SupplierRatingService.java:385` 的 `normalizeGradeRule`），数组顺序即"从高到低"；`gradeOf` 取第一个满足 `total ≥ min` 的档（`SupplierRatingService.java:570`）。
5. **历史评级必须是快照**：`sup_rate_item` 冗余 `dim_code/dim_name/weight/max_score`（`V42__sup_rating.sql:84`）。测试里确认 95 分 A 级后把方案改成质量 50/价格 10，历史记录的权重仍是 40/30/20/10、总分仍 95.00——否则"按什么标准打的分"就无法审计。
6. **确认才回写主档，且只单向暂停**：`confirmRating` 才写 `sup_supplier.grade/rating_score/rated_at`（`SupplierRatingService.java:307`）；低于等于 `suspend_grade` 时置 `SUSPENDED`（`shouldSuspend`，`SupplierRatingService.java:581`），但**评级变好不会自动恢复**——解除暂停要走准入复审或人工判断，否则"这个月分数回来了"就把上个月的停用决定抹掉了。同时确认评级不改 `PENDING → QUALIFIED`：那是准入评审的职责（P8-5-2），两件事不能混。
7. **同供应商+方案+周期唯一**：`uk_sup_rate` 部分唯一索引（`V42__sup_rating.sql:80`）挡重复；想重评先删草稿或换周期。已确认的评级不可改、不可删（409），审计留痕。

**结论与决策**
- 表：`sup_rate_scheme` + `sup_rate_dim` + `sup_rate` + `sup_rate_item`；`sup_supplier` 增 `grade/rating_score/rated_at` 三列。
- 维度整表替换保存（与 8D 模板、检查表口径一致），旧维度行物理删除不影响历史（历史只依赖快照列）。
- 方案被评级引用时禁删（409），要停用请把 `status` 改为 `INACTIVE`；停用后不能发起新评级。
- 预置一套通用方案 `RATE-DEFAULT`（质量 40 / 交付 30 / 价格 20 / 服务 10，A≥90 B≥75 C≥60 D≥0，D 级自动暂停）作为开箱可用样例（`V42__sup_rating.sql:113` 起）。
- 权限 `sup.rating.read/write`，与 `sup.*` 前缀口径一致。

**遗留与后续动作**
- 评级数据目前手动录入，没有自动取数（来料合格率来自 IQC、交付准时率来自采购到货）——待 P8-5 后续接质量/采购数据源，现在只提供接口口径。
- 没有"多评委打分取平均"：一条评级只有一个 `rated_by`；若要委员会评审需加 `sup_rate_vote`（待需求确认）。
- 没有评级到期提醒与自动排程（等 P9 通知通道）。
- 准入评审（PENDING→QUALIFIED 的检查项与审批）仍待做，本次只做评级，两者刻意解耦。

- 前端：供应商详情抽屉新增「准入评审」区块（明细/提交/通过/驳回），发起对话框带 6 条预置检查项与结果/证据列。

**遗留与后续动作**

## EXP-20261106-35 集成任务要不要落表；幂等与重试放在哪一层；字段映射做成配置还是代码

**目标问题**：P9 第 1 条要求"集成框架 + 重试/死信/幂等"。要定：① 调用对端是直接发还是落任务表；② 幂等靠应用判断还是库约束；③ 重试同步做还是后台做、何时进死信；④ 字段映射放配置（表）还是写在适配器代码里；⑤ 认证信息怎么存与怎么回传。

**范围与方法**：先看既有的外部调用形态（`plm-stage/.../doc` 与 `supplier` 均无外部 HTTP 调用，本项目此前全部是内部数据），按 P9 后续要接金蝶五条链路（物料/BOM/图文档/工艺路线/请购单）反推最小可复用底座，设计 `V45__integration.sql` + `IntegrationService` + `ItgHttpSender` + `MappingEngine`，用 `IntegrationSmokeTest#mappingIdempotentRetryDeadLetterReplay` 起 JDK 内嵌 HTTP 端点跑通真实发送与失败路径。

**关键发现**
1. **必须落任务表**：对端会超时、会 500、会重复收到；没有 `itg_job` 就无法回答"这条到底发没发、发了几次、对端回了什么"，也没法做重试与死信重放（`IntegrationService.java:526` 的 `execute` 是整个模块的唯一发送入口）。
2. **幂等交给数据库**：(endpoint_id, biz_type, biz_key) 唯一索引（`V45__integration.sql:64` 起的 `uk_itg_job_biz`），应用只做"先查后插"的快路径，并发穿透由唯一键兜住并回落到"返回已存在任务 + duplicated=true"（`IntegrationService.java:410`）。用应用判断挡并发一定会漏。
3. **报文快照不可变**：提交时就把映射结果写进 `request_payload`，重放用快照、不重新取源数据（`IntegrationService.java:474`）。否则"当年发了什么"这条证据会随源数据变化而消失。
4. **重试异步 + 死信人工**：提交时只同步发一次，失败置 FAILED 并算 `next_retry_at`（30s×2^(n-1)，上限 1 小时）；attempt 用尽置 DEAD，只能 replay（`IntegrationService.java:491`）。同步重试会把请求线程占满，用户侧表现为"提交没反应"。
5. **抢占式执行**：发送前 `UPDATE ... WHERE status IN ('PENDING','FAILED')`，影响行数为 0 就放弃（`IntegrationService.java:526`）。定时任务与人工触发并发时不会重复发送。配套 `reclaimStaleRunning`（`:515`）回收进程重启后卡在 RUNNING 的任务。
6. **映射必须是配置**：五条链路的字段名对不上是常态（客户改字段名/换账套），写死在适配器里就得改代码重新发布。规则只支持声明式点路径 + 六种转换（`MappingEngine.java:62`），刻意不支持脚本——配置里塞脚本既无法静态校验，也无法在界面里解释。
7. **认证信息只写不读**：`auth_config` jsonb 存密钥，接口只回传 `authConfigured` 布尔（`V45__integration.sql:23` 起的 `auth_config`）。更新时 `authConfig` 传 null 表示"保持不变"，避免前端拿着脱敏数据保存把密钥清空——这是配置类接口最容易踩的坑。
8. **端点地址必须 http/https 绝对地址**：`ItgHttpSender.parseUri` 拒绝 `file://` 等 scheme，否则配置填错会让服务端读本地文件。

**结论与决策**
- 四张表：`itg_endpoint`（端点 + 认证 + 超时）/ `itg_mapping`（对象 + 方向 + 规则 jsonb）/ `itg_job`（任务 + 快照 + 状态 + 重试）/ `itg_log`（每次尝试）；权限 `itg.config.read/write` + `itg.job.read/write`。
- 状态机：`PREVIEW`（dry-run 只出报文）/ `PENDING` / `RUNNING` / `SUCCESS` / `FAILED`（待重试）/ `DEAD`（死信）。
- 端点删除只软删并连带停用映射，历史任务保留（任务列表 LEFT JOIN 端点仍能显示编码）。
- 后台定时任务 `ItgRetryJob`（`nexplm.integration.retry.enabled` 开关，默认 60s）负责回收卡死 + 到期重试。
- 前端 `/itg` 集成中心：端点 / 映射 / 任务三页签，含手动提交（可 dry-run 预览）、发送、重放与报文对照。

**遗留与后续动作**
- `auth_config` 明文存库（未接 KMS/加密），生产前需加密或改为引用外部密钥（**待验证**：等安全加固阶段统一处理）。
- 任务表无归档策略：长期运行后 `itg_job/itg_log` 会膨胀，需要按保留期归档或分区。
- 未做限流与熔断：对端持续 500 时仍会按退避重试，缺少"连续失败 N 次自动熔断端点"的保护。
- 报文里没有签名/时间戳（P9-4 Webhook 才需要签名），回传（IN 方向）也尚未实现解析入库。
- `payload` 完整内容只截断存库，排障需看对端日志（后续可考虑对象存储旁路保存全文）。

**目标问题**：P9 第 3 条要求"OpenAPI：API Key + 作用域 + 限流 + 审计；对外提供对象查询/创建/文件上传下载"。要定：① 外部凭证形态（长期 JWT / API Key / OAuth2）；② 作用域如何参与既有鉴权；③ 限流实现层次；④ 对外是否开放"创建对象"；⑤ 密钥怎么存、怎么轮换。

1. **不能用长期 JWT**：JWT 无状态，签发后到过期前收不回来；外部 key 泄漏必须能立刻失效。故 API Key 走库校验（`enabled`/`expires_at` 改一行立即生效，见 `ApiKeyService.java:183`）。

3. **作用域映射成权限字面量**：`object.read` → `open.object.read`，由 `@PreAuthorize` 判定，与站内权限同一套机制。这样"有 key"不等于"能调站内管理接口"，也不需要自造鉴权（`ApiKeyAuthenticationFilter` 只往 authorities 里放 `open.*`）。

5. **限流是单机内存固定窗口**（`ApiKeyService.java:243`）：多实例部署各算各的，需要 Redis。这一点如实写在类注释与遗留里，没有假装解决。
6. **对外不开放"创建对象"**：写对象要过元数据校验、生命周期、权限、审计，直接给外部开 create 等于绕过全部内部规则。外部要写数据应走集成任务（P9-1），由内部规则产生对象。故 `/open` 只提供对象查询 + 文件上传下载。
7. **公司维度强制**：所有 `/open` 查询都带 `company_id = API Key 所属公司`，外部客户端看不到其他公司数据。

**结论与决策**
- 表 `itg_api_client`（`V46__api_client.sql:19`）：`key_prefix` + `key_hash`、`scopes` jsonb、`rate_limit_per_min`、`enabled`、`expires_at`、`last_used_at`；权限 `itg.client.read/write`。

- 对外接口 `/open/whoami`、`/open/objects`、`/open/objects/{id}`、`/open/files/{fileId}/content`、`POST /open/files`。
- 前端集成中心新增「API 客户端」页签：作用域勾选、限流、到期日，创建/轮换后弹窗展示 Key 并支持复制。

**遗留与后续动作**
- 限流单机内存，多实例需换 Redis（或网关层限流）。
- 未做 IP 白名单/来源限制；也未记录每次调用的审计日志（只有 `last_used_at`），排障能力弱于站内接口。

- 开放接口没有版本化路径（`/open/v1/...`），对外承诺稳定性前应先加版本前缀。

## EXP-20261106-39 Webhook 订阅与投递要不要复用集成任务表；事件从哪发；签名怎么对齐

**目标问题**：P9-4 要「事件订阅（文档发布、变更生效、任务完成）+ 签名 + 重试」。要定：① 订阅与投递交几张表、能否复用 `itg_job`；② 三类事件从哪里发出（业务层直调集成层，还是发领域事件）；③ 签名放在报文内还是请求头；④ 同一事件重复触发会不会给对端重复通知。

**范围与方法**：先盘点 P9-1 的任务表语义（`(endpoint_id, biz_type, biz_key)` 幂等 + `MappingEngine` 映射 + `itg_log` 每次尝试），再核对三类业务动作的写入点（`LifecycleService.transition`、`ChgExecService.execute`、`ProjectTaskService.approve/updateTask`），最后用 `WebhookSmokeTest` 起真 HTTP 端点验证签名与重放。

**关键发现**
1. **不能复用 `itg_job`**：那张表的幂等键是「端点 + 业务类型 + 业务键」且报文必须过 `MappingEngine`；webhook 的语义是「一条订阅 × 一个事件 = 一条投递」，报文必须原样冻结才能"重放发出与当初完全一致的内容"。混用会让两种幂等语义互相牵制（`WebhookService.java:41-43` 类注释）。
2. **订阅与投递必须分表**：改一次 URL 若影响历史投递，排障时"发到哪、发了什么"就无从复原；故 `itg_webhook_delivery.payload` 存 jsonb 快照（`V48__webhook.sql:43`）。
3. **业务层不该依赖集成层**：三类事件都发到 `platform.object.event`（`ObjectStateChangedEvent`/`ChangeExecutedEvent`/`TaskCompletedEvent`），只带 id 与状态；由 `WebhookPublisher` 补编码/名称/版本。发布点：`LifecycleService.java:238`、`ChgExecService.java:246`、`ProjectTaskService.java:311`（直接改状态到 DONE）与 `:617`（审核通过）。
4. **用 `AFTER_COMMIT` 而不是普通监听**：事务回滚时对外通知是错的（"已发生事实"才发）；同时 `fallbackExecution = true` 兜住无事务调用，避免"事件发了没人收到"（`WebhookPublisher.java:45`）。监听体内全部 try/catch——对端不可达不能反向影响本系统业务提交。
5. **PostgreSQL jsonb `?` 与 JDBC 占位符冲突**：`events ? 'doc.released'` 会被 JDBC 当参数标记，解析报错；改用 `events @> CAST(? AS jsonb)` 传 `["doc.released"]`（`WebhookService.java:301`）。
6. **幂等靠唯一索引**：`(webhook_id, event_key)` 唯一 + `ON CONFLICT DO NOTHING`（`WebhookService.java:360`），业务侧重试触发不会给对端重复通知；重试复用同一行（只增 `attempt`），所以"重试"与"重复事件"是两件事。
7. **签名放请求头**：`X-NexPLM-Signature: sha256=<HMAC-SHA256(secret, 原始报文)>`（`WebhookService.java:398`、`:538`），另带事件/投递/订阅/时间戳，便于对端按投递去重与排障；密钥只写不读回，轮换后旧密钥立即失效。

**结论与决策**
- 新增 `itg_webhook` + `itg_webhook_delivery`（Flyway V48）与权限 `itg.webhook.read/write`；接口 `/api/v1/itg/webhooks`（订阅 CRUD、`rotate-secret`、`test`、投递分页/详情/`replay`、事件字典）。
- 事件驱动：领域事件 + `@TransactionalEventListener(AFTER_COMMIT)`；报文信封 `{event, eventId, occurredAt, companyId, data}`。
- 失败退避重试（base 30s 指数、上限 1h）、次数用尽进 `DEAD`、死信按原报文快照重放；`WebhookRetryJob` 每 60s 回收 `SENDING` 并重试到期项。
- 验证：`WebhookSmokeTest` 3 用例全绿（真 HTTP + 真签名 + 事件过滤 + 失败重放 + 任务完成），后端全量 72 用例（71 通过 + 1 压测跳过）无回归；前端 `vue-tsc` + `vite build` 通过。

**遗留与后续动作**
- 未做「事件重发窗口」与「按事件类型的订阅分组管理」，订阅多时列表只能按关键字筛（当前 `size` 上限 200）。
- 只实现了 3 类事件；P5 的 ECN/问题、P6 的工艺路线发布等若要订阅，需要各自补领域事件与服务端载荷（**待排期**）。

## EXP-20261106-40 SSO 用会话还是无状态 state；id_token 要不要验签；LDAP 的坑在哪

**目标问题**：P9-5 要接 OIDC 与 LDAP/AD。要定：① 回调怎么防 CSRF（服务端会话还是自签 state）；② id_token 只解析不验签行不行；③ LDAP 认证有哪些"看着成功其实被绕过"的坑；④ IdP 里的人怎么落到本站账号。

**范围与方法**：盘点现有认证链路（`AuthService` 登录/刷新/`JwtService`、`SecurityConfig` 白名单、`sys_user.auth_provider`），读 `sys_user`/`sys_user_role` 表结构确定建号所需字段；用 `SsoSmokeTest` 起真 OIDC IdP（RSA 私钥签 id_token + JWKS + 令牌端点）跑通全链路，LDAP 侧用不可达地址验证失败语义。

**关键发现**
1. **必须无状态**：`SecurityConfig` 是 STATELESS（`SecurityConfig.java:50`），没有 HttpSession 可存 state/nonce；故 state 自签（base64url(JSON) + HMAC-SHA256，内含 provider/verifier/nonce/10 分钟过期），回调验签即完成 CSRF 与防重放（`OidcClient.java:83`、`:102`）。
2. **不验签等于信任任何人**：只解析 id_token 的话，任何能访问回调地址的人伪造一个 payload 就能登录。改为按 `header.kid` 取 JWKS 的 RSA 公钥验 RS256，并校验 `iss`/`aud`/`exp`/`nonce`（`OidcClient.java:158`）；同时只接受 RS256，避免 `alg=none` 类降级。
3. **PKCE 要真发出去**：verifier 存在 state 里，换令牌时作为 `code_verifier` 发送（`OidcClient.java:128`）；测试里断言 IdP 确实收到非空 verifier，否则"配了 PKCE 但没生效"无法被发现。
4. **LDAP 空密码是真实漏洞**：不少目录在密码为空时退化为匿名 bind 并成功，等于任意账号零密码登录；故先拒绝空口令再进入查找/绑定（`LdapAuthenticator.java:42`）。
5. **过滤串必须转义**：`{0}` 直接拼进 filter 会被 `*)(uid=*` 绕过；按 RFC 4515 转义五个字符（`LdapAuthenticator.java:136`）。
6. **账号落点是产品决策，不能靠猜**：定为「绑定表 → 同公司同名账号自动绑定 → 自动建号 → 拒绝」四级（`SsoService.java:232`）。自动建号用随机密码哈希（本地登录不可用）、`auth_provider='SSO'`、按 `default_role_code` 授最小角色（`:301`）。

**结论与决策**
- 新增 `sys_sso_provider` + `sys_user_sso`（Flyway V49），权限 `sys.sso.read/write` 只授 SYS_ADMIN。
- 接口：公开 `GET /auth/sso/providers`、`GET /auth/sso/{code}/authorize`、`POST /auth/sso/{code}/callback`、`POST /auth/sso/{code}/ldap-login`；管理 `/sys/sso-providers`（CRUD，密钥只写不读回、详情回 `secretFields`）。
- 令牌出口统一为 `AuthService.issueToken`（原 `buildToken` 提升为 public），本地登录/刷新/SSO 共用，避免三套签发逻辑漂移。
- 验证：`SsoSmokeTest` 3 用例全绿（含自动建号与二次登录复用），后端全量 75 用例（74 通过 + 1 压测跳过）无回归；前端 `vue-tsc` + `vite build` 通过。

**遗留与后续动作**
- LDAP 侧只验证了配置校验与失败语义，**未对真实 AD/OpenLDAP 联调**（本机无目录服务）；`objectGUID` 为二进制属性，`String.valueOf(attr.get())` 会得到乱码而不是 GUID 字符串，生产接 AD 时应改用 `entryDN` 或对 `objectGUID` 做十六进制转换（**待验证**）。

## EXP-20261107-01 转换器入参到底是什么；命令怎么派发到 exe；成功/失败怎么回传

**约束前提**：本次全部为**本地开发机**上的静态分析 + 本地进程试运行。未登录 `198.168.6.23`（蓝本中 FileServer / CommandService 的地址，仅作为文本证据引用），未调用任何远程接口、未连接 8897/9000/9001-9003 端口（用户 2026-11-07 明确要求）。

**目标问题**：`docs/01` ADR-10 决定新系统保留「转换代理」、Java 不实现 CAD 解析。要落地该代理，必须知道旧系统 Windows 转换节点上的**进程级契约**：`HoteamFileToPDFEntrance.exe`（以及 `HoteamFileToPDF.exe`、`HoteamBigDWGToPDF.exe` 等族）被谁调用、带什么参数、输入输出在哪、结果如何通知调用方。

**范围与方法**：读 `PLMSOFT/DistributedFileServer` 下四个一级目录（`CommandService`、`ConfigCenter`、`FileConversionService`、`FileServer`）的配置与 `Bin` 清单；对 `FileConversionService/Bin` 内 76 个 exe/dll 做 UTF-16 双对齐字符串提取（.NET `#US` 堆奇偶对齐需各取一次，否则中文提示串会漏）；解析 `DistributedFileServer/CommandService/Temp` 下 5549 个历史 `.trans` 命令文件并统计命令/扩展名分布；在本地用临时命令文件实测两个转换器的入参行为（重定向 stdout + 超时 kill）。

**关键发现**

1. **服务是四段式，职责分明**：`DistributedFileServer` 一级只有 `CommandService`（.NET Core 派发，主程序 `hoteam.icp.commandservice.daemon.exe` / `conversionstart` / `assignserverstart`）、`ConfigCenter`、`FileConversionService`（Windows 侧真正干活的 Bin/Config/Plugins/Signature）、`FileServer`（文件存储 + `FileServiceConfig.xml` 扩展名策略）。转换器**不在** FileServer 里跑，而是在独立的 Windows 转换节点上由 CommandService 拉起。
2. **扩展名→转换命令的权威定义**在 `FileServer/Config/FileServiceConfig.xml:27-35`：`dwg`（`:30`）= `TransCommand="FileToPDF" TransCheck="*.pdf" AfterCommand="WaterMark"`；`report`（`:29`）额外 `NoSourceFile="true"`；`jpg/png/gif/bmp`（`:22-26`）无需转换。`TransCheck` 就是「产物存在性校验」的 glob。
3. **命令名→exe 的映射在 `FileConversionService/Config/CommandServiceConfig.xml`**：`CommandDeal`（`:50-62`）如 `FileToPDF → HoteamFileToPDF.exe`（`:51`）、`HoteamBigDWGToPDF → HoteamBigDWGToPDF.exe`（`:62`）、`OfficeCOMToPDF → HoteamOfficeComToPDF.exe`（`:57`）；转换节点按端口分三组：`CommonEndpoint 9001`（`:16`）、`CADEndPoint 9002`（`:30`）、`ReportTEndpoint 9003`（`:42`），同组内同名转换器串行、不同组可并行。
4. **每种扩展名该派给哪个 exe** 由 `FileConversionService/Config/FileConversionConfig.xml:33-55` 的 `BrowseType/@DealExe` 决定，例如 `dwg`（`:45`）走 `HoteamBigDWGToPDF.exe`（同文件 `:61` 备注：大数据量 dwg 用 `HoteamFileToPDF.exe` 会卡死），`doc/xls/ppt`（`:46-51`）走 `HoteamAsposeToPDF.exe`，`prt/idw/slddrw`（`:33-39`）走 `HoteamDraftDrwToPDF.exe`。
5. **派发单元 = 一个 JSON 命令文件**：`CommandService/Temp/<guid>.trans`（实测 5549 个）。内容示例字段：`Command`（`FileToPDF`/`FileToWrite`/`FileToThumbnail`）、`SrcFile`、`DesDir`、`AfterCommand`、`SubFileList`、`FileServerIP/FileServerPort`、`FileServiceVolumnPath`、`ConversionObjectInfo{ObjectID,ObjectName,ObjectCreator,ObjectCreateTime}`、`<命令类型>专属字段`（如 `FileToWrite` 才有 `WriteInfo`/`DicUserAndImageInfo`/`ProcessID`）。历史分布：`FileToPDF/.report` 4821、`FileToPDF/.dwg` 373、`FileToWrite/.dwg` 278、`FileToPDF/.slddrw` 30、`FileToWrite/.xlsx` 19、`FileToPDF/.brd` 5 等——**主流量是工艺卡片（report）转 PDF，不是 CAD**。
6. **转换器入参只有一个：命令文件路径，没有任何 `-i/-o` 风格开关**。证据链（三条互相印证）：
   - 接口程序集 `Hoteam.InforCenter.FileConvert.Interface.dll` 内嵌中文提示：`命令文件不存在：`、`源文件SrcFile为空`、`目标路径DesDir为空`、`转换命令中原文件路径为空`、`需要转换的文件不存在：`、`解密原文件文件异常：`、`转换失败解密的临时文件缺失：`、`反签后的文件不存在`、`删除临时文件失败！`——全部是「读 .trans 后做校验」型错误，不存在参数个数错误分支（只有 `args.Length == 0`）。
   - 本地实测 `HoteamFileToPDFEntrance.exe` 无参 → stdout `HoteamFileToPDFEntrance:args.Length == 0`；传 `notexistproc_aa` → `命令文件不存在：notexistproc_aa`。
   - 本地实测 `HoteamFileToPDF.exe "<合法 .trans>"`（`SrcFile` 指向不存在的 dwg）→ `需要转换的文件不存在：<SrcFile>`，证明它读到并解析了命令文件。
7. **进度与结果靠标志文件回传，不靠退出码**：每条命令在 `CommandService/Temp/COMMANDINFO_<CommandID>/<ConversionID>/` 下产生 0 字节标志 `Begin.trans` / `End.trans` / `Error.trans`（该命名串在接口 DLL 中为 `\Begin.trans`、`\End.trans`、`\Error.trans`）。实测全库 `Begin.trans` 27 个、`Error.trans` 30 个、**`End.trans` 0 个**——成功命令的工作目录被清理，只剩失败/中断残迹。同目录还落 `file.desc`（内容形如 `LocalName:123.slddrw`，用于把 UUID 文件名还原成原始文件名）、`thumbnial.jpg`（拼写沿用旧系统）、以及源文件副本。
8. **产物命名**：正片 `00000.pdf`，占位 `00000.pdf.default`（`IsGenerateDefaultFile`/`NoSourceFile` 场景，见 `FileConversionConfig.xml:29` 的 `NoSourceFile` 与 `FileServiceConfig.xml:29`）；PDF 之后还要过 `WaterMark`（水印图 `Config/shoukongyouxiao.bmp`，配置在 `FileConversionConfig.xml:26-27`）。
9. **`HoteamFileToPDFEntrance.exe` 不是主转换器，是「打印式兜底」的前置清理器**：整包仅 7168 字节，字符串/元数据里只有 `ExecutePDF`、`GetKillList`、`GetProcesses`、`Process.Kill`、`GetSettingValue`、`PDFPrinterClear`，对应 `FileConversionConfig.xml:5` 的 `PDFPrinterClear="winword;excel;powerpnt;et;wps"`；即：调 PDF 打印机（`:3` `Foxit Reader PDF Printer`）前先把会占用文件的 Office/WPS 进程清掉，失败则记 `Clear error` / `ToPDF error! file:`。它**不能**独立完成 CAD 解析。

**结论与决策**

- 旧系统的转换契约可以完整复刻，不必逆向 CAD 库：`写 <guid>.trans（JSON）→ 启动 DealExe "<trans绝对路径>" → 轮询 COMMANDINFO_*/<conversionid>/ 下的 End.trans / Error.trans → 到 <DesDir>/00000.pdf 取产物`。
- 新系统侧（NexPLM）维持 `docs/01` ADR-10 的「Java 只判定 + 代理执行」路线；本次补的是**代理侧的进程级契约**，Java 端不需要引入任何 CAD/Office 解析依赖。
- 若将来自研替代转换器，**必须沿用同一契约**（唯一参数=命令文件、同一套标志文件名、同一产物目录约定），这样旧 Windows 转换节点与新服务可互换、可灰度。
- 复刻优先级应据实测流量重排：`report`（工艺卡片）占 4821/5549 ≈ 87%，`dwg` 373 条次之；先把卡片转 PDF 打通比先啃 CAD 更划算。

**遗留与后续动作**

- `HoteamFileToPDFEntrance` 走 Foxit 打印机的**完整成功路径未验证**（本机无该打印机，且按约束不连外部机）——**待验证**。
- `End.trans` 到底由 CommandService 轮询写入还是转换器自写，尚未定论；当前只能确定「成功的命令在工作目录里不留 End」。可查 `hoteam.icp.commandservice.core.dll` 的字符串进一步确认——**待验证**。
- `.trans` 的 `DatasetID` / `Volumn` / `OriginalFileServerInfo` 等字段在转换器内部的实际用途未逐字段验证（目前只确认 `Command`/`SrcFile`/`DesDir`/`AfterCommand`/`SubFileList` 必读）——**待验证**。
- 需产品确认：新系统是否需要「工艺卡片转 PDF」（旧系统主流量）；若需要，`report` 类型依赖 `HoteamReportToPDF.exe` + Chrome 类渲染（`FileConversionConfig.xml:12-13` 的 `ReportToPDFScale`），迁移成本需单独评估——**待确认**。

## EXP-20261107-02 HOTEAM 转换器能否重编译成 Windows/Linux 双跑

**约束前提**：纯本地静态分析（PE 头 + 元数据字符串），未登录 `198.168.6.23`、未在本机运行任何转换器做实际转码。

**目标问题**：`docs/03` 第 260 条已确认转换契约可复刻。方案讨论中提出「反编译并重编译 `HOTEAM*.EXE` 与配套 DLL，使其同时支持 Windows 与 Linux」。需判定该路线在技术上是否成立、边界在哪、哪些能力可换开源实现。

**范围与方法**：对 `FileConversionService/Bin` 下 76 个 exe/dll 逐个解析 PE 头（`IMAGE_FILE_HEADER.Machine` 判架构 + Optional Header 数据目录第 15 项 `CLR Runtime Header` 判托管/原生），得到 22 原生 / 54 托管；再对每个 `Hoteam*.exe` 抽取元数据字符串，匹配 COM ProgID、原生 DLL 名、ActiveX、注册表与打印栈关键字。工具链现状：本机 `dotnet` / `mono` / `ilspycmd` 均未安装。

**关键发现**

1. **转换内核是 22 个原生 x86 Windows DLL，全部无源码、无 Linux 构建**：ODA/Teigha 系列 11 个（`TeighaX_22.2src_14.dll`、`OdaX_22.2src_14.dll`、`TD_DbCore/TD_Db/TD_Ge/TD_Gi/TD_Gs/TD_Root/TD_Alloc/TD_DbRoot/TD_SpatialIndex/TD_Zlib`）+ `FreeImage.dll`、`libhpdf.dll`、`libpng16.dll`、`zlib.dll`、`DrawLib.dll`、`ModifyAttributes.dll`。它们被托管外壳 P/Invoke 调用，Linux 上无法加载（PE/x86/Win32 API）。
2. **三条关键路径绑死 Windows 特有机制**（托管字符串证据）：
   - `HoteamFileToPDF.exe` / `HoteamBigDWGToPDF.exe` → `TeighaX` + `kernel32`（DWG 内核，ODA 商业组件）；
   - `HoteamOfficeComToPDF.exe` → `Word.Application`（Office COM 自动化）；`HoteamDraftDrwToPDF.exe` → `Creo` / `SolidWorks` COM + `user32`；
   - `HoteamReportToPDF.exe` → `AxREPORTEDITLib`（ActiveX OCX 报表编辑控件）。
3. **54 个托管程序集是 .NET Framework 4.8 / x86**（`*.exe.config` 均为 `sku=".NETFramework,Version=v4.8"`）。理论可反编译改写为 .NET 8，但改完仍要调用上面那些原生 DLL 与 COM → **只有在剥掉 CAD/Office COM 之后才有跨平台意义**。
4. **真正"纯托管、无 Windows 依赖"的只有清理类小工具**：`HoteamClearProcess.exe`、`HoteamFileToPDFEntrance.exe`（前者杀进程、后者杀 Office 进程后交打印机），二者本身也没有移植价值——它们的作用是给 Windows 打印链路清场。
5. **外呼型依赖也已确认**：`HoteamFileToSvl.exe` / `HoteamFileToThumbnail.exe` / `HoteamFileToImage.exe` 不 `Process.Start` 任何外部 exe（字符串里只有自身名），全部靠托管→原生 DLL 完成，说明三维轻量化同样卡在原生内核上，不能靠"换外部命令"绕过。
6. **本机无 .NET/Mono 工具链**（`C:\Program Files\dotnet` 不存在、无 `mono`、无 `ilspycmd`），即便走"反编译→重编译"路线也需先装 .NET SDK，并需 Aspose/Spire 等商业库的 Linux/.NET Core 授权。

**结论与决策**

- **整包移植不成立**：DWG（TeighaX）、Creo/SolidWorks 工程图（COM）、报表卡片（ActiveX）三条路径在 Linux 上没有技术出路，不是工作量问题。
- **可跨平台的能力只有"非 CAD"子集**，且应以开源/商业替代重建、而不是移植旧 exe：Office→PDF 用 LibreOffice headless；PDF 水印/返签用 PDFBox（Java，纯托管，与 NexPLM 技术栈一致）；图片→PDF/缩略图用 PDFBox + Thumbnailator。
- **三维与二维 CAD 分两条新路**：三维 `STEP/IGES/STL/OBJ` 用 OCCT（native 或 WASM）转 `glTF` 交 three.js 直渲，彻底绕开 `.svlx`；二维 `dwg` 用 ODA File Converter（Linux 版）或 LibreDWG → DXF → 前端渲染，需验证授权与质量（**待验证**）。
- **能力边界必须写进产品口径**：`prt/sldprt/catpart/casm/cprt` 等闭源 CAD 原生格式在 Linux 侧无解，只能保留 Windows 节点代理或明确"不支持在线预览"。

**遗留与后续动作**

- ODA File Converter 是否提供可免费商用的 Linux 版、LibreDWG 对国内图纸（含天正/中望扩展实体）的解析质量——均**待验证**，需实际取样本文件测试。
- OCCT 走 `occt-import-js`（WASM，前端直渲）还是服务端 native 转 glTF，取决于并发与首屏时延目标——**待决策**。
- 反编译产物如需保留（`Hoteam.InforCenter.FileConvert.Interface.dll` 的命令文件解析逻辑有参考价值），需先装 .NET SDK 与 ILSpy——**待授权**。
- 本机工具链缺口：无 .NET SDK / Mono / ILSpy；若坚持"移植旧 exe"路线必须先补齐，且仍需 Aspose/Spire 商业授权。

## EXP-20261107-03 本地实跑旧转换器：框架全通，DWG 分支缺应用层控件

**约束前提**：全部在本机（Windows，.NET Framework 4.8 已装）执行，未登录 `198.168.6.23`。为隔离实验，把 `FileConversionService` 复制到 `%TEMP%\convtest` 运行，蓝本目录只读。经用户授权，以管理员安装过蓝本自带的 `TeighaX_Setup_4.0.1.msi`（可卸载）。

**范围与方法**：按 EXP-20261107-01 的命令协议构造 `.trans`，以真实历史命令文件为模板改写 `SrcFile`/`DesDir`/`AfterCommand`；用 `Doc/Dataset/Config/UploadFile/CAD/HT_系统管理员.dwg` 与 `Config/Empty.pdf` 做对照；用 32 位宿主 `LoadLibraryEx + DllGetClassObject` 直接探测每个 COM 类的可用性；用 `Reflection` 读取 `Interop.OdaX.dll`/`Interop.TeighaX.dll` 的 coclass CLSID，再与 Bin 内 22.2 构建逐一比对。

**关键发现**

1. **转换框架（非 CAD 部分）本地完全可用**：以 `Empty.pdf` 为源、`Command=FileToPDF` 调用 `HoteamFileToPDF.exe`，退出后产出 `00000.pdf` + `00000.pdf.default` + `thumbnial.jpg` + **`End.trans`**。这同时证伪了 EXP-20261107-01 的遗留问题——**`End.trans` 由转换器自身写入**，不是 CommandService 轮询写的。

6. **`Bin\TeighaX_22.2src_14.dll` / `OdaX_22.2src_14.dll` 的 `DllRegisterServer` 是空实现**（`DllGetClassObject` 里自注册返回 S_OK 却一个键都不写），必须按 CLSID 手工注册——这也解释了为什么原厂部署要靠 MSI/安装器。

**结论与决策**

- **Windows 复用旧转换器的路线成立**，但只覆盖「非 CAD → PDF/图片」：`pdf/txt/office(Aspose)/report` 等分支可直接用；`.trans` 协议、产物命名、`End.trans`/`Error.trans` 标志、缩略图均已本地验证。

## EXP-20261107-04 蓝本里有没有 SViewConverter 的启动参数；dwg→PDF 到底谁是引擎

**约束前提**：纯本地静态分析与本机试运行。未登录 `198.168.6.23`（FileServer/CommandService 地址，仅作文本证据），未调用任何远程接口。本机 `C:\Program Files\HoteamSoft\SViewConverter Enterprise(64bit)` 的试跑也仅在本机，与蓝本目录无关（蓝本只读）。

**目标问题**：拟用华天 SViewConverter Enterprise（本机已装，浮动锁 `10.1.202.26:8831`）承担 DWG→PDF，需要它的命令行入参。先问：旧系统 PLM 蓝本里是否已存在 `SViewConverterCmd` 的调用或参数模板可抄？

**范围与方法**：全蓝本 grep `SViewConverter` / `DWG 2D` / `PDF 2D` / `fileConversionConfig`；对 `DistributedFileServer/FileConversionService/Bin` 下 `HoteamFileToSvl.exe`、`HoteamBigDWGToPDF.exe`、`Hoteam2DDWGToPDF.exe`、`HoteamCADService.dll`、`Hoteam.InforCenter.FileConvert.Interface.dll` 做 ASCII/UTF-16 双对齐字符串提取；解析 `Bin/SVL/SVLConvertConfig.cfg` 头部字节；读本机安装目录 `SViewConverterCmd.cfg` 并用 12 组参数模板实跑 `SViewConverterCmd.exe`。

**关键发现**

1. **蓝本里没有任何 `SViewConverterCmd` 的调用或参数模板**。全库仅两处命中 SViewConverter，且都是 Web 端 ActiveX 下载声明：`PLMSOFT/Server/InforCenter/Config/SViewConverter/ActiveX.activex:3`（`Url="~\InforCenter\Config\SViewConverter\SViewConverterEnterprise.exe" Version="9,2,0,4" AutoDownLoad="false"`）与同目录 `ActiveX.dic:5-6`（`华天软件-SViewConverter Enterprise 9.2.0.4`）。即 SViewConverter 在旧系统里只承担**客户端本地 ActiveX 插件**角色，服务端转换链路从不调用它。

## EXP-20261107-05 SViewConverterCmd 的官方启动参数（含实测验证）；许可为何恒失败

**约束前提**：参数来源为**官方文档联网检索**（`service.sv3d.cn/help/document/SView9.1|9.2/SViewConverter API.html`、`anydwg.com/help/dwg-to-pdf-pro/command.htm`），本机 `web_fetch` 直链全部 10s 超时，最终靠搜索摘要取到原文片段。实测在本机 `C:\Program Files\HoteamSoft\SViewConverter Enterprise(64bit)` 执行，输入为临时 dwg，输出到 `%TEMP%\svccmd`，未连任何远程接口（仅转换器自身向浮动锁 `10.1.202.26:8831` 申请许可）。

**目标问题**：`EXP-20261107-04` 已确认蓝本里没有 `SViewConverterCmd` 的调用，12 组参数模板全负。需要从官方渠道确定它真正的启动参数，并区分「参数错」与「许可错」。

**范围与方法**：按官方 API 文档「3.总接口 SviewConverterCmd 接口调用方式」的参数表构造命令；格式串严格取 `SViewConverterCmd.cfg` 的 `InputFormat`/`OutputFormat` 原值；四条并行检索 + 本机实测（重定向 stdout、180s 超时、检查产物目录与 `.log`）。

**关键发现**

1. **总接口是 5 个位置参数，不是 4 个**（官方 SView9.1/SView9.2 API 文档）：

   ```
   SViewConverterCmd.exe "InFilePathName" "InFileFormat" "OutPath" "OutFormat" "configfilePath"
   ```

   | 参数 | 含义 | 备注 |
   |---|---|---|
   | InFilePathName | 输入文件全路径 | 必填 |
   | InFileFormat | 输入文件格式 | 必填，须等于 cfg 的 `InputFormat` |
   | OutPath | 输出**目录**（非文件名） | 必填 |
   | OutFormat | 输出格式 | 必填，须等于 cfg 的 `OutputFormat` |
   | configfilePath | 配置文件全路径 | 必填，即 `SViewConverterCmd.cfg` |

   官方原文：「根据参数中 InFileFormat 和 OutFormat 和格式配置文件《SViewConverterCmd.cfg》自动调用对应转换程序」——即它是**调度总入口**，按格式表找到 `ConverterInterface` 再拉起子转换器。`EXP-20261107-04` 的 4 参数模板（`"in" "out.pdf" "DWG 2D" "PDF 2D"`）参数个数与顺序双错，因此恒定 `-1`。
2. **格式串必须逐字取 cfg 原值**：`InFileFormat="DWG 2D (*.dwg)"`、`OutFormat="PDF 2D (*.pdf)"`（`SViewConverterCmd.cfg` 的 `InputFormat`/`OutputFormat` 字段）。仅写 `DWG 2D` 不等于该字段值。
3. **实测：参数完全正确，程序已走到真正的转换环节**。命令与输出：

   ```
   SViewConverterCmd.exe "…\in.dwg" "DWG 2D (*.dwg)" "…\out1" "PDF 2D (*.pdf)" "…\SViewConverterCmd.cfg"

   can not parse xml
   Exe path: …\Converters\CADExchanger
   V233- R20230630
   A flexlm license isn't available
   File Format = 35
   no license,code =200
   RetCode:-4
   ```

   产物目录生成 `in.dwg.pdf.log`（507 字节），证明**已定位到 `CADExchanger.exe` 子转换器并写日志**，不再是我在 04 里判断的「解析前退出」。
4. **`-4` 是官方码表里的「没有转换许可」**（同一文档的返回码表：`0` 成功、`-1` 输入参数不正确、`-2` 没有转换许可、`-4` 没有转换许可、`4` 输入输出路径为空、`7` 转换过程出错）。日志进一步给出许可根因：

   ```
   Par:<in.dwg>  PDF 2D  <out>/in.dwg.pdf  …\SViewConverterCmd.ini
   RegOpenKeyEx fail,error code:2   HKEY_CURRENT_USER   (-[VerifyLic.cpp Verify::GetLicDirByReg]:1535)
   Get REGEDIT  fail !
   License error:DWGPDF 2D
   ```

   即：内部把 5 参数重组为 `(输入文件, 输出格式, 输出文件路径, ini)`，随后 `VerifyLic.dll` 去 `HKEY_CURRENT_USER` 读许可目录注册表项，`error code:2` = `ERROR_FILE_NOT_FOUND` → 许可校验直接失败。
5. **许可机制从 `VerifyLic.dll` 字符串还原**：`HKCU\Software\FLEXlm License Manager`、`SView_LICENSE_FILE`、`\HoteamSoft\License\sviewdr.lic`、`Verify::GetLicDirByReg` / `Verify::GetLicPath` / `getLocalLicFilePath`、错误码 `ERROR_REGLICDIR`/`ERROR_OUTOFLICDATE`/`LICENSE_FILE_FOUND`/`ERROR`。结论：它是**本地 `.lic` 文件校验**（注册表给出目录，拼 `HoteamSoft\License\sviewdr.lic`）。
6. **本机三条许可路径全部不通**：`HKCU\Software\FLEXlm License Manager` 不存在；`C:\ProgramData\HoteamSoft`（官方手册指定的 `DataKitLic` 位置）不存在；设 `LM_LICENSE_FILE`/`SView_LICENSE_FILE`/`HOTEAM_LICENSE_FILE` = `8831@10.1.202.26` 后重跑输出**完全不变**（仍 `no license,code =200` / `RetCode:-4`）。另外启动 GUI（`SViewConverterEnt.exe`）等 45s 让其完成网络授权，`HKCU` 下**依旧没有**任何 flex/lic 键——说明 GUI 的网络锁与转换器的本地 lic 是**两套独立机制**，GUI 授权成功不会让 CLI 获得许可。
7. **其它转换器的官方契约（同一文档，可备用）**：
   - `CadConverter.exe "filePath" "outputPath" "configfilePath"`（`filePath` 输入全路径、`outputPath` 输出目录、`configfilePath` 配置全路径），返回码同上；示例 `"…\CadConverter.exe" "E:\modeltest\test.prt" "E:\svl" "…\default.config"`。
   - `IdConverter.exe "filePath" "outputPath"`（两参数）；`RVMConverter.exe` 为三参数。
   - 这正好**逐位解释**了蓝本 `HoteamFileToSvl.exe` 里的 `"{0}" "{1}"  "{2}"` =（输入文件，输出目录，配置文件），04 的遗留项就此闭合。
8. **旧系统 dwg→PDF 引擎（AnyDWG）的官方命令行**（`anydwg.com/help/dwg-to-pdf-pro/command.htm`）：
   ```
   单文件：dp.exe /InFile source-file-name /OutFile destination-pdf-file-name
   整目录：dp.exe /InFolder source-folder /OutFolder destination-folder /ConvertType conversion-type [/IncSubFolder]
   ```
   注意官方可执行名为 `dp.exe`，蓝本里是 `anydpp.exe`（`Any DWG` 的 **PDF Pro** 变体），开关风格一致但需实测确认。

**结论与决策**

## EXP-20261107-06 SView 许可文件 `licence(3).dat` 的结构与绑定对象

**详细报告**：`NexPLM/docs/EXP-20261107-06-SView许可文件licence(3).dat深度分析.txt`（16 章，含 SHA-256、完整 75 行 HEXDUMP、148 组配对表、37 个码位映射表、rand 序列验证、合规边界）。

**约束前提**：纯本地静态解析用户提供的一个文件副本（1188 字节，2026-11-07 01:18 落盘），未修改、未生成任何许可文件，未向 `sview.sv3d.cn` 发起申请。

**目标问题**：`EXP-20261107-05` 已确认 `SViewConverterCmd` 参数正确、`RetCode:-4` 仅因许可缺失。用户提供了一个许可文件 `licence(3).dat`，需要判断它是什么、能不能解决本机 `-4`。

**范围与方法**：读文件头 128 字节 + 全文 uint32 解包；按 `[uint32 count]` + `count × (uint32, uint32)` 假设校验伪随机位；对数据位做取值分布统计并按 4 位十六进制拼 UTF-16LE 码位还原明文；与本机 `Get-NetAdapter -IncludeHidden` 全适配器 MAC 比对；与 `VerifyLic.dll` 内嵌字符串交叉印证。

**关键发现**

1. **文件布局**（1188 字节 = 4 + 148×8，无尾部附加数据）：

   ```
   offset 0        : uint32 count = 148
   重复 count 次    : { uint32 噪声 ; uint32 一个十六进制字符的 ASCII 码 }
   ```

   噪声位是标准 **MSVC `rand()`（seed=1）** 序列：`41, 18467, 6334, 26500, 19169, 15724, 11478, 29358, 26962, 24464, ...`（前 19 项逐项吻合），作用是干扰肉眼/字符串扫描，不参与还原。
2. **数据位 = 十六进制字符**：取值分布为 `48(79次)=0 / 49(4)=1 / 50(16)=2 / 51(31)=3 / 52(3)=4 / 54(2)=6 / 55(4)=7 / 68(9)=D`，即 ASCII `0-9`、`A-F`。将 148 个 hex 字符**每 4 个拼一个 UTF-16LE 码位**（`0032`→`2`、`002D`→`-`、`0023`→`#`），恰好还原 **37 个字符**（148/4=37），长度自洽。
3. **明文内容**：

   ```
   2026-11-2#2027-3-31#00-67-C1-4C-07-37
   ```

   三段式 `起始日期#到期日期#MAC`：起始 2026-11-02（当日申请）、到期 2027-03-31（约 5 个月，典型临时许可）、绑定 MAC `00-67-C1-4C-07-37`。
4. **与 `VerifyLic.dll` 字符串一一对应**：该 DLL 内含 `License start date:`、`License end date:`、`License Native Mac`、`License File Mac:`、`License file version is`，与本文件的「起始/到期/MAC」三段吻合，可判定 `.dat` 就是该模块的许可数据形态（经混淆后），而非 flexlm 文本 `.lic`。
5. **MAC 与本机不匹配（决定性）**：本机全部适配器 MAC 为 `20-53-8D-3C-6F-6D`（Realtek 以太网，Up）与 `00-FF-E8-92-EB-87`（Sangfor SSL VPN 虚拟网卡），`-IncludeHidden` 亦无 `00-67-C1-4C-07-37`。**该许可是为另一台机器申请的**，即使放到位也过不了 MAC 校验。
6. **与 `-4` 的关系**：`EXP-20261107-05` 的 `-4` 是「找不到许可目录/许可文件」，本文件则说明「已有许可但绑错机器」，两者叠加，本机仍然无法转换。

**结论与决策**

- `licence(3).dat` 的格式与内容已完全确定：**混淆的三段式许可凭据（起始日、到期日、绑定 MAC）**，噪声位掩盖内容但不影响还原。
- **该文件不能解决本机 `-4`**，因为它绑定的是 `00-67-C1-4C-07-37`，不是本机任一网卡。
- 走正规途径只有两条：① 用本机 MAC `20-53-8D-3C-6F-6D` 重新申请；② 若 `00-67-C1-4C-07-37` 是公司另一台转换服务器，把文件交付到那台机器。**不采用改 MAC / 伪造许可的做法**（既违反授权协议，也会让授权审计失真）。
- 另需提示产品侧：官方手册写明**临时许可的输出格式有限**（仅 SVL1.0/SVL2.0/PDF 3D 等），`PDF 2D` 是否在临时许可范围内需向厂商确认——这是 `-4` 之外的第二道门槛，**待确认**。

**遗留与后续动作**

- 需用户确认 `00-67-C1-4C-07-37` 归属哪台机器（是否是旧系统转换节点 `198.168.6.23` 那类服务器）——**待用户确认**。

## EXP-20261107-08 文档预览改造：从「等转换代理」改为「浏览器内直接渲染」

**范围与方法**：读 `VisualService`（判定引擎）与 `VisualPreview.vue`（前端分发）确认现状；核对前端依赖清单；按「浏览器能否原生渲染」重新划分扩展名类别；用 SheetJS 造多 sheet + 中文表头 + 日期 + 空单元格的工作簿，以组件的实际读取参数回读比对数据结构。

**关键发现**

1. **原判定把文本也误伤了**：`TO_PDF` 集合含 `txt`，且判定顺序上 `TO_PDF` 排在 `PLAIN_TEXT` 之前（`VisualService.java` 原判定链），导致 `.txt` 被判成「需转换」而不是直接当文本看。本次把 `txt` 从 `TO_PDF` 移除并并入 `PLAIN_TEXT`。
2. **前端此前零预览依赖**：`frontend/package.json` 只有 element-plus / bpmn-js / pinia / vue / vue-router，PDF 靠 `<iframe>` 交浏览器内置查看器，Office 无任何渲染能力。

5. **两个库的体积必须拆包**：构建产物 `xlsx-*.js` 500.05 kB（gzip 163.12）、`docx-preview-*.js` 174.97 kB（gzip 51.62）。已用动态 `import()` 拆成独立 chunk，不进首屏。

**结论与决策**

- 引擎划分改为六类：`PDF` / `IMAGE` / `TEXT` / **`DOCX`** / **`SHEET`** / `NONE`，`SVIEW` 不变。`docx` 归 `DOCX`，`xlsx|xlsm|xls` 归 `SHEET`，`doc|ppt|pptx|xps|report|CAD` 仍归 `TO_PDF`（`needsConvert=true`）。

- 文本预览补 BOM 识别 + UTF-8/GB18030 自适应：国内存量 `txt/csv` 多为 GBK，`blob.text()` 按 UTF-8 解会变问号。
- 表格预览加保护：单 sheet 最多渲染 1000 行 / 80 列、文件上限 30MB，超出提示下载，避免超大宽表打满主线程与内存。

**遗留与后续动作**

## EXP-20261107-09 NexPLM 开发环境启动方式：后端改源码为何不生效

**约束前提**：本机开发环境实测。为排查「文档预览改动上线后页面仍不可用」，期间停止并重启了一次后端进程（未改数据库、未改代码）。

**范围与方法**：比对运行进程启动时间与 `nexplm.jar` / `VisualService.class` 时间戳；读进程命令行与父进程；读 `backend/boot.log` 确认实际数据源；核对 `application.yml` 默认值；重启后端后直接调 REST 接口验证返回值。

**关键发现**

1. **根因是运行时未更新，不是代码问题**：旧进程 `java -jar plm-app\target\nexplm.jar`（PID 41188，启动 00:16:24），而该 `nexplm.jar` 的 mtime 为 **00:13:32**，本次新编译的 `VisualService.class` mtime 为 **20:18:18**。即进程跑的是凌晨的包，`DOCX/SHEET` 判定逻辑根本不在里面 → 页面自然还走「需转换代理」分支。

4. **数据库是嵌入式 PG，不是常规安装**：`postgres.exe` 路径为 `C:\Users\lenovo\AppData\Local\Temp\embedded-pg\PG-<hash>\bin\postgres.exe`，监听 5432。`boot.log` 里实际连接是 `jdbc:postgresql://localhost:5432/postgres`（**库名 postgres，不是配置默认的 nexplm**），profile `dev`。这些由环境变量 `NEXPLM_DB_URL/USER/PASSWORD` 注入；用 `postgres/postgres` 实测可连。
5. **前后端端口分工**：前端 5173（Vite dev，改前端即时热更新）；后端 8080 是**纯 API**，访问 `/` 返回 401，不托管前端产物——即前端改动**不需要**重新打包后端。
6. **重启后接口验证通过**：`GET /api/v1/visual/docs/2118730400443428865` 返回 `engine=DOCX`、`needsConvert=false`、hint「Word 文档（.docx），浏览器内直接渲染」；同库的 `.dwg` 文档仍返回 `engine=PDF`、`needsConvert=true`（符合预期）。文件流 `GET /files/{fileId}/content` 返回 54,369 字节，magic `50 4b 03 04`（标准 OOXML zip）。

**结论与决策**

- **后端改动的生效链是「停进程 → `mvn -pl plm-app -am package -DskipTests` → 重启 jar」**，只 `compile` 或不重启都看不到变化。这解释了本次「预览不了」的全部原因。
- 重启时工作目录必须是 `backend`，因为 `NEXPLM_FILE_ROOT` 默认 `./data/files` 是相对路径，否则文件仓会指向别处。
- **排障口径**：前端页面不对先看后端接口返回（`engine` 字段），能直接区分「后端旧代码」与「前端渲染问题」，不必反复刷新猜测。
- 前端改动只需 Vite 热更新，无需重新构建后端；仅当前端产物要被后端托管时（本机不是这种模式）才需一起打包。

**遗留与后续动作**

- 原进程启动时的环境变量（`NEXPLM_DB_*` 等）未随进程保存，父终端已退出无法回溯；本次用嵌入式 PG 默认凭据 `postgres/postgres` 启动成功。若后续有正式启动脚本，应以脚本为准——**待确认**。
