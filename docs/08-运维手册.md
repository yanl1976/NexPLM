# NexPLM 运维手册（P10-7）

> 面向：部署与维护 NexPLM 的实施/运维人员。
> 配套：`deploy/docker-compose.yml`（中间件）、`deploy/upgrade.sh`（升级）、`deploy/backup.sh`（备份）、
> `deploy/perf/`（压测）、`docs/07-安全加固与等保自查.md`（安全口径）。

## 一、系统组成

| 进程 | 形态 | 默认端口 | 说明 |
|---|---|---|---|
| 后端 | Spring Boot 可执行 jar | 8080 | 同时提供 REST 接口与 Actuator |
| 前端 | 静态文件（`frontend/dist`） | 80/443 | 由 Nginx 托管，`/api` 反代到后端 |
| PostgreSQL | 容器 / 独立实例 | 5432 | 业务库；Flyway 管理表结构，Flowable 的 `ACT_*` 由引擎自管 |
| Redis | 容器 | 6379 | 缓存/会话辅助 |
| MinIO | 容器 | 9000 / 9001 | `NEXPLM_FILE_STORAGE=minio` 时存文件；`local` 时不用 |
| RabbitMQ | 容器 | 5672 / 15672 | 预留（当前业务流程同步执行，尚未接入异步消息） |

**部署形态是"三件套"**：中间件用 compose 起、后端跑 jar（systemd 托管）、前端 Nginx 静态 + 反代。
不要指望把 jar 塞进 compose 就完事——`deploy/docker-compose.yml` 里只有中间件，没有应用服务。

## 二、首次部署

### 1. 中间件

```bash
cd /opt/nexplm/deploy
cp .env.example .env      # 修改数据库/Redis/MinIO/RabbitMQ 口令
docker compose up -d
docker compose ps         # 全部 healthy 再继续
```

### 2. 后端

```bash
# 环境变量（写进 /etc/nexplm/nexplm.env，权限 600）
NEXPLM_JWT_SECRET=<32 字节以上随机串>        # 生产必须覆盖
NEXPLM_ADMIN_PASSWORD=<初始管理员密码>        # 首次启动建 admin，登录后强制改密
NEXPLM_DB_URL=jdbc:postgresql://<host>:5432/nexplm
NEXPLM_DB_USER=nexplm
NEXPLM_DB_PASSWORD=<口令>
NEXPLM_DB_POOL_MAX=60                        # 见"容量与调优"
NEXPLM_FILE_STORAGE=minio                    # 或 local
NEXPLM_FILE_ROOT=/opt/nexplm/data/files      # storage=local 时生效
```

`/etc/systemd/system/nexplm.service`：

```ini
[Unit]
Description=NexPLM Backend
After=network-online.target

[Service]
Type=simple
User=nexplm
WorkingDirectory=/opt/nexplm
EnvironmentFile=/etc/nexplm/nexplm.env
ExecStart=/usr/bin/java -Xms1g -Xmx2g -jar /opt/nexplm/nexplm.jar
SuccessExitStatus=143
Restart=on-failure
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload && systemctl enable --now nexplm
curl -fsS http://127.0.0.1:8080/actuator/health
```

首次启动会：执行 Flyway 迁移 → Flowable 建表 → 依据 `NEXPLM_ADMIN_PASSWORD` 建管理员。
**迁移失败会直接启动失败**，不要反复重启，先看日志里的 Flyway 报错。

### 3. 前端

```bash
cd frontend && npm ci && npm run build     # 产物 frontend/dist
rsync -a --delete frontend/dist/ /var/www/nexplm/
```

Nginx 关键片段：

```nginx
server {
    listen 443 ssl http2;
    server_name plm.example.com;
    root /var/www/nexplm;
    client_max_body_size 500m;             # 与后端 multipart 上限（500MB）对齐

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;           # 大批量导入/导出会跑很久
    }
    location / {
        try_files $uri $uri/ /index.html;  # 前端 history 路由
    }
}
```

## 三、配置项速查

| 环境变量 | 默认值 | 生产是否必改 | 说明 |
|---|---|---|---|
| `SERVER_PORT` | 8080 | 否 | 后端端口 |
| `SPRING_PROFILES_ACTIVE` | dev | 建议 `prod` | 运行环境标识 |
| `NEXPLM_JWT_SECRET` | 开发默认串 | **必改** | ≥32 字节随机；改了等于全员重新登录 |
| `NEXPLM_ADMIN_USERNAME` / `NEXPLM_ADMIN_PASSWORD` | admin / Admin@12345 | **必改** | 仅首次启动建号时生效 |
| —（CI） | — | **上线前必做** | 依赖漏洞扫描：`pwsh deploy/ci/security-scan.ps1`（trivy，HIGH/CRITICAL 即失败），用法见 `deploy/README.md` |
| `NEXPLM_HTTPS_ENFORCE` | false | **生产建议 true** | 开启后未带 `X-Forwarded-Proto: https` 的请求一律 308 到 https（探针 `/actuator/health|info` 跳过）。**必须部署在可信代理之后**，否则转发头可伪造 |
| `NEXPLM_PWD_MIN_LENGTH` / `_REQUIRED_CLASSES` / `_HISTORY_SIZE` / `_EXPIRE_DAYS` | 8 / 3 / 3 / 0 | 按等保要求 | 密码策略：最短长度、需含字符类数（大小写/数字/符号）、历史不可重用条数、有效期天数（0=不过期）。**注意**：开启有效期前需确认历史账号有 `pwd_updated_at`，否则会被判过期 |
| `NEXPLM_DB_URL` / `_USER` / `_PASSWORD` | localhost/nexplm | **必改** | |
| `NEXPLM_DB_POOL_MAX` | 20 | 按并发调 | Hikari 最大连接，见调优 |
| `NEXPLM_FILE_STORAGE` | local | 按需 | `local` / `minio` |
| `NEXPLM_FILE_ROOT` | ./data/files | 建议改绝对路径 | 内容寻址布局 `{root}/{sha0:2}/{sha2:4}/{sha}` |
| `NEXPLM_MINIO_*` | minioadmin | **必改** | endpoint/access/secret/bucket |
| `NEXPLM_FILE_SCAN` | noop | 按需 | 文件安全扫描实现：`noop`（不扫描）\| `clamav`（流式送检 clamd，检出即禁止下载） |
| `NEXPLM_CLAMAV_HOST` / `_PORT` / `_TIMEOUT_MS` / `_CHUNK_SIZE` | 127.0.0.1 / 3310 / 30000 / 8192 | 按需 | `scan=clamav` 时生效；超时含建连与读取，块大小 1KB~64KB |
| `NEXPLM_FILE_MAGIC_CHECK` | true | 按需 | 校验"文件头与扩展名一致"（pdf/图片/OOXML/老 Office/zip）；无统一签名的格式自动跳过，关掉需显式设 false |
| `NEXPLM_FILE_BLOCKED_EXT` | 见默认清单 | 按需 | 禁止上传的扩展名（逗号分隔，空串=不拦）。默认 `exe,dll,bat,cmd,ps1,scr,msi,com,pif,jsp,jspx,php,asp,aspx,html,htm,svg`；单文件与分片会话两个入口都校验 |
| `NEXPLM_FILE_MAINTENANCE` / `_RETAIN_HOURS` | true / 24 | 否 | 每小时回收孤儿文件、清理超时分片 |
| `NEXPLM_SMTP_*` | 空 | 按需 | 通知通道留空时回落到这里；两处都空会明确报"SMTP 未配置" |
| `NEXPLM_NOTIFY_RETRY` | true | 否 | 通知失败退避重试（base 30s，上限 1h，超限进死信） |
| `NEXPLM_WF_ERP_PUBLISH_ENABLED` / `_DRY_RUN` / `_ENDPOINT_CODE` | true / false / 空 | 按需 | 流程归档后自动下发金蝶；`_ENDPOINT_CODE` 填 `itg_endpoint.code` 指定测试/生产账套，**配了找不到会跳过下发、不回退**到其它账套；留空取 id 最小的启用端点 |
| `NEXPLM_PREVIEW_STALE_MINUTES` | 5 | 否 | 文档预览 `PENDING` 超过该分钟数视为僵尸（进程重启/线程中断），维护任务转 `FAILED` 可重试 |
| `NEXPLM_PREVIEW_RATE_LIMIT_PER_MINUTE` | 10 | 按需 | 每用户每分钟最多触发多少次预览生成；`0` 不限制 |
| `NEXPLM_PREVIEW_MAINTENANCE` | true | 否 | 预览维护任务开关（每分钟回收僵尸 + 清理限流窗口） |
| `NEXPLM_CAPP_PDF_FONT_PATH` | 自动探测 | 建议显式配 | 工艺卡片 PDF 中文字体；找不到时导出返回 400 而不是乱码 |

## 四、日常运维

```bash
systemctl status nexplm                 # 进程状态
systemctl restart nexplm                # 重启（graceful shutdown 已开启）
journalctl -u nexplm -n 200 --no-pager   # 最近日志
journalctl -u nexplm -f                  # 跟踪
curl -fsS http://127.0.0.1:8080/actuator/health
curl -fsS http://127.0.0.1:8080/actuator/metrics | head -c 500
```

日志级别可在运行时查看/调整（`/actuator/loggers` 已暴露）：
`curl -X POST -H 'Content-Type: application/json' -d '{"configuredLevel":"DEBUG"}' \
 http://127.0.0.1:8080/actuator/loggers/com.nexplm`。排查完记得改回 INFO —— 生产长期 DEBUG 会打满磁盘。

## 五、升级

### 标准流程（推荐）

```bash
# 1. 上传新包为 nexplm.jar.new（不要直接覆盖正在跑的 jar）
scp nexplm.jar yanl@host:/opt/nexplm/nexplm.jar.new
# 2. 执行升级（内部会先备份库与文件、停服、换包、验活，失败自动回滚 jar）
ssh yanl@host 'APP_DIR=/opt/nexplm bash /opt/nexplm/deploy/upgrade.sh'
```

### 手工流程（没有 systemd 或需要完全掌控时）

```bash
cd /opt/nexplm
bash deploy/backup.sh                        # ① 备份，别跳
systemctl stop nexplm                        # ② 停服
cp nexplm.jar backup/nexplm-$(date +%F-%H%M).jar
install -m 0644 nexplm.jar.new nexplm.jar    # ③ 换包
systemctl start nexplm                       # ④ 启动（Flyway 自动迁移）
for i in $(seq 1 40); do curl -fsS http://127.0.0.1:8080/actuator/health && break; sleep 3; done
```

### 回滚

| 情况 | 做法 |
|---|---|
| 新版本启动失败、**迁移未成功提交** | 还原旧 jar 重启即可（Flyway 事务会回退失败的迁移） |
| 新版本启动成功、迁移已执行，业务异常 | 还原旧 jar 重启，但要评估新版本是否已写入新结构数据；**jar 回滚不会撤销数据库变更** |
| 数据被写坏 | 用 `deploy/backup.sh` 的 dump 恢复：`pg_restore --clean --if-exists -h <host> -p 5432 -U <user> -d nexplm <dump>`，恢复后全员需重新登录 |

**升级红线**：`deploy/upgrade.sh` 在备份失败时会直接中止升级 —— 这是刻意的，宁可升不了，也不能没有可恢复点。

## 六、备份与恢复

```bash
# 每日 02:00 全量（数据库 + 本地文件仓），保留 14 天
0 2 * * * APP_DIR=/opt/nexplm BACKUP_ROOT=/data/nexplm-backup RETAIN_DAYS=14 \
          bash /opt/nexplm/deploy/backup.sh >> /var/log/nexplm-backup.log 2>&1
```

- **必须库与文件同时间点备份**：库里存 sha256 与归属关系，文件仓是内容寻址物理文件，只备一边都还原不全；
- `storage=minio` 时文件由对象存储侧负责（开启版本化 + 站点复制），脚本只备数据库；
- **RPO/RTO 基线**：日备份 RPO ≤ 24h；不含文件仓的库恢复 RTO 约 10~30 分钟（取决于库大小）；
- **每季度做一次恢复演练**：在隔离环境恢复上一份 dump + 文件包，抽查 10 个文档能否打开、附件能否下载 —— 没演练过的备份等于没有备份。

## 七、巡检清单

**每日**

- [ ] `systemctl is-active nexplm` 为 active；`/actuator/health` 为 UP
- [ ] 日志无 ERROR 激增（`journalctl -u nexplm --since today | grep -c ERROR`）
- [ ] 磁盘：`df -h`（文件仓 + PG 数据目录），低于 20% 告警
- [ ] 备份任务昨晚成功（看 backup 日志尾部与 `ls -lh backup`）

**每周**

- [ ] 慢查询：`SELECT query, calls, mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10`
- [ ] 通知死信：`SELECT count(*) FROM sys_notify_message WHERE status='DEAD'`，有则看错误原因
- [ ] 孤儿文件：`du -sh` 文件仓 vs `SELECT count(*) FROM file_object` 是否明显偏离
- [ ] 会话/连接：`SELECT count(*) FROM pg_stat_activity WHERE datname='nexplm'` 是否接近池上限

**每月**

- [ ] 依赖与安全补丁（见 `docs/07-安全加固与等保自查.md` 待整改项）
- [ ] 审计日志归档（避免无限增长）
- [ ] 容量趋势：库大小、文件仓大小、日增量

## 八、故障排查

| 现象 | 常见原因 | 排查与处置 |
|---|---|---|
| 启动即退出 | Flyway 迁移失败 / 数据库连不上 / JWT secret 太短 | `journalctl -u nexplm -n 100`；确认 `NEXPLM_DB_URL` 可达（`psql` 手连一次）；secret ≥32 字节 |
| health 一直 DOWN | 数据库不可达或连接池耗尽 | 看 health 详情（`show-details: when_authorized` 需带令牌）；`pg_stat_activity` 看是否有大量 idle in transaction |
| 登录 401 | 密码错 / 账号锁定 / 令牌过期 | 查 `sys_user.lock_until`；确认服务器时间同步（`timedatectl`），JWT 对时间敏感 |
| 接口 403 | 角色没授权限点 | 查 `sys_role_permission`；注意新版本可能新增权限点（如 `ana.dashboard.read`），升级后要补授权 |
| 列表看不到数据、详情 404 | 数据作用域限制（非缺陷） | 确认用户角色作用域是 COMPANY/ORG/SELF；`SYS_ADMIN` 是 ALL 才能看全集团 |
| 接口 500 | 多为运行环境而非代码 | 开发与生产连同一套库时，开发正常而生产 500 通常是连接池耗尽/跨网络延迟；看 `[Production] ...查询失败` 日志 |
| 上传失败 | 超过 multipart 上限（200MB/500MB）或存储不可写 | 查 Nginx `client_max_body_size` 与后端 multipart 配置；`storage=local` 时查 `NEXPLM_FILE_ROOT` 权限 |
| 下载很慢 | 未用 Range / 走了应用流式代理 | 大文件建议用 `GET /files/{id}/url` 拿预签名直链（minio）绕过应用 |
| PDF 导出 400 | 没配中文字体 | 安装 `fonts-noto-cjk` 或挂载字体并设置 `NEXPLM_CAPP_PDF_FONT_PATH`（`.ttc` 要带索引 `,0`） |
| 通知发不出 | SMTP/机器人配置为空、密钥被覆盖成空、死信 | 看 `sys_notify_message` 的 `status/last_error`；通道详情只回 `secretFields`，改配置留空＝保持不变 |
| 页面白屏 | 前端未 rebuild / Nginx root 指错 | 确认 `dist` 已同步、`try_files` 回退到 index.html |
| 时间相关异常（令牌/审批时间） | 服务器时钟漂移 | `timedatectl set-ntp true` + `chronyc tracking`；时钟偏差会导致 JWT 校验失败 |

## 九、容量与调优

- **连接池**：`NEXPLM_DB_POOL_MAX` 是硬上限。经验值 = `PG max_connections × 0.6 / 应用实例数`；PG 端
  compose 默认 `max_connections=200`，单实例给 60 比较稳。池子小于并发时，排队时间会全部算进接口耗时
  （压测时会表现为 P95 高但 CPU 不高）。
- **PostgreSQL**：`shared_buffers` ≈ 内存 25%，`work_mem` 16~32MB（BOM 递归查询吃内存），
  `effective_cache_size` ≈ 内存 50%；长期开启 `pg_stat_statements`。
- **文件仓**：`local` 用 SSD，容量按"年新增图纸量 × 3（版本）× 1.5（余量）"估；`minio` 至少 4 节点纠删码。
- **JVM**：`-Xms` = `-Xmx`（避免堆伸缩抖动），堆大小按并发与批量导入规模给，2~4G 起步。
- **批量导入**：单次事务体量大时把 `spring.servlet.multipart.max-request-size` 与 Nginx 上限同步放大，
  否则会先被 Nginx 413 拦掉。

## 十、安全运维

- 密钥轮换：`NEXPLM_JWT_SECRET` 变更会让所有会话失效（安排在维护窗口）；API Key 与通知通道密钥支持在界面轮换，
  详情接口只回 `secretFields`，改配置时留空表示保持原值。
- 审计：关键写操作走 `@Audit` 落审计表；审计表只追加，定期归档。
- 权限变更（尤其升级后新增权限点）要走变更记录，避免"升级后管理员看不到新菜单"这类问题。
- 等保配合与待整改项见 `docs/07-安全加固与等保自查.md`。
