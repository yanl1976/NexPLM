2. 判定：它不是 flexlm 文本许可（.lic）
================================================================================

  三类常见许可载体对照：

  (a) FlexLM/FlexNet 文本许可   —— 纯 ASCII，以 SERVER / FEATURE / INCREMENT 行开头，
                                   例如 "FEATURE sview ... 31-mar-2027 ..."。
                                   本文件不含任何此类可读文本，判定排除。

  (b) 直接序列化的结构体       —— 通常可见字段名或定长字符串。
                                   本文件首 512 字节做 ASCII 视图后仅得到乱码，排除。

  (c) 混淆后的自有格式         —— 本文件属于此类，详见第 3 节。

  判别依据：对全文做 ASCII（0x20-0x7E，长度>=5）与 UTF-16LE 两种方式抽取字符串，
  除结构性的极小片段外无可读内容；同时 uint32 解包后呈现强规律性（见第 4、6 节）。

================================================================================
3. 文件布局（二进制结构）
================================================================================

  整体结构（全部为小端序 little-endian，单位 uint32）：

      +------------------+-----------------------------------------------+
      | offset 0         | uint32  count = 148                           |
      +------------------+-----------------------------------------------+
      | offset 4 起      | count 个重复的 8 字节块：                     |
      |                  |   { uint32 noise ; uint32 data }              |
      +------------------+-----------------------------------------------+

  长度自洽验算：

      4 + 148 * 8 = 4 + 1184 = 1188 字节    == 文件实际大小，完全吻合
      即：文件头 4 字节 + 148 组 * 8 字节，无任何尾部附加数据、无填充、无校验尾部。

  两个字段的角色：

      noise —— 伪随机干扰位，不承载信息（第 6 节证明它是标准 MSVC rand 序列）。
      data  —— 真正的信息位，取值恒为某个十六进制字符的 ASCII 码（第 7 节）。

4. 完整十六进制转储
================================================================================

  见文末「附录 B：完整 HEXDUMP（1188 字节 / 75 行）」。

  头 32 字节说明（逐字段拆解）：

      94 00 00 00   -> uint32 = 0x00000094 = 148   （count，即配对总数）
      29 00 00 00   -> uint32 = 0x00000029 = 41    （pair[0].noise）
      30 00 00 00   -> uint32 = 0x00000030 = 48    （pair[0].data  = '0'）
      23 48 00 00   -> uint32 = 0x00004823 = 18467 （pair[1].noise）
      30 00 00 00   -> uint32 = 0x00000030 = 48    （pair[1].data  = '0'）
      be 18 00 00   -> uint32 = 0x000018be = 6334  （pair[2].noise）
      33 00 00 00   -> uint32 = 0x00000033 = 51    （pair[2].data  = '3'）

  注意 data 位的典型形态：低字节是 ASCII，高 3 字节恒为 0x00。
  这是"把单个字符当 uint32 存储"的典型特征。

================================================================================
5. count 字段
================================================================================

  offset 0 处 uint32 = 148，与后续数据块数量严格一致：

      (1188 - 4) / 8 = 148.0      整除，无余数

  这一自洽性反证了「[count][pair...]」的布局假设，而非「固定长度记录」或「变长记录」。

================================================================================
6. 噪声位：MSVC rand()，seed = 1（148/148 完全匹配）
================================================================================

  假设：pair[i].noise 由 C 运行库 MSVC 的 rand() 生成，种子为 1。

  MSVC rand() 的算法（与 glibc 不同，必须区分）：

      state = state * 214013 + 2531011          （32 位无符号回绕，模 2^32）
      rand() = (state >> 16) & 0x7FFF

  以 seed = 1 实测验证结果：

      匹配数      148 / 148
      不匹配数    0
      首个失配    -1（不存在）

  前 20 项序列（文件中的实际值）：

      41, 18467, 6334, 26500, 19169, 15724, 11478, 29358, 26962, 24464,
      5705, 28145, 23281, 16827, 9961, 491, 2995, 11942, 4827, 5436

  工程含义：

  1) 这不是加密，是「混淆」。噪声位不参与任何运算，只用于让文件在文本视图与
     字符串扫描下不可读，并让 uint32 数值看起来杂乱。
  2) 因为序列完全确定（seed 恒为 1），解析时可以直接跳过；也说明生成方未使用
     时间/机器相关的随机源，即同一明文在不同机器上生成的字节流一致（除数据位外）。
  3) 实现侧的一个坑：PowerShell 中 `-band 0xFFFFFFFF` 会把 0xFFFFFFFF 当作 int32 的 -1
     处理，导致 32 位回绕失效、验证全部失配；必须改用 `% 4294967296` 或 [uint64] 掩码。
     本报告首次验证即踩此坑（得到 matched=1 / mismatch=147），修正后为 148/148。

7. 数据位：单个十六进制字符
================================================================================

  pair[i].data 全部落在 ASCII 十六进制字符集内。取值分布（148 个）：

      value=48  ('0')  count=79
      value=49  ('1')  count=4
      value=50  ('2')  count=16
      value=51  ('3')  count=31
      value=52  ('4')  count=3
      value=54  ('6')  count=2
      value=55  ('7')  count=4
      value=68  ('D')  count=9

  合计 79+4+16+31+3+2+4+9 = 148，与 count 一致。

  两点结论：

  1) 字符集严格限定在 0-9 / A-F（本例未出现 5、8、9、A、B、C、E、F），
     没有出现任何非 hex 字符，说明 data 位的语义就是「十六进制文本的一个 nibble 行」。
  2) 148 恰好是 4 的整数倍（148 / 4 = 37），与第 9 节「每 4 位组成一个 UTF-16 码位」
     的还原方式严丝合缝，没有余数需要丢弃。

10. 明文与语义分段
================================================================================

  还原后的 37 个字符：

      2026-11-2#2027-3-31#00-67-C1-4C-07-37

  以 '#'（0x0023，出现 2 次，位于码位 09 与 19）为分隔符切分，得到 3 段：

  段号  值                     长度  语义
  ----  ---------------------  ----  ------------------------------------------
  [0]   2026-11-2              9     许可起始日期（年月日，月/日未补零）
  [1]   2027-3-31              8     许可到期日期（年月日，月/日未补零）
  [2]   00-67-C1-4C-07-37      17    绑定网卡 MAC（6 组、冒号/连字符分隔）

  分段长度校验：9 + 1(#) + 8 + 1(#) + 17 = 37，与总字符数一致，无剩余数据。

  语义推断的两条独立证据：

  1) 日期区间：起始日 2026-11-02 与文件落盘时间 2026-11-07 01:18 接近（相差 5 天），
     到期 2027-03-31 约为 5 个月，符合「临时许可」的典型形态。
  2) MAC 形态：00-67-C1-4C-07-37 是标准 6 字节 MAC，前缀 00-67-C1 为 IEEE 注册的
     OUI。该值与日期并列存放，且 VerifyLic.dll 中确有 "License Native Mac" 字样（第 11 节）。

  因日期未补零（"2026-11-2" 而非 "2026-11-02"），推断其生成侧采用格式化输出而非固定宽度，
  解析时不宜假设定长字段。

12. 与运行现象（RetCode -4）的关联
================================================================================

  本机用它调用转换总接口（参数见 EXP-20261107-05）：

      SViewConverterCmd.exe "<in.dwg>" "DWG 2D (*.dwg)" "<outdir>" "PDF 2D (*.pdf)" "<cfg>"

  实测 stdout：

      can not parse xml
      Exe path: ...\Converters\CADExchanger
      V233- R20230630
      A flexlm license isn't available
      File Format = 35
      no license,code =200
      RetCode:-4

  产物目录留下的日志（in.dwg.pdf.log）：

      Par:<in.dwg>  PDF 2D  <out>/in.dwg.pdf  ...\SViewConverterCmd.ini
      RegOpenKeyEx fail,error code:2   HKEY_CURRENT_USER   (-[VerifyLic.cpp Verify::GetLicDirByReg]:1535)
      Get REGEDIT  fail !
      License error:DWGPDF 2D

  按官方返回码表：0=成功，-1=输入参数不正确，-2=没有转换许可，-4=没有转换许可，
  4=输入输出路径为空，7=转换过程出错。

  因此本机 -4 的直接原因是「找不到许可」，而不是本文件内容有误。
  两类失败需区分：

      (A) 许可文件缺失 / 注册表目录未建立  -> 本机现状（error code 2 = ERROR_FILE_NOT_FOUND）
      (B) 许可文件存在但绑定 MAC 不匹配    -> 若把本文件强行放到本机，将落入此类

  本报告分析的 .dat 属于为另一台机器签发的许可，投入本机会命中 (B)。

================================================================================

  本机全部适配器（Get-NetAdapter -IncludeHidden 结果）：

      本地连接* 5..8        WAN Miniport (PPPOE / IPv6 / IP / Monitor)  -             无 MAC 或全 0

  结论：本机不存在 00-67-C1-4C-07-37 这块网卡，该许可与本机无绑定关系。

  用户已确认：00-67-C1-4C-07-37 即旧系统转换节点 198.168.6.23。
  该节点正是蓝本 DistributedFileServer 中 FileServer / CommandService 所在地址，
  也是旧系统 Windows 转换服务的实际执行者。

14. 结论
================================================================================

  1) 格式结论：licence(3).dat 是「[uint32 count] + count×{uint32 随机噪声, uint32 hex 字符}」
     的混淆容器，明文为 UTF-16 码位的十六进制文本化。148/148 噪声位与本文件数据位
     的还原过程均可精确复现，无未知字段、无尾部数据、无校验和。

  2) 内容结论：明文 = 2026-11-2#2027-3-31#00-67-C1-4C-07-37
     即「起始日 # 到期日 # 绑定 MAC」，是一个 5 个月有效期的临时许可。

  3) 归属结论：该许可绑定 198.168.6.23，不能用于本机；本机也不存在该 MAC。

  4) 对本机的影响：本机 SView 转换仍为 RetCode -4，需另循正规途径取得绑定本机
     （20-53-8D-3C-6F-6D）的许可，或改由 198.168.6.23 节点执行转换。

  5) 遗留（待验证）：
     - .dat 到 sviewdr.lic 的「安装许可」转换步骤未复现（本机
       HKCU\Software\FLEXlm License Manager 键不存在，GUI 亦不写该键）。
     - 官方手册称临时许可输出格式有限（SVL1.0/SVL2.0/PDF 3D 等），
       PDF 2D 是否在临时许可授权范围内，需向厂商确认。
     - 本文件未包含格式授权清单字段，故格式许可很可能另有载体（网络锁 / 服务端配置）。

15. 合规边界（重要）
================================================================================

  * 本报告只做只读识别与还原，用于解释「为何本机转换失败」，不提供、也不会提供
    修改 MAC / 重新编码生成可用许可的任何工具或步骤。
  * 软件许可绑定机器是厂商的授权控制措施。篡改许可文件使其在未授权机器生效，
    违反许可协议，并触及《著作权法》关于规避技术措施的规定。
  * 正确做法：① 用本机 MAC 向厂商申请对应许可；② 把该文件交付给 198.168.6.23 使用；
    ③ 改用不依赖该授权的引擎（如 ODA File Converter、AnyDWG 试用版）。

16. 复现方法（只读解析）
================================================================================

  等价伪代码（任何语言均可实现）：

      data  = read_all_bytes(file)
      count = uint32_le(data[0..3])
      hex   = ""
      for i in 0..count-1:
          off   = 4 + i*8
          noise = uint32_le(data[off .. off+3])      # 丢弃
          ch    = uint32_le(data[off+4..off+7])      # ASCII '0'-'9','A'-'F'
          hex  += chr(ch)
      assert len(hex) % 4 == 0
      plain = ""
      for j in 0..(len(hex)/4 - 1):
          plain += chr(int(hex[j*4 .. j*4+3], 16))
      print(plain)

  校验点（用于确认解析正确）：
      - count == 148
      - (filesize - 4) / 8 == count 且整除
      - hex 串长度 == 148，全为 hex 字符
      - noise 序列 == MSVC rand(seed=1) 前 148 项
      - 明文按 '#' 切成 3 段，段长 9 / 8 / 17
